=============================================================================
RELATIONSHIPS IN SQL (MySQL)
=============================================================================

-----------------------------------------------------------------------------
1. ONE-TO-MANY
-----------------------------------------------------------------------------

A single record in one table relates to multiple
records in another table.

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

One User → Many Orders

-----------------------------------------------------------------------------
users
-----------------------------------------------------------------------------

id | name
1  | Ajay

-----------------------------------------------------------------------------
orders
-----------------------------------------------------------------------------

id | product | user_id
1  | Laptop  | 1
2  | Phone   | 1

=============================================================================
2. ONE-TO-ONE
=============================================================================

Each record in one table is linked to exactly one
record in another table.

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

One User → One Passport

=============================================================================
3. MANY-TO-MANY
=============================================================================

Multiple records in one table relate to multiple
records in another table.

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

Students ↔ Courses

One student can join many courses.
One course can contain many students.

=============================================================================
MONGODB SCHEMA DESIGN
=============================================================================

MongoDB is document-based database.

Instead of tables + rows:
• Uses collections
• Stores JSON-like documents

=============================================================================
6 RULES OF THUMB FOR MONGODB SCHEMA DESIGN
=============================================================================

-----------------------------------------------------------------------------
1. Favor embedding unless there is a strong reason not to
-----------------------------------------------------------------------------

Store related data together if frequently accessed together.

-----------------------------------------------------------------------------
2. Needing to access an object on its own is a compelling reason
   NOT to embed it
-----------------------------------------------------------------------------

If child data must exist independently, use references.

-----------------------------------------------------------------------------
3. Arrays should not grow without bound
-----------------------------------------------------------------------------

Very large arrays reduce performance.

-----------------------------------------------------------------------------
4. Data that does not access together should not store together
-----------------------------------------------------------------------------

Separate unrelated frequently-changing data.

-----------------------------------------------------------------------------
5. Optimize schema for most common queries
-----------------------------------------------------------------------------

Design schema based on read patterns.

-----------------------------------------------------------------------------
6. Duplicate data when necessary
-----------------------------------------------------------------------------

MongoDB allows controlled duplication for performance.

=============================================================================
MONGO RELATIONSHIPS
=============================================================================

=============================================================================
ONE-TO-MANY → APPROACH 1 (ONE-TO-FEW)
=============================================================================

Store child documents directly inside parent document.

-----------------------------------------------------------------------------
USED WHEN
-----------------------------------------------------------------------------

• Small number of child documents
• Data accessed together frequently

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

{
  _id: ObjectId("651d1b116976164a9cbf5520"),

  username: "sherlockholmes",

  addresses: [

    {
      location: "221B Baker Street",
      city: "London"
    },

    {
      location: "P36 DownTown",
      city: "London"
    }
  ],

  _v: 1
}

-----------------------------------------------------------------------------
IMPORTANT
-----------------------------------------------------------------------------

• Addresses embedded inside user document
• No separate collection required
• Faster reads
• Good for small arrays

=============================================================================
ONE-TO-MANY → APPROACH 2 (REFERENCE IN PARENT)
=============================================================================

Store child document references inside parent.

-----------------------------------------------------------------------------
USED WHEN
-----------------------------------------------------------------------------

• Child documents are larger
• Need separate collection
• Moderate number of children

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

{
  _id: ObjectId("651d223314f1e136d6766e14"),

  name: "Rahul Kumar",

  orders: [

    ObjectId("651d1e5a06e366283d3ae002"),
    ObjectId("651d1e5a06e366283d3ae003")
  ],

  _v: 0
}

-----------------------------------------------------------------------------
IMPORTANT
-----------------------------------------------------------------------------

• orders array stores ObjectIds
• Actual orders exist in separate collection
• Similar to foreign key concept

=============================================================================
POPULATE() IN MONGOOSE
=============================================================================

populate() replaces ObjectIds with actual documents.

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

const findCustomer = async () => {

  let result = await Customer
    .find({})
    .populate("orders");

  console.log(result);
};

-----------------------------------------------------------------------------
WHAT populate() DOES
-----------------------------------------------------------------------------

Before populate:

orders: [ObjectId(), ObjectId()]

After populate:

orders: [{order1}, {order2}]

-----------------------------------------------------------------------------
IMPORTANT
-----------------------------------------------------------------------------

• Similar to JOIN in SQL
• Mongoose feature
• MongoDB itself uses $lookup internally

=============================================================================
ONE-TO-MANY → APPROACH 3 (ONE-TO-SQUILLIONS)
=============================================================================

Store parent reference inside child document.

-----------------------------------------------------------------------------
USED WHEN
-----------------------------------------------------------------------------

• Huge number of child documents
• Child collection grows massively

-----------------------------------------------------------------------------
EXAMPLE
-----------------------------------------------------------------------------

{
  _id: ObjectId("651d27deaadf315de08b7fa9"),

  content: "Hello World!",

  likes: 7,

  user: ObjectId("651d27deaadf315de08b7fa8"),

  _v: 0
}

{
  _id: ObjectId("651d2852f213f39556fddeea"),

  content: "Bye Bye",

  likes: 23,

  user: ObjectId("651d27deaadf315de08b7fa8"),

  _v: 0
}

-----------------------------------------------------------------------------
IMPORTANT
-----------------------------------------------------------------------------

• Each post stores parent user reference
• Parent does NOT store huge array
• Best for massive scaling

=============================================================================
FINAL UNDERSTANDING
=============================================================================

APPROACH 1 → EMBEDDING
-----------------------------------------------------------------------------
Parent stores full child documents

Good for:
• Small related data
• Fast reads

=============================================================================

APPROACH 2 → REFERENCES IN PARENT
-----------------------------------------------------------------------------
Parent stores child ObjectIds

Good for:
• Medium relationships
• Separate collections

=============================================================================

APPROACH 3 → REFERENCES IN CHILD
-----------------------------------------------------------------------------
Child stores parent ObjectId

Good for:
• Massive child collections
• Better scalability
