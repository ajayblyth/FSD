3. Why createPool() instead of createConnection()?

This is important for interviews.

createConnection()
const connection = await mysql.createConnection({...});

Creates one database connection.

You would generally have to manage that connection yourself.

createPool()
const pool = mysql.createPool({...});

Creates a pool of reusable connections.

Think:

Your Express App
       |
       v
   Connection Pool
   ┌───────────────┐
   │ Connection 1  │
   │ Connection 2  │
   │ Connection 3  │
   │ ...           │
   │ Connection 10 │
   └───────────────┘
       |
       v
     MySQL

Suppose 10 users make database requests:

Request 1 ──> Connection 1
Request 2 ──> Connection 2
Request 3 ──> Connection 3
...

When a query finishes, the connection can be reused.

Why pool is best practice for a web application
createConnection()
→ one connection
→ less suitable for many concurrent requests

createPool()
→ multiple reusable connections
→ handles concurrent requests better
→ avoids repeatedly opening/closing connections
→ better suited for Express/API applications

So for EventHub, I'd use a pool.

how many max connections can we set

There isn't one universal maximum. It depends on MySQL's server limit, your hosting plan, and your application's workload.

In your code:

connectionLimit: 10

means your Node.js application can have up to 10 active connections in its pool.

Important distinction
connectionLimit: 10
        ↓
Maximum connections THIS APP'S POOL can use

MySQL max_connections
        ↓
Maximum connections THE MYSQL SERVER allows overall

For example:

MySQL server
max_connections = 151

       ├── EventHub backend pool → 10
       ├── Another application   → 20
       ├── MySQL Workbench       → 1
       └── Other connections     → ...

So you shouldn't simply set connectionLimit to 151.

For a normal small Express application:

connectionLimit: 10

is a perfectly reasonable starting point.

As traffic grows, you can increase it based on actual workload and server capacity.

One important thing

A bigger pool doesn't automatically mean faster.

If you set:

connectionLimit: 1000

but your MySQL server can only handle a limited number of concurrent operations, you can actually create resource/connection pressure.

Interview answer:

connectionLimit defines the maximum number of connections that a particular application's connection pool can maintain/use. The practical limit depends on the MySQL server's max_connections, available resources, workload, and hosting configuration.

7. Why getConnection() and release()?

This:

const connection = await pool.getConnection();

asks the pool:

"Give me one available connection."

Then:

connection.release();

says:

"I'm finished. Put this connection back into the pool so somebody else can use it."

Important:

release()

does not normally mean "destroy the database connection."

It returns it to the pool.

8. But there's an even simpler way to run queries

With mysql2/promise, you can usually do:

const [rows] = await pool.query("SELECT * FROM users");

You don't need to manually call getConnection() for every simple query.

The pool handles the connection for you.

For example:

import pool from "../config/db";

const [rows] = await pool.query("SELECT * FROM users");

console.log(rows);

Flow:

pool.query()
     ↓
Pool finds available connection
     ↓
Executes SQL
     ↓
Returns result
     ↓
Connection becomes available again

This is one reason I recommend using a pool.

12. One important production improvement

Don't put SQL values directly into strings.

❌ Avoid:

const title = req.body.title;

const [rows] = await pool.query(
  `SELECT * FROM events WHERE title = '${title}'`
);

Instead use parameterized queries:

const title = req.body.title;

const [rows] = await pool.query(
  "SELECT * FROM events WHERE title = ?",
  [title]
);

The ? is a placeholder.

SQL:
SELECT * FROM events WHERE title = ?

Values:
["React Workshop"]

mysql2 safely handles the value.

This helps protect against SQL injection.

Why use a connection pool?

A connection pool maintains multiple reusable database connections. Instead of creating a new database connection for every request, the application borrows an available connection from the pool and reuses it after the query finishes. This is more efficient and better suited for applications handling multiple concurrent requests.

Database — Interview Definition

A database is an organized collection of data that allows applications to store, manage, retrieve, and update information efficiently.
It provides a structured way to persist data instead of keeping it only in application memory.
Databases can be relational (SQL) like MySQL or non-relational (NoSQL) like MongoDB.
Applications communicate with databases using queries or database APIs to perform CRUD operations — Create, Read, Update, and Delete.


## Relational vs Non-Relational Database

Relational (SQL) databases store data in tables with rows and columns and usually define relationships between tables using keys. Examples: MySQL, PostgreSQL, SQL Server, Oracle.

Non-relational (NoSQL) databases store data in more flexible structures such as documents, key-value pairs, graphs, or wide columns, rather than traditional tables. Examples: MongoDB, Redis, Cassandra.

SQL / Relational          NoSQL / Non-Relational
─────────────────         ─────────────────────
Tables                    Documents / other structures
Rows + Columns             Flexible schema
Relationships              Usually more flexible structure
MySQL                      MongoDB
PostgreSQL                 Redis
flexible?

Flexible means the data structure does not have to follow one fixed table structure for every record.

SQL — fixed structure

Suppose users table:

id | name | age | email

Every row follows the same columns:

1 | Ajay | 31 | ajay@gmail.com
2 | Rahul | 28 | rahul@gmail.com

You generally define the table structure first.

MongoDB — more flexible structure

One document could be:

{
  "name": "Ajay",
  "age": 31,
  "email": "ajay@gmail.com"
}

Another could have an additional field:

{
  "name": "Rahul",
  "age": 28,
  "email": "rahul@gmail.com",
  "phone": "9876543210"
}

MongoDB can store these documents with different fields.

So flexible schema means:

The database allows records/documents to have different structures without requiring every document to have exactly the same set of fields.

Important: Flexible does not mean "no rules" or "anything goes." Your application can still enforce a structure using Mongoose schemas, validation, etc.
