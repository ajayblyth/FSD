==================== INDEX IN MYSQL ====================

Definition:
• Index is a database object that improves query performance
• Works like a book index → helps find data faster

.

🧠 Simple idea
Without index → DB scans entire table (slow)
With index → DB uses shortcut (fast)
---------------------------------------------------------------
WHY USE INDEX
---------------------------------------------------------------

• Faster SELECT queries
• Quick searching, sorting, filtering
• Avoid full table scan

---------------------------------------------------------------
SYNTAX
---------------------------------------------------------------

-- Create index
CREATE INDEX idx_name
ON table_name(column_name);

---------------------------------------------------------------
EXAMPLE
---------------------------------------------------------------

CREATE INDEX idx_name
ON users(name);

-- Query becomes faster
SELECT * FROM users WHERE name = 'Ajay';

---------------------------------------------------------------
TYPES OF INDEX
---------------------------------------------------------------

1) PRIMARY KEY
• Automatically indexed
• Unique + NOT NULL

2) UNIQUE INDEX
• No duplicate values allowed

3) NORMAL INDEX
• Allows duplicates

4) COMPOSITE INDEX
• Index on multiple columns

Example:
CREATE INDEX idx_multi
ON users(name, city);

---------------------------------------------------------------
KEY POINTS
---------------------------------------------------------------

• Speeds up READ operations
• Slows down INSERT/UPDATE (index maintenance) //Because MySQL has to update the index structure too.
• Uses extra storage

---------------------------------------------------------------
INTERVIEW LINE
---------------------------------------------------------------

"Index improves query performance by allowing faster data
retrieval, similar to an index in a book."

==================== WHY CREATE INDEX IF PRIMARY KEY EXISTS ====================

TABLE:
---------------------------------------------------------------------
users(id PRIMARY KEY, name, email)

---------------------------------------------------------------------
CORE IDEA
---------------------------------------------------------------------
• Primary Key already creates an index ✔
• BUT it works only for that column (id)

---------------------------------------------------------------------
WORKING
---------------------------------------------------------------------

CASE 1: SEARCH USING PRIMARY KEY
---------------------------------------------------------------------
SELECT * FROM users WHERE id = 10;

✔ Fast (uses primary key index)


CASE 2: SEARCH USING OTHER COLUMN
---------------------------------------------------------------------
SELECT * FROM users WHERE email = 'a@gmail.com';

❌ Slow (full table scan)
• Primary key index on id is NOT used


---------------------------------------------------------------------
SOLUTION (CREATE EXTRA INDEX)
---------------------------------------------------------------------
CREATE INDEX idx_email ON users(email);


---------------------------------------------------------------------
AFTER INDEX
---------------------------------------------------------------------
SELECT * FROM users WHERE email = 'a@gmail.com';

✔ Fast (uses email index)


---------------------------------------------------------------------
KEY IDEA
---------------------------------------------------------------------
• Primary key index → only for id
• Extra index → for other searchable columns


---------------------------------------------------------------------
INTERVIEW LINE
---------------------------------------------------------------------
Primary key index works only on its column, so additional indexes
are created on frequently queried columns to avoid full table scans.
---------------------------------------------------------------------

Real examples

Suppose users:

id | name  | email              | city      | age | gender
---+-------+--------------------+-----------+-----+-------
1  | Ajay  | ajay@gmail.com     | Bangalore | 31  | M
2  | Rahul | rahul@gmail.com    | Delhi     | 28  | M
3  | Priya | priya@gmail.com    | Bangalore | 26  | F


| Column        | Query                              | Index useful?                     | Why                                      |
| ------------- | ---------------------------------- | --------------------------------- | ---------------------------------------- |
| `email`       | `WHERE email = 'ajay@gmail.com'`   | ✅ Very useful                     | Exact lookup                             |
| `id`          | `WHERE id = 100`                   | ✅                                 | Usually already indexed as PK            |
| `city`        | `WHERE city = 'Bangalore'`         | ✅ Sometimes                       | Frequent filtering, especially many rows |
| `age`         | `WHERE age > 30`                   | ✅ Sometimes                       | Range search                             |
| `created_at`  | `ORDER BY created_at DESC`         | ✅ Often                           | Sorting/filtering by date                |
| `status`      | `WHERE status = 'ACTIVE'`          | ⚠️ Depends                        | Few distinct values → less useful        |
| `gender`      | `WHERE gender = 'M'`               | ❌ Usually not very useful         | Only a few distinct values               |
| `name`        | `WHERE name = 'Ajay'`              | ✅ Often                           | Search by name                           |
| `description` | `WHERE description LIKE '%event%'` | ❌ Normal index usually won't help | Wildcard starts with `%`                 |
| tiny table    | any lookup                         | ⚠️ Often little benefit           | Table scan may already be cheaper        |


An index on name can usually help because the search starts from the beginning.

WHERE name LIKE '%jay'

A normal B-tree index generally can't efficiently use the index because the wildcard is at the beginning.

Composite index

If you frequently do:

SELECT *
FROM users
WHERE city = 'Bangalore'
  AND name = 'Ajay';

then:

CREATE INDEX idx_city_name
ON users(city, name);

can be useful.

Easy rule:

Good candidates:
WHERE column = ...
WHERE column > / < ...
ORDER BY column
JOIN ... ON column

Usually poor candidates:
Very few distinct values (gender, boolean, etc.)
Tiny tables
LIKE '%something'
Columns rarely used for searching/filtering


Also, an index isn't automatically beneficial just because a column exists. MySQL's optimizer decides whether using it is actually cheaper.

==================== B-TREE & B+ TREE INDEXING ====================

---------------------------------------------------------------
1) B-TREE INDEX (B-Tree = Balanced Tree)
---------------------------------------------------------------

Definition:
• Balanced tree data structure used for indexing
• Data stored in sorted order
• Nodes contain keys + data + child pointers

⚡ Why it’s fast
Tree is balanced
Each step removes half (or more) data
Very few comparisons
---------------------------------------------------------------
STRUCTURE
---------------------------------------------------------------

                [50]
              /      \
        [20,30]      [60,80]
        /    \        /    \
   [10]   [25]   [55]   [90]

• Data can exist at ANY level (root/intermediate/leaf)

---------------------------------------------------------------
HOW IT WORKS
---------------------------------------------------------------

• Start from root
• Compare value → move left/right
• May find data before reaching leaf

Example:
Search 30
→ 30 < 50 → go left
→ reach [20,30] → found

---------------------------------------------------------------
KEY POINT
---------------------------------------------------------------

• Search time → O(log n)
• Faster than linear search


## B-TREE TERMINOLOGY

1. Node
   → An element in the tree that stores information.

   Example:
   [30 | 50]
   ↑
   This whole box is a NODE.


2. Key
   → The actual value stored inside a node.

   Example:
   [30 | 50]
    ↑     ↑
   key   key


3. Root Node
   → The top/starting node of the tree.

             [30 | 50]
             ↑
          Root node


4. Child Node
   → A node directly below another node.

             [30 | 50]
            /    |    \
           ↓     ↓     ↓
        [10,20] [40]  [60,70]
          ↑
       Child node


5. Parent Node
   → A node that has child nodes.

             [30 | 50]
             ↑
          Parent node


6. Leaf Node
   → A node at the bottom that has no children.

             [30 | 50]
            /    |    \
       [10,20]  [40]  [60,70]
          ↑              ↑
       Leaf node       Leaf node


7. Pointer
   → A reference that tells the database where another
     node/data is located.

   Think:
   "Go to this location."


8. Balanced
   → The tree keeps its branches at roughly the same depth,
     so searching doesn't become unnecessarily long.


9. Sorted
   → Keys are maintained in an ordered manner.

   Example:
   [10 | 20 | 30 | 40 | 50]


10. Branch / Subtree
    → A section of the tree below a particular node.

---------------------------------------------------------------
## 2) B+ TREE INDEX (USED IN MYSQL) ⭐
---------------------------------------------------------------

Definition:
• Improved version of B-Tree
• Used in MySQL (InnoDB)

---------------------------------------------------------------
STRUCTURE
---------------------------------------------------------------

                [50]
              /      \
        [20,30]      [60,80]
        /    \        /    \
   [10,20] [25,30] [55,60] [80,90]

Leaf Nodes (Linked):
[10,20] ⇄ [25,30] ⇄ [55,60] ⇄ [80,90]

• Internal nodes → only keys
• Leaf nodes → actual data
• Leaf nodes connected sequentially

---------------------------------------------------------------
HOW IT WORKS
---------------------------------------------------------------

Search:
• Always traverse from root → leaf
• Data found ONLY at leaf level

Example:
Search 30
→ 30 < 50 → go left
→ reach [20,30]
→ go to leaf [25,30] → found

---------------------------------------------------------------
RANGE QUERY (ADVANTAGE)
---------------------------------------------------------------

Why is B+Tree better for databases?

The big advantage is searching ranges and sorted data.

Suppose:

SELECT *
FROM users
WHERE age BETWEEN 30 AND 60;

With B+Tree:

              [30 | 50]
             /    |    \
            ↓     ↓     ↓
       [10,20] [30,40] [50,60,70]
                    ↘
                     ↔

MySQL:

1. Find 30
      ↓
2. Reach the leaf node containing 30
      ↓
3. Follow the linked leaf nodes
      ↓
4. Get 40
5. Get 50
6. Get 60

It doesn't have to repeatedly travel from the root.

That's the big conceptual advantage.
---------------------------------------------------------------
WHY B+ TREE IS BETTER
---------------------------------------------------------------

• Faster range queries (linked leaves)
• More keys per node → smaller tree height
• Better disk I/O performance

---------------------------------------------------------------
DIFFERENCE
---------------------------------------------------------------

Feature        | B-TREE                  | B+ TREE
---------------|--------------------------|-------------------------
Data Storage   | In all nodes            | Only in leaf nodes
Search         | Can stop early          | Must reach leaf
Range Query    | Slower                  | Faster
Usage          | General                 | Databases (MySQL)

---------------------------------------------------------------
INTERVIEW LINE
---------------------------------------------------------------

"MySQL uses B+ Tree indexing because it provides faster search
and efficient range queries using linked leaf nodes."

==================== TIME COMPLEXITY (HIGH LEVEL) ====================

Definition:
• Time complexity measures how execution time grows with input size (n)
• Focus is on growth pattern, not exact time

---------------------------------------------------------------
COMMON TYPES
---------------------------------------------------------------

O(1)   → Constant time (no change with input size)  
O(log n) → Logarithmic (very fast growth, e.g., binary search)  
O(n)   → Linear (time increases with input size)  
O(n log n) → Efficient for sorting (merge sort, quicksort avg)  
O(n²)  → Quadratic (nested loops, slower for large data)

---------------------------------------------------------------
INTUITION
---------------------------------------------------------------

• Small n → difference not visible  
• Large n → huge impact on performance  

Example:
n = 1,000,000  
O(n)   → 1,000,000 steps  
O(log n) → ~20 steps  

---------------------------------------------------------------
WHY IMPORTANT
---------------------------------------------------------------

• Helps choose efficient algorithms  
• Predicts performance for large data  
• Critical for optimization (DB queries, indexing)

---------------------------------------------------------------
DB CONTEXT
---------------------------------------------------------------

• Index search (B+ Tree) → O(log n)  
• Full table scan → O(n)  

---------------------------------------------------------------
INTERVIEW LINE
---------------------------------------------------------------

"Time complexity shows how an algorithm scales with input size,
helping us choose efficient solutions."

==================== INDEX TYPES & CONCEPTS (MYSQL) ====================

---------------------------------------------------------------
DEFINITION
---------------------------------------------------------------

• Index = data structure that improves SELECT query performance
• Works like a book index → faster data lookup

---------------------------------------------------------------
TYPES OF INDEX
---------------------------------------------------------------

1) PRIMARY INDEX
• Created automatically on PRIMARY KEY
• Unique + NOT NULL
• Only one per table

---------------------------------------------------------------

2) UNIQUE INDEX
• Ensures all values are unique
• Allows NULL (once or multiple depending on DB)

CREATE UNIQUE INDEX idx_email
ON employees(email);

---------------------------------------------------------------

3) NORMAL INDEX
• Improves search performance
• Allows duplicate values

CREATE INDEX idx_salary
ON employees(salary);

---------------------------------------------------------------

4) COMPOSITE INDEX
• Index on multiple columns

CREATE INDEX idx_dept_salary
ON employees(department, age);

---------------------------------------------------------------
LEFTMOST PREFIX RULE ⭐
---------------------------------------------------------------

• Composite index works from LEFT to RIGHT

Index: (department, age)

Works:
✔ WHERE department = 'IT'
✔ WHERE department = 'IT' AND age > 25

Does NOT work efficiently:
❌ WHERE age > 25   (skips first column)

---------------------------------------------------------------

5) FULLTEXT INDEX
• Used for searching large text data
• Works with MATCH() AGAINST()

CREATE FULLTEXT INDEX idx_desc
ON table_name(description);

6) DROP INDEX 


Definition:
• Removes an existing index from a table
• Does NOT delete data, only removes index structure

DROP INDEX index_name
ON table_name;
---------------------------------------------------------------
EXAMPLE QUERIES (INDEX USAGE)
---------------------------------------------------------------

SELECT name, department 
FROM employees 
WHERE department = 'IT';

SELECT name, department, age 
FROM employees 
WHERE department = 'IT' AND age > 25;

---------------------------------------------------------------
DISADVANTAGES
---------------------------------------------------------------

• Slows down INSERT / UPDATE / DELETE  
  → because index also needs to be updated  

• Takes extra storage space  

• Too many indexes can degrade performance  

---------------------------------------------------------------
WHEN TO USE
---------------------------------------------------------------

• Frequent SELECT queries  
• WHERE, JOIN, ORDER BY columns  
• Large tables with filtering

---------------------------------------------------------------
KEY POINT
---------------------------------------------------------------

• Use indexes for READ-heavy systems  
• Avoid over-indexing  
==================== INDEX BEST PRACTICES & CASES ====================

---------------------------------------------------------------
IMPORTANT RULES
---------------------------------------------------------------

1) Avoid Functions on Indexed Columns ❌
• Index is NOT used if column is wrapped in function

❌ SELECT * FROM users WHERE UPPER(name) = 'AJAY';
✔ SELECT * FROM users WHERE name = 'Ajay';

---------------------------------------------------------------

2) Avoid Calculations on Indexed Columns ❌
❌ WHERE salary + 1000 > 5000
✔ WHERE salary > 4000

---------------------------------------------------------------

3) Use Index on JOIN Columns ✔
• Speeds up joins significantly

SELECT * 
FROM orders o
JOIN users u ON o.user_id = u.id;

→ Index on user_id and id helps

---------------------------------------------------------------

4) Use Index on WHERE / FILTER Columns ✔
• Most benefit when filtering large data

WHERE department = 'IT'

---------------------------------------------------------------

5) Use Index on ORDER BY / GROUP BY ✔
• Helps sorting and grouping

ORDER BY salary DESC

---------------------------------------------------------------

6) Composite Index Efficiency ⚠
• Benefit depends on usage

Example:
Index (A, B, C)

✔ WHERE A = ?
✔ WHERE A = ? AND B = ?
✔ WHERE A = ? AND B = ? AND C = ?

❌ WHERE B = ?  (skips A → no use)

---------------------------------------------------------------

7) Selectivity Matters ⭐
• High uniqueness → better index

✔ email (unique)
❌ gender (few values → low benefit)

---------------------------------------------------------------

8) Too Many Indexes ❌
• Slows down INSERT / UPDATE / DELETE
• Uses more storage

---------------------------------------------------------------

9) Small Tables ❌
• Index often not useful (full scan is faster)

---------------------------------------------------------------

10) Range Queries ⚠
• Index works, but stops further columns

WHERE department = 'IT' AND age > 25
→ age is range → next columns ignored

---------------------------------------------------------------
REALITY CHECK (COMMON MISCONCEPTION)
---------------------------------------------------------------

• “2 columns = 50%, 3 columns = 33% faster” ❌ WRONG

✔ Performance depends on:
  - Data size
  - Selectivity
  - Query pattern
  - Index usage

---------------------------------------------------------------
KEY POINT
---------------------------------------------------------------

• Index helps only when used correctly in query
• Wrong usage → index ignored

---------------------------------------------------------------
INTERVIEW LINE
---------------------------------------------------------------

"Indexes improve performance only when used on proper columns
without functions, with good selectivity, and aligned with query patterns."
---------------------------------------------------------------


---------------------------------------------------------------
INTERVIEW LINE
---------------------------------------------------------------

"Indexes improve read performance but add overhead to write
operations, so they should be used wisely."

CAP THEOREM — DISTRIBUTED SYSTEM TRADE-OFFS
=====================================================================

DEFINITION
---------------------------------------------------------------------
CAP theorem states that a distributed system cannot guarantee all
THREE CAP properties simultaneously during a network partition:

→ Consistency (C)
→ Availability (A)
→ Partition Tolerance (P)

Distributed system simply means:

A system where multiple computers/servers work together as one system.
                    EventHub
                       ↓
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       Server 1     Server 2     Server 3
          ↓            ↓            ↓
       Database     Database     Database
       This can help with scaling, availability, and handling large traffic.

IMPORTANT ⭐
---------------------------------------------------------------------
In a real distributed system → Partition Tolerance (P) is mandatory.

Therefore, the practical choice is:

→ CP = Consistency + Partition Tolerance
→ AP = Availability + Partition Tolerance

CA is generally NOT considered a practical choice for a distributed
system because it gives up Partition Tolerance.


=====================================================================
1) CONSISTENCY (C)
=====================================================================

All users/nodes see the same latest data after a successful write.
→ Every node gives the same/latest data.

In CAP terminology, Consistency means that after a successful write, a read gets the most recent committed value, rather than an older value from another node.
Example:

User 1 updates balance → ₹100
             ↓
User 2 reads balance → ₹100 ✔

→ No user should see an older value after the update is committed.



Bank balance
→ Correct/latest data is critical
→ Prefer Consistency

Social media feed
→ Slightly old data is usually acceptable
→ Availability can be prioritized

## how to achieve consistecy in brief

1. TRANSACTIONS
   → Group related operations together.
   → COMMIT if all succeed, ROLLBACK if something fails.

2. CONSTRAINTS
   → PRIMARY KEY
   → FOREIGN KEY
   → UNIQUE
   → NOT NULL
   → CHECK

3. CORRECT UPDATE LOGIC
   → Validate data before changing it.
   → Prevent invalid states.

4. LOCKING / ISOLATION
   → Prevent concurrent transactions from incorrectly
     modifying the same data.



     ## eventhub example:
     START TRANSACTION
       ↓
Create booking

       ↓
   Both succeed?

  YES       NO
   ↓         ↓
COMMIT    ROLLBACK

“We maintain database consistency using transactions, constraints, validation, and proper concurrency control such as locking and transaction isolation.”
=====================================================================
2) AVAILABILITY (A)
=====================================================================

→ Every request gets a response back, even if the response may not
contain the latest data.

Example:

Server receives request
        ↓
Server responds ✔
        ↓
Data may temporarily be outdated

## In real projects, we maintain it mainly through:
1. REPLICATION
   → Keep multiple servers/DB replicas.
   → If one fails, another can serve requests.

2. LOAD BALANCING
   → Distribute requests across multiple servers.
   → If one server fails, traffic can go to others.

3. FAILOVER
   → Automatically switch to a backup server
     when the primary fails.

4. REDUNDANCY
   → Avoid having one single point of failure.

5. HEALTH CHECKS + MONITORING
   → Detect failed/unhealthy servers and remove them
     from serving traffic.

Good example for Availability → Social Media

Suppose you post:
"Had an amazing day!"
Your followers' servers haven't received the latest post yet.
One follower opens your profile and sees:
Yesterday's posts
instead of your new post.

That's stale data, but the application still responds and works.

Availability
→ User gets a response ✅
→ Data might temporarily be stale ⚠️

3) PARTITION TOLERANCE (P)
=====================================================================

System continues operating despite a network failure between nodes.

Example:

Node A  ✕ network ✕  Node B

→ Nodes cannot communicate with each other.
→ The distributed system is designed to tolerate this failure.


In short, in a typical MySQL/EventHub project, we maintain consistency using:

1. TRANSACTIONS
   → Group related operations together.
   → COMMIT if all succeed, ROLLBACK if something fails.

2. CONSTRAINTS
   → PRIMARY KEY
   → FOREIGN KEY
   → UNIQUE
   → NOT NULL
   → CHECK

3. CORRECT UPDATE LOGIC
   → Validate data before changing it.
   → Prevent invalid states.

4. LOCKING / ISOLATION
   → Prevent concurrent transactions from incorrectly
     modifying the same data.

Partition Tolerance → System continues operating despite network   communication failure between nodes.   what this means

It means the servers can no longer communicate with each other, but the system is designed to keep running instead of completely stopping.

Simple example

## Suppose your system has 3 servers:

Server 1  ←──── network ────→  Server 2
                                  ↕
                              Server 3

Now the network connection between Server 1 and Server 2 breaks:

Server 1   ❌❌❌   Server 2
                       ↕
                   Server 3

This is a network partition.

The servers are still running, but they can't communicate with each other.


Very important

Partition Tolerance does NOT mean the network never fails.

It means:

The system can tolerate the network failure when it happens.

=====================================================================
CP SYSTEM
=====================================================================

CP = Consistency + Partition Tolerance

→ Prioritizes correct/latest data.
→ During a partition, the system may delay or reject some requests
  rather than return potentially inconsistent data.

Example:
→ Banking / financial systems

Reason:
Better to reject/delay a transaction than show incorrect balance
or process conflicting data.


=====================================================================
AP SYSTEM
=====================================================================

AP = Availability + Partition Tolerance

→ Prioritizes availability.
→ System continues responding during a partition.
→ Some users may temporarily receive stale/outdated data.
→ Data can become consistent after the partition is resolved.

Example:
→ Social media feeds

Reason:
It may be preferable for a feed to load with slightly old data
rather than fail completely.


=====================================================================
CA SYSTEM
=====================================================================

CA = Consistency + Availability

→ Gives up Partition Tolerance.
→ Can exist when network partitions are not part of the system model,
  such as a single-server/local setup.

Example:
→ Traditional RDBMS running on a single server.

IMPORTANT ⭐
---------------------------------------------------------------------
CA is NOT a practical choice for a distributed system where
network partitions can occur.

Therefore:

Distributed system → P is required
                     ↓
                  CP or AP


=====================================================================
WHY CP OVER CA?
=====================================================================

In a distributed system:

Network failure
      ↓
Nodes may stop communicating
      ↓
Partition (P)

If the system cannot tolerate this → it is not partition tolerant.

Therefore, in a distributed environment, the meaningful choice is
generally:

→ CP
OR
→ AP

NOT CA.


=====================================================================
SYNCHRONOUS vs ASYNCHRONOUS REPLICATION
=====================================================================

SYNCHRONOUS
---------------------------------------------------------------------
Write data
    ↓
Replicate/confirm with required replicas
    ↓
Response

→ System waits for replication/confirmation before completing
  the operation.

✔ Helps maintain strong consistency
❌ Can increase latency


ASYNCHRONOUS
---------------------------------------------------------------------
Write data
    ↓
Respond
    ↓
Replicate to other nodes later

✔ Lower latency / faster response
❌ Replicas may temporarily contain old data

IMPORTANT:
---------------------------------------------------------------------
Synchronous/asynchronous replication is related to how replicas
receive updates. Do NOT treat it as exactly the same thing as
CAP's Consistency vs Availability.

They can influence the trade-off, but they are separate concepts.


=====================================================================
REAL-WORLD ANALOGY
=====================================================================

BANKING:
→ Consistency is highly important.
→ During certain failures, the system may reject/delay operations
  rather than risk inconsistent balances.

SOCIAL MEDIA:
→ Availability is highly important.
→ A feed may temporarily show older data rather than fail completely.


=====================================================================
KEY TRADE-OFF
=====================================================================

CP → Consistency + Partition Tolerance
     Prefer correct/consistent data during partition

AP → Availability + Partition Tolerance
     Prefer continued responses during partition,
     even if data may temporarily be stale


=====================================================================
IMPORTANT CAP INTERVIEW POINT
=====================================================================

"CAP theorem states that in a distributed system, when a network
partition occurs, the system must choose between Consistency and
Availability, while Partition Tolerance is maintained."

Do NOT simply say:
"CAP means you can always choose any 2 of the 3."

More accurate:
→ The trade-off becomes important when a partition occurs.
→ In distributed systems, P is generally unavoidable.


=====================================================================
OLTP vs OLAP
=====================================================================

DEFINITION
---------------------------------------------------------------------

OLTP = Online Transaction Processing
→ Handles day-to-day business transactions.
→ Focuses on fast, frequent transactions.

OLAP = Online Analytical Processing
→ Used for analysis, reporting and decision-making.
→ Focuses on complex queries over large amounts of data.


=====================================================================
OLTP — UNDERSTANDING
=====================================================================

System designed for:

→ Real-time transactions
→ Frequent INSERT / UPDATE / DELETE
→ Short, simple queries
→ Fast response
→ Maintaining current operational data

Example:

INSERT INTO orders VALUES (...);

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;


=====================================================================
OLAP — UNDERSTANDING
=====================================================================

System designed for:

→ Data analysis
→ Reporting
→ Aggregations
→ Complex SELECT queries
→ Large volumes of historical data

Example:

SELECT department, AVG(salary)
FROM employees
GROUP BY department;


=====================================================================
OLTP vs OLAP — COMPARISON
=====================================================================

Feature          | OLTP                         | OLAP
-----------------|------------------------------|----------------------------
Purpose          | Transactions                 | Analysis / reporting
Users            | End users / applications     | Analysts / managers
Queries          | Simple, frequent             | Complex, fewer
Operations       | INSERT, UPDATE, DELETE       | Mainly SELECT
Data             | Current operational data     | Large historical data
Transaction size | Small                         | Large analytical queries
Response time    | Very fast, usually ms        | Usually slower
Schema           | Usually normalized            | Often denormalized
Workload         | Write-heavy / mixed          | Read-heavy
Examples         | Banking, orders, bookings    | Data warehouse, BI


=====================================================================
WHY SEPARATE OLTP AND OLAP?
=====================================================================

Suppose an EventHub application has millions of bookings.

OLTP database:

→ User books ticket
→ INSERT booking
→ UPDATE available tickets
→ Payment/transaction processing

At the same time, an analyst runs:

→ GROUP BY event
→ JOIN multiple large tables
→ SUM revenue
→ AVG ticket price
→ Analyze years of booking history

A huge analytical query can consume significant database resources
and affect real-time transactions.

Therefore:

OLTP → optimized for operational/real-time transactions
OLAP → optimized for large-scale analysis


=====================================================================
KEY DIFFERENCE
=====================================================================

OLTP
→ "Process the transaction."

Example:
User buys 2 tickets.


OLAP
→ "Analyze the transactions."

Example:
Which events generated the most revenue this year?


=====================================================================
IMPORTANT NOTE ⭐
=====================================================================

Do NOT think:

OLTP = only INSERT/UPDATE/DELETE
OLAP = only SELECT

The distinction is about the SYSTEM/WORKLOAD and its purpose.

OLTP:
→ real-time operational processing
→ short, frequent transactions

OLAP:
→ analytical processing
→ complex queries over large datasets

# ======================================================================
TRANSACTIONS — MySQL
======================================================================

DEFINITION
----------------------------------------------------------------------

A transaction is a group of SQL statements treated as ONE unit of work.

→ Either ALL operations succeed → COMMIT
→ Or something goes wrong → ROLLBACK

Example:
Bank transfer ₹1000 from A → B

1. Deduct ₹1000 from A
2. Add ₹1000 to B

Both must happen.

We don't want:
A loses ₹1000 but B doesn't receive it.


======================================================================
BASIC SYNTAX
======================================================================

START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

COMMIT;


If something goes wrong:

START TRANSACTION;

UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

-- Something went wrong...

ROLLBACK;

→ Changes made since START TRANSACTION are undone.


======================================================================
COMMIT vs ROLLBACK
======================================================================

COMMIT
→ Permanently save the transaction's changes.

ROLLBACK
→ Undo the transaction's changes.

Easy rule:

COMMIT   = SAVE
ROLLBACK = UNDO


======================================================================
REAL EVENTHUB EXAMPLE
======================================================================

Suppose user books 2 tickets.

Two things need to happen:

1. Create booking
2. Reduce available tickets

START TRANSACTION;

INSERT INTO bookings (user_id, event_id, quantity)
VALUES (10, 5, 2);

UPDATE ticket_tiers
SET available_quantity = available_quantity - 2
WHERE event_id = 5;

COMMIT;


If the second operation fails:

ROLLBACK;

→ Booking INSERT is also undone.

Without transaction:

Booking created              ✅
Ticket quantity update       ❌

→ Database becomes inconsistent.


======================================================================
ACID PROPERTIES
======================================================================

Transactions follow ACID:

A → Atomicity
C → Consistency
I → Isolation
D → Durability


1. ATOMICITY
----------------------------------------------------------------------

"All or nothing."

Either all statements in the transaction happen,
or none of them happen.

Example:
Transfer ₹1000:

Deduct + Add → both happen
Deduct only  → ROLLBACK


2. CONSISTENCY
----------------------------------------------------------------------

Transaction must leave the database in a valid state.

Example:
If account balance cannot be negative,
a transaction should not leave it violating that rule.


3. ISOLATION
----------------------------------------------------------------------

Multiple transactions can run at the same time,
but they should not improperly interfere with each other.

Example:
Two users trying to book the last ticket simultaneously
should not both successfully take that same ticket.


4. DURABILITY
----------------------------------------------------------------------

After COMMIT, the changes are permanently saved
and should survive a database/server restart.


======================================================================
IMPORTANT COMMANDS
======================================================================

START TRANSACTION;
→ Begin a transaction.

COMMIT;
→ Save changes permanently.

ROLLBACK;
→ Undo changes in the current transaction.


Example:

START TRANSACTION;

UPDATE users
SET name = 'Ajay'
WHERE id = 1;

ROLLBACK;

→ Name change is undone.


START TRANSACTION;

UPDATE users
SET name = 'Ajay'
WHERE id = 1;

COMMIT;

→ Name change is saved.


======================================================================
IMPORTANT: INNODB
======================================================================

Transactions require a transaction-supporting storage engine.

MySQL's default InnoDB engine supports transactions.

CREATE TABLE accounts (
    id INT PRIMARY KEY,
    balance DECIMAL(10,2)
) ENGINE=InnoDB;


======================================================================
AUTOCOMMIT
======================================================================

MySQL normally has AUTOCOMMIT enabled.

That means individual statements are automatically committed.

Example:

UPDATE users
SET name = 'Ajay'
WHERE id = 1;

→ Normally this is automatically committed.

When you explicitly use:

START TRANSACTION;

→ You control when changes are saved using COMMIT
   or undone using ROLLBACK.

async function bookTickets() {

    const connection = await pool.getConnection();

    try {
        await connection.beginTransaction();

        // 1. Create booking
        await connection.query(`
            INSERT INTO bookings (user_id, event_id, quantity)
            VALUES (10, 5, 2)
        `);

        // 2. Reduce available tickets
        await connection.query(`
            UPDATE ticket_tiers
            SET available_quantity = available_quantity - 2
            WHERE event_id = 5
        `);

        // Everything succeeded
        await connection.commit();

    } catch (error) {

        // Something failed → undo everything
        await connection.rollback();

        throw error;

    } finally {

        // Return connection to the pool
        connection.release();
    }
}
======================================================================
FULL TRANSACTION EXAMPLE — BANK TRANSFER
======================================================================

Suppose:
Account A (id = 1) → ₹5000
Account B (id = 2) → ₹3000

We want to transfer ₹1000 from A → B.

Goal:
A → ₹4000
B → ₹4000


----------------------------------------------------------------------
SUCCESS FLOW — COMMIT
----------------------------------------------------------------------

START TRANSACTION;

-- Step 1: Deduct ₹1000 from A
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

-- Step 2: Add ₹1000 to B
UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

-- Both operations succeeded
COMMIT;


Result:

A → ₹4000
B → ₹4000

COMMIT
→ Permanently saves BOTH changes.


----------------------------------------------------------------------
FAILURE FLOW — ROLLBACK
----------------------------------------------------------------------

Suppose Step 1 succeeds but Step 2 fails.

START TRANSACTION;

-- Step 1 succeeds
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

-- Step 2 fails / something goes wrong
UPDATE accounts
SET balance = balance + 1000
WHERE id = 999;

-- Undo everything done in this transaction
ROLLBACK;


Result:

A → ₹5000
B → ₹3000

The ₹1000 deduction from A is also undone.

ROLLBACK
→ Restores the database to the state before
  START TRANSACTION.


----------------------------------------------------------------------
COMPLETE FLOW
----------------------------------------------------------------------

              START TRANSACTION
                     ↓
             Deduct ₹1000 from A
                     ↓
             Add ₹1000 to B
                     ↓
                Everything OK?
                  /        \
                YES         NO
                 ↓           ↓
              COMMIT      ROLLBACK
                 ↓           ↓
              SAVE ALL    UNDO ALL


======================================================================
WHY TRANSACTION IS NEEDED
======================================================================

WITHOUT TRANSACTION:

Deduct from A       ✅
Add to B            ❌

→ A loses money
→ B doesn't receive money
→ Database becomes inconsistent


WITH TRANSACTION:

All succeed         → COMMIT   → Save all changes
Any failure         → ROLLBACK → Undo all changes

Easy rule:

START TRANSACTION = START
COMMIT             = SAVE
ROLLBACK           = UNDO
