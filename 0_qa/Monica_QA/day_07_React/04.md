The important thing to understand is that JWT authentication is mainly a frontend + backend flow. React doesn't generate the JWT in a typical application; the backend generates it after successful login.

# JWT

JWT (JSON Web Token) is a compact, self-contained token used to securely transmit information between a client and server. It is commonly used for authentication, where the server issues a token after successful login and the client sends it with the following requests.

In simple words:

JWT is a token that the backend gives to the client after successful login, and the client uses that token to prove its identity when accessing protected APIs.

1. Why do we need JWT?

Suppose you log in:

Email: ajay@gmail.com    Password: 123456

Backend verifies the credentials.

Now, for the next request:

GET /profile

How does the backend know:

"This request is from Ajay, who already logged in"?

JWT solves this.

Backend gives you a token:

Backend → JWT → Client

Then the client sends that token with protected requests:

Client → JWT → Backend

Backend verifies the JWT and knows who the user is.


2. JWT structure
This is very important for interviews.

A JWT has 3 parts:

HEADER.PAYLOAD.SIGNATURE

For example:

eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMiLCJyb2xlIjoiVVNFUiJ9.abc123xyz...

The three parts are:

Header + Payload + Signature

They are separated by a .


3. Header

The header contains information about the token itself.

Example:

{
  "alg": "HS256", //So the algorithm is basically the method used to create and verify the signature.
  "typ": "JWT"
}

alg → Algorithm used for signing.

Example:

HS256

Other algorithms exist, such as:

RS256

typ → Token type:

JWT

So:

Header tells us how the JWT is signed and what type of token it is.


4. Payload

The payload contains claims.

Example:

{
  "sub": "123",
  "email": "ajay@gmail.com",
  "role": "USER",
  "iat": 1720000000,
  "exp": 1720000900
}

These are pieces of information about the token/user.

Common claims:

Claim    Meaning
sub      Subject, usually user ID
iat      Issued At
exp      Expiration time
iss      Issuer
aud      Audience

You can also have custom claims:

{
  "userId": 123,
  "role": "ADMIN"
}

Important!

JWT payload is NOT encrypted by default.

It is normally Base64URL encoded, not encrypted.

Therefore:

❌ Don't put:

password
credit card number
OTP

inside the JWT payload.

Anyone who gets the token can decode the payload.


5. Signature

This is the most important security part.

The signature is used to verify that:

The JWT was created by a trusted party and has not been modified.

Conceptually, with HMAC:

Signature = HMAC(base64Url(header) + "." + base64Url(payload), secretKey)

So:

Header + Payload + Secret key → Signature

The backend has the secret key.

The client does not know the secret key.


6. Why is the signature needed?

Suppose the JWT says:

{
  "userId": 123,
  "role": "USER"
}

A malicious user could decode the payload and change it to:

{
  "userId": 123,
  "role": "ADMIN"
}

But they cannot create a valid signature without the signing key.

So when the modified token reaches the backend:

Backend → Verify signature → ❌ Invalid

Request is rejected.


Note:JWT consists of Header, Payload, and Signature. Header contains signing information, Payload contains claims, and Signature verifies the token's authenticity and integrity.

7. JWT is signed, not necessarily encrypted

This distinction is very important.

Signed JWT → Protects against: Modification

It allows the server to detect:

"Has someone changed this token?"

Encrypted token → Protects the contents from being read.

JWT by itself normally does not provide this confidentiality.

So remember:

JWT is usually encoded + signed, not encrypted.


8. How JWT authentication works

Now the complete flow becomes easy.

Step 1 — Login

React → email + password → POST /login → Backend

Backend verifies:

email/password

If correct:

Generate JWT

Step 2 — Backend sends JWT

Backend → JWT → Browser

Depending on the architecture, it may be stored in an HttpOnly cookie or otherwise handled by the application.

Step 3 — Client requests protected API

For example:

GET /profile

The authentication credential is sent with the request.

Conceptually:

React → JWT → GET /profile → Backend

Step 4 — Backend verifies JWT

Backend checks:

Is signature valid? → Is token expired? → Are required claims valid? → Who is the user?

If valid:

Allow request

If invalid:

401 Unauthorized


9. Authentication vs Authorization with JWT

This is another important interview connection.

Authentication → Who are you?

JWT can identify the user.

For example:

{
  "sub": "123"
}

means:

User ID = 123

Authorization → What are you allowed to do?

For example:

{
  "sub": "123",
  "role": "ADMIN"
}

Backend can use the role:

ADMIN → can delete users
USER  → cannot delete users

So JWT can carry information used for authorization, but the backend must still enforce the permissions.


10. JWT expiration

JWTs commonly have an expiration time:

{
  "sub": "123",
  "exp": 1720000900
}

Once expired:

JWT → Expired → Backend rejects it → 401 Unauthorized

That's why access tokens are commonly made short-lived.

For example:

Access Token → 15 minutes

And a refresh mechanism can be used to obtain a new access token.


11. Access token vs Refresh token

You will need this for question 48.

Access token → Used for accessing APIs → Short-lived → Example: 15 minutes

Refresh token → Used to obtain a new access token → Longer-lived → Example: Days/weeks

Flow:

Login → Access Token + Refresh Token → Access token used for APIs → Access token expires → Refresh token used → New access token


12. Is JWT stateful or stateless?

JWT authentication is commonly described as stateless authentication.

Traditional session authentication:

Login → Server creates session → Server stores session → Client sends session ID → Server looks up session

JWT:

Login → Server creates signed JWT → Client sends JWT → Server verifies JWT

The server can validate the token without needing to look up a server-side session for every request.

But don't say JWT can never involve server-side state. Real systems may maintain things such as refresh-token records, revocation lists, or other session/security state.


13. Important JWT rules to remember

For interviews, remember these:

Rule 1 → JWT has: Header.Payload.Signature

Rule 2 → They are separated by: .

Rule 3 → Payload contains claims.

Rule 4 → Payload is not encrypted by default.

Rule 5 → Signature helps detect modification.

Rule 6 → The signing secret/private key must never be exposed to the frontend.

Rule 7 → JWTs can have an expiration: exp

Rule 8 → Don't put sensitive information such as passwords in the payload.

Rule 9 → HTTPS should be used so tokens/credentials aren't exposed in transit.

Rule 10 → For browser applications, HttpOnly + Secure cookies are generally preferred for sensitive long-lived authentication credentials, especially refresh tokens.


14. JWT vs Cookie

One important clarification:

JWT and cookie are not alternatives.

They are different things.

JWT is: TOKEN FORMAT

Cookie is: STORAGE / TRANSPORT MECHANISM

You can have:

JWT → HttpOnly Cookie

That's exactly what the earlier React example was doing.


15. JWT vs Session

Session authentication:

Client → Session ID → Server → Session stored on server

JWT authentication:

Client → JWT → Server → Verify JWT

Very simplified interview difference:

Session authentication stores session state on the server, whereas JWT authentication can allow the server to verify authentication information directly from the signed token.


16. The one mental picture to remember

LOGIN → Email + Password → Backend → Verify credentials → Generate JWT

                         ↓

          ┌─────────────────────────────┐
          ↓                             ↓
     Access Token                Refresh Token
     short-lived                  long-lived
          ↓                             ↓
   Protected APIs              Refresh access


And the JWT itself:

┌──────────┬───────────┬─────────────┐
│  HEADER  │  PAYLOAD  │  SIGNATURE  │
└──────────┴───────────┴─────────────┘
      ↓          ↓             ↓
 algorithm    claims       verification


If the interviewer asks "What is JWT?"

A strong short answer is:

"JWT stands for JSON Web Token. It is a compact, signed token commonly used for authentication and authorization. It consists of a header, payload, and signature. The payload contains claims such as user ID or role, while the signature allows the backend to verify that the token hasn't been tampered with. JWT payloads are Base64URL encoded, not encrypted by default, and tokens commonly have an expiration time."

Because JavaScript cannot directly read an HttpOnly cookie.

# 47. Where should you store an authentication token?

There are several possibilities:

Storage	Main issue
localStorage	JavaScript can access it → vulnerable to token theft through XSS
sessionStorage	Same XSS concern

HttpOnly cookie	JavaScript cannot directly access it
Memory	Safer from persistent theft, but disappears on refresh

For browser authentication, HttpOnly, Secure cookies are generally preferred for refresh/session credentials.

A typical setup is:

Access token(jwt here)
     ↓
HttpOnly Secure cookie


Refresh token
     ↓
HttpOnly Secure cookie

The exact architecture depends on the application.

Why not simply use localStorage?

You might see:

localStorage.setItem("token", token);

This is easy, but JavaScript can read it:

localStorage.getItem("token");

So if malicious JavaScript executes in the application, the token can potentially be stolen.

Therefore, for a security-sensitive browser application, I would generally prefer HttpOnly cookies rather than putting long-lived authentication tokens in localStorage.

# 48. How do you refresh an expired JWT token?


JWTs are commonly short-lived.

For example:

Access token
expires in → 15 minutes


Refresh token
expires in → several days/weeks

Why?

If an access token gets stolen, its useful lifetime is limited.

Without refresh token

Imagine:

10:00 → login
10:15 → access token expires
10:16 → API request
          ↓
        401
          ↓
       logout

That would be annoying for the user.

With refresh token

Instead:

API request
    ↓
Access token expired
    ↓
Backend returns 401
    ↓
React calls /auth/refresh
    ↓
Backend verifies refresh token
    ↓
New access token generated
    ↓
Retry original request
    ↓
Success

The refresh token should generally be kept in a secure HttpOnly cookie rather than exposed to JavaScript.

Refresh implementation

Let's add this to our API service.

src/services/api.js
async function refreshToken() {
  const response = await fetch(
    "http://localhost:8080/api/auth/refresh",
    {
      method: "POST",
      credentials: "include",
    }
  );


  if (!response.ok) {
    throw new Error("Session expired");
  }


  return response.json();
}

Now create a function that automatically handles an expired access token:

export async function apiRequest(url, options = {}) {
  let response = await fetch(url, {
    ...options,
    credentials: "include",
  });


  if (response.status !== 401) {
    return response;
  }


  // Access token expired
  await refreshToken();


  // Retry original request
  response = await fetch(url, {
    ...options,
    credentials: "include",
  });


  return response;
}

Then instead of:

fetch("http://localhost:8080/api/profile")

we can use:

apiRequest("http://localhost:8080/api/profile")
Backend flow

The backend has two important endpoints:

POST /auth/login
POST /auth/refresh
Login
email + password
       ↓
verify credentials
       ↓
generate access token
       ↓
generate refresh token
       ↓
set secure HttpOnly cookies
Refresh
refresh request
       ↓
read refresh-token cookie
       ↓
verify refresh token
       ↓
generate new access token
       ↓
set new access-token cookie

If the refresh token itself is expired or invalid:

refresh fails
    ↓
401 Unauthorized
    ↓
user must login again

Remember JWT authentication as three stages:

"I handle JWT authentication by sending the user's credentials to the backend. After successful login, the backend issues the authentication tokens, typically through secure HttpOnly cookies. # 49. What are Error Boundaries in React?
First understand the problem

Imagine your application has:

App
 ├── Navbar
 ├── ProductList
 └── PaymentComponent

Suppose PaymentComponent has a JavaScript error while rendering.

Without an Error Boundary, that error can cause part of the React UI to disappear.

An Error Boundary is a React component that catches certain errors in its child component tree 
and displays a fallback UI instead of letting the entire UI break.

Simple idea:

Parent
  │
  ├── Navbar
  │
  └── Error Boundary
         │
         └── Payment
               ↓
             ERROR
               ↓
        Show fallback UI

For example:

Something went wrong.
Please try again.
Important limitation

Error Boundaries catch errors during things like:

Rendering
Lifecycle methods
Constructors of child components

They do not automatically catch:

Event handler errors
Errors inside setTimeout
Errors in arbitrary async code
Server-side errors

Those need to be handled separately.

Implementation

Traditionally, Error Boundaries are implemented using a class component.

ErrorBoundary.jsx
import React from "react";


class ErrorBoundary extends React.Component {
  constructor(props) {
    super(props);


    this.state = {
      hasError: false,
    };
  }


  static getDerivedStateFromError(error) {
    return {
      hasError: true,
    };
  }


  componentDidCatch(error, errorInfo) {
    console.error("Error caught:", error);
    console.error("Error information:", errorInfo);
  }


  render() {
    if (this.state.hasError) {
      return <h2>Something went wrong.</h2>;
    }


    return this.props.children;
  }
}


export default ErrorBoundary;
Use it in App.jsx
import ErrorBoundary from "./ErrorBoundary";
import ProductList from "./ProductList";


function App() {
  return (
    <div>
      <h1>My Store</h1>


      <ErrorBoundary>
        <ProductList />
      </ErrorBoundary>
    </div>
  );
}


export default App;

The important concept is:

<ErrorBoundary>
  <ProductList />
</ErrorBoundary>

ProductList is now inside the boundary.

If an appropriate rendering error occurs inside it, the boundary can show its fallback UI.

Cross-question: Why use Error Boundaries?

To prevent a rendering error in one part of the application from breaking the entire user interface and to provide a fallback UI.

Interview answer

"Error Boundaries are used to catch rendering-related errors in a React component tree and show a fallback UI instead of allowing the broken component tree to crash the application. Traditionally they're implemented using class components with getDerivedStateFromError and componentDidCatch. For API errors or event-handler errors, I handle those separately."

# 52. What are Higher-Order Components?

A Higher-Order Component, or HOC, is a function that takes a component as an argument and returns a new enhanced component.

Think:

Component
    ↓
HOC function
    ↓
Enhanced Component

The basic pattern is:

function withSomething(Component) {
  return function EnhancedComponent(props) {
    // additional logic


    return <Component {...props} />;
  };
}

Notice:

<Component {...props} />

We pass the original component's props to the new component.

Simple example

Suppose we want to add authentication checking to multiple components.

function withAuth(Component) {
  return function ProtectedComponent(props) {
    const isLoggedIn = true;


    if (!isLoggedIn) {
      return <h2>Please login</h2>;
    }


    return <Component {...props} />;
  };
}

Now:

function Dashboard() {
  return <h1>Dashboard</h1>;
}

We enhance it:

const ProtectedDashboard = withAuth(Dashboard);

Then:

function App() {
  return <ProtectedDashboard />;
}

The flow is:

Dashboard
    ↓
withAuth()
    ↓
ProtectedDashboard
    ↓
Check authentication
    ↓
Render Dashboard
Are HOCs still commonly used?

They are still an important React concept, especially when discussing older/legacy React code.

But with modern React, Hooks and component composition are generally preferred for sharing logic.

For example, instead of:

withAuth(Dashboard)

you might use a custom Hook:

const isLoggedIn = useAuth();
Interview answer

"A Higher-Order Component is a function that takes a component and returns an enhanced component with additional behavior. HOCs were commonly used to reuse logic across components. In modern React, Hooks and component composition are usually preferred, but HOCs are still important when working with existing or legacy code."

# 54. What are Synthetic Events in React?
in React, the event object you receive in event handlers is a SyntheticEvent.
First understand it

When you write:

<button onClick={handleClick}>
  Click Me
</button>

React gives your handler an event object:

const handleClick = (event) => {
  console.log(event);
};

This event object is a React Synthetic Event.

It provides a consistent event interface across browsers.

For example:

function App() {
  const handleClick = (event) => {
    console.log(event.type);
    console.log(event.target);
  };


  return <button onClick={handleClick}>Click</button>;
}

You can use familiar properties/methods:

event.target           → The element that actually triggered the event.
event.currentTarget    → The element on which the event handler is attached.
event.preventDefault() → Prevents the browser's default action.
event.stopPropagation()→ Stops the event from propagating to parent elements.

Why does React use Synthetic Events?

The event object provides information about the event and methods to control its behavior, such as accessing target and currentTarget, preventing the default action, and stopping propagation.

Native Event
      ↓

event.nativeEvent

# 55. What is Event Bubbling?

This is a JavaScript DOM concept, not something unique to React.

Suppose we have:

<div onClick={() => console.log("Parent")}>
  <button onClick={() => console.log("Button")}>
    Click
  </button>
</div>

When we click the button:

Button clicked
      ↓
Button handler
      ↓
Parent handler

The event travels from the target element up toward its ancestors.

That's called event bubbling.

So the output is:

Button
Parent
Why does this happen?

DOM events have propagation phases.

Simplified:

        Document
           ↑
         Parent
           ↑
         Button
           ↑
        Target

During bubbling, the event moves:

Target → Parent → Document
stopPropagation()

If we don't want the event to reach the parent:

function App() {
  const handleParent = () => {
    console.log("Parent");
  };


  const handleButton = (event) => {
    event.stopPropagation();


    console.log("Button");
  };


  return (
    <div onClick={handleParent}>
      <button onClick={handleButton}>
        Click
      </button>
    </div>
  );
}

Now clicking the button produces:

Button

The event doesn't continue bubbling to the parent.

Why is bubbling useful?

One important use is event delegation.

For example, instead of adding a click handler to every list item:

Item 1 → handler
Item 2 → handler
Item 3 → handler
...

we can put one handler on the parent and determine which item was clicked.

function List() {
  const handleClick = (event) => {
    console.log(event.target);
  };


  return (
    <div onClick={handleClick}>
      <button>Item 1</button>
      <button>Item 2</button>
      <button>Item 3</button>
    </div>
  );
}

The click bubbles from the button to the parent.

Inside handleClick:

event.target

means:

The element that actually triggered the event.

So:

While:

means:

Easy memory trick

target = where the event started

currentTarget = where the handler is attached

"Event bubbling means an event starts at the target element and then propagates upward through its parent elements. # 56. What is Event Capturing?

Event capturing is essentially the opposite direction of bubbling.

Instead of:

Target → Parent → Document

capturing travels:

Document → Parent → Target

So the overall event propagation looks like:

CAPTURING:

Document
   ↓
Parent
   ↓
Button
   ↓
TARGET
   ↓
BUBBLING

Button
   ↑
Parent
   ↑
Document

How do we use capturing in React?
React provides the Capture version of event handlers.

For example:

<div
  onClickCapture={() => console.log("Parent capture")}
  onClick={() => console.log("Parent bubble")}
>
  <button
    onClickCapture={() => console.log("Button capture")}
    onClick={() => console.log("Button bubble")}
  >
    Click
  </button>
</div>

When we click the button, conceptually:

Parent capture
Button capture
Button bubble
Parent bubble

The capture handlers run while the event is moving down toward the target.

Then the target handler runs, followed by bubbling handlers moving back upward.

| **Aspect**        | **Bubbling**       | **Capturing**                            |
| ----------------- | ------------------ | ---------------------------------------- |
| **Direction**     | Target → Parent    | Parent → Target                          |
| **React example** | `onClick`          | `onClickCapture`                         |
| **Happens**       | After target phase | Before target phase                      |
| **Common use**    | Event delegation   | Handling events before they reach target |

## Note:
capturing
It means:
The event originated at the target, but before the browser delivers it to the target, it travels through the target's ancestors in the capturing phase.

Capturing runs first, then the target, then bubbling.

Even though the event happens/originates at the target, the browser processes the propagation phases in this order:

CAPTURING → TARGET → BUBBLING

Most React applications primarily use bubbling.

Capturing is useful when you specifically need a parent to observe/intercept an event before it reaches the child.

You don't need to use it for normal button clicks.

## Bubbling is commonly used for event delegation; capturing can be used when a parent needs to observe or intercept an event before the target handles it.
