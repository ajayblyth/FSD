PART 1 — Virtual DOM, Real DOM, Reconciliation & Fiber
======

This part has 4 questions, but they are connected. If you understand the flow, you can handle a lot of cross-questioning.

# 1. What is the Virtual DOM in React?
Interview answer

The Virtual DOM is a lightweight JavaScript representation of the actual DOM. React uses it to keep track of what the UI should look like. When state or props change, React creates a new Virtual DOM representation, compares it with the previous one, and then updates only the necessary parts of the actual DOM.

That's the interview answer. Now let's understand what it actually means.

What is the Real DOM?

The DOM (Document Object Model) is the browser's representation of your HTML page.
Simply put, the DOM is the browser's representation of your HTML page as a tree of objects.

For example:

function App() {
  return (
    <div>
      <h1>Hello</h1>
      <p>Welcome</p>
    </div>
  );
}

The browser creates something conceptually like:

DOM
└── div
    ├── h1 → Hello
    └── p  → Welcome

This is the Real DOM.

Then what is Virtual DOM?

React keeps a JavaScript representation of that UI in memory.

Conceptually:

Virtual DOM
└── div
    ├── h1 → Hello
    └── p  → Welcome

It's not another visible HTML page.

It's an internal representation React uses to determine what needs to change.

Why do we need it?

Imagine:

<h1>Hello</h1>
<p>Welcome</p>
<button>Count: 0</button>

Now the state changes:

Count: 0
   ↓
Count: 1

React doesn't blindly say:

"Let me rebuild/update the entire DOM."

Instead, React determines:

Previous UI:
button → Count: 0


New UI:
button → Count: 1


Difference:
button text changed

So React can update the relevant DOM node.

-----
Real DOM

The Real DOM is the browser's actual representation of the HTML document.

<h1>Hello</h1>

Browser creates a DOM node:

Document
  └── html
       └── body
            └── h1
                 └── "Hello"

These are actual browser DOM objects that the browser uses to display and manipulate the page.

Virtual DOM

The Virtual DOM is a JavaScript representation of what the UI should look like, maintained by React.

Important clarification

Don't say this in an interview:

❌ "Virtual DOM makes the DOM faster."

That's an oversimplification.

A better statement is:

"The Virtual DOM gives React an efficient way to represent and compare UI changes so React can determine what updates are necessary for the actual DOM."

The performance benefit comes from how React calculates and applies updates, not simply because "Virtual DOM is faster than DOM."

# 2. Virtual DOM vs Real DOM

Virtual DOM	Real DOM
JavaScript representation of UI	Browser's actual DOM
Exists in memory	Exists in the browser document
Managed by React	Managed by the browser
Used to determine UI changes	Actually displays the page
Lightweight representation	More expensive to manipulate
Interview answer

The Real DOM is the actual DOM maintained by the browser, while the Virtual DOM is React's in-memory representation of the UI. React uses the Virtual DOM to determine what changed and then applies the required changes to the Real DOM.

# 3. How does React reconciliation work?

This is the important connection.

Suppose initially:

function App() {
  return <h1>Hello</h1>;
}

React has a representation like:

Previous:
h1 → Hello

Then state changes and the component returns:

<h1>Hello Ajay</h1>

Now React has:

Previous:
h1 → Hello


New:
h1 → Hello Ajay

React compares the two representations.

It determines:

h1 is still the same element
        ↓
only text changed
        ↓
update the text in the Real DOM

This process of determining the differences between the previous and new UI representations and deciding what should change is called reconciliation.

Interview answer

Reconciliation is the process React uses to compare the previous UI representation with the new one after a render and determine what changes are required in the actual DOM. React then applies those necessary updates.

What happens when state changes?

This is the flow you should remember:

State changes
     ↓
Component renders again
     ↓
New UI representation is created
     ↓
React compares it with previous representation
     ↓
Reconciliation
     ↓
Required DOM updates are determined
     ↓
Real DOM is updated
Very important distinction

Rendering ≠ DOM updating

When someone says:

"The component re-rendered"

it does not automatically mean:

"The entire DOM was changed."

React can render a component, compare the result, and discover that very little—or even nothing—needs to change in the DOM.

This distinction is frequently asked in interviews.

# 4. What is React Fiber?

Fiber sounds complicated, but the basic idea is actually straightforward.

React Fiber is the internal reconciliation architecture introduced in React 16. It breaks rendering work into smaller units, allowing React to prioritize and schedule that work more efficiently. This makes React more capable of handling complex updates and enables features such as concurrent rendering.

Now let's understand that.

Before Fiber

Imagine React has a lot of UI work to perform:

Component A
Component B
Component C
Component D
Component E
Component F

If React treats the entire rendering process as one large uninterrupted task, it can become difficult to prioritize important work.

Fiber changed the architecture so React can represent rendering work as smaller units called Fiber nodes.

Conceptually:

Large rendering task
        ↓
Fiber A
Fiber B
Fiber C
Fiber D
Fiber E

React can then work through these units and make decisions about scheduling/prioritization.
----
Note: React sets the priority, not us directly.

Why was Fiber introduced?

Imagine the user is typing into a search box while the application is also rendering a large list.

The user interaction is important:

Typing "a"
Typing "ab"
Typing "abc"

React needs to keep the interface responsive.

Fiber provides the architecture that allows React to schedule and prioritize rendering work, which is important for modern concurrent features.

Very important: Fiber is NOT the Virtual DOM

This is a common cross-question.

You may be asked:

"Is Fiber the Virtual DOM?"

Answer:

"No. They're related, but they're not the same thing. The Virtual DOM is a conceptual representation of the UI, while Fiber is React's internal architecture for representing and processing rendering work."

Think:

Virtual DOM
    ↓
"What should the UI look like?"


Fiber
    ↓
"How should React process and schedule
the work required to get there?"

That's a much better mental model.

Cross-questioning
Q1. Does React update the entire Real DOM whenever state changes?

Answer:

No. A state change causes the component to render again. React then compares the new result with the previous one during reconciliation and applies the necessary changes to the Real DOM.

Q2. Does Virtual DOM mean React creates a complete copy of the browser DOM?

Answer:

Not exactly. The Virtual DOM is an in-memory JavaScript representation of the UI. It's a representation React uses internally; it's not a second browser DOM.

Q3. Is Virtual DOM the reason React is fast?

Answer:

It's one part of React's rendering approach, but saying "Virtual DOM makes React fast" is too simplistic. React's performance comes from its overall rendering, reconciliation, scheduling, and update strategies.

Q4. What triggers reconciliation?

A new render. For example, when state or props change, React may render the component again and then reconcile the new UI representation with the previous one.

Q5. Does re-rendering mean the Real DOM is updated?

Not necessarily. Re-rendering means React calculates the component's new UI. During reconciliation, React determines whether an actual DOM update is necessary.

This is very important.

Re-render
   ≠
DOM update
Q6. What is the relationship between Virtual DOM and reconciliation?

The Virtual DOM represents the UI, while reconciliation is the process React uses to compare the previous and new UI representations and determine what needs to change.

Q7. What is the relationship between reconciliation and Fiber?

Fiber is the internal architecture React uses to perform and schedule reconciliation work. It allows React to break work into smaller units and prioritize it more effectively.

Q8. Does Fiber directly manipulate the DOM?

Not in the sense of Fiber being "the DOM."

A good interview answer:

Fiber represents and manages React's rendering work. After React determines the necessary changes, React's commit phase applies the required changes to the actual DOM.

The complete mental model

If the interviewer asks you to explain all four together, you should be able to say:

"React maintains an in-memory representation of the UI, commonly referred to as the Virtual DOM. When state or props change, the component renders again and React gets a new UI representation. React then performs reconciliation, where it compares the previous and new representations to determine what needs to change. Fiber is the internal architecture that allows React to represent, schedule, and process this rendering and reconciliation work efficiently. Finally, React commits the necessary changes to the actual DOM."

And visualize it like this:

             STATE / PROPS CHANGE
                     ↓
              Component renders
                     ↓
             New UI representation
                     ↓
               RECONCILIATION
                     ↓
          Compare old vs new UI
                     ↓
                FIBER
      (process/schedule rendering work)
                     ↓
              Commit changes
                     ↓
                REAL DOM
⭐ The 4 things you must NOT mix up
Virtual DOM
→ Representation of the UI


Reconciliation
→ Comparing old and new UI to determine changes


Fiber
→ Internal architecture for processing/scheduling rendering work


Real DOM
→ Actual browser DOM that gets updated


# PART 2 — Re-rendering, Keys & Batching

Note:A re-render does NOT mean the entire DOM is recreated.

# 5. What happens when the state of a parent component changes?

When a parent's state changes, React schedules a re-render of that parent. By default, React also renders its child components to determine what their new UI should be. React then reconciles the new result with the previous one and updates the actual DOM only where necessary.

Let's understand this carefully.

Consider:

function Parent() {
  const [count, setCount] = useState(0);


  return (
    <div>
      <button onClick={() => setCount(count + 1)}>
        Count: {count}
      </button>
      <Child />
    </div>
  );
}

When we click the button:

count: 0
   ↓
count: 1

The Parent re-renders.

But what about Child?

By default, React also calls/renders the Child component again as part of rendering the parent subtree.

Conceptually:

Parent state changes
        ↓
Parent renders again
        ↓
React renders Child again
        ↓
Reconciliation
        ↓
Only required DOM changes are committed
Does that mean Child's DOM changes?

No.

Suppose:

function Child() {
  return <h2>Hello</h2>;
}

The child may render again, but React sees:

Previous:
<h2>Hello</h2>


New:
<h2>Hello</h2>

There is no difference.

Therefore:

Child function may execute again
        ↓
but
        ↓
DOM doesn't need to change

This distinction is very important in React interviews.

Let's prove it with code
function Parent() {
  const [count, setCount] = useState(0);


  console.log("Parent rendered");


  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>


      <Child />
    </>
  );
}


function Child() {
  console.log("Child rendered");


  return <h2>Hello</h2>;
}

Click the button.

You'll typically see:

Parent rendered
Child rendered


Parent rendered
Child rendered


Parent rendered
Child rendered

So the child function executes again.

But the browser doesn't necessarily recreate:

<h2>Hello</h2>

because the output hasn't changed.

# 6. Why does React sometimes re-render a component unnecessarily?

A component re-rendering doesn't automatically mean React is doing something wrong.

React's default behavior is essentially:

Parent renders → React evaluates the child subtree.

For example:

function Parent() {
  const [count, setCount] = useState(0);


  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>


      <Child />
    </>
  );
}

Every time count changes, Parent renders.

Therefore Child can also render again, even though it doesn't use count.

Why does React do this?

Because React needs to determine whether the child's output has changed.

It can't simply assume:

"Child doesn't care about the parent's state."

The child could depend on:

props
context
state
something else affecting its output

So React follows its rendering model.

How can we prevent unnecessary child renders?

One important tool is:

React.memo()  {not for context, only for props}

Example:

const Child = React.memo(function Child() {
  console.log("Child rendered");


  return <h2>Hello</h2>;
});

Now React can skip rendering the child when its props haven't changed.

Conceptually:

Parent state changes
       ↓
Parent renders
       ↓
Child is memoized
       ↓
Props didn't change?
       ↓
Yes
       ↓
Skip Child render

But remember:

React.memo() is a performance optimization, not something you should automatically apply to every component.

We'll cover re-render optimization more deeply later.

Very important cross-question

"Does React re-render the entire application when state changes?"
No.

A good interview answer:

"No. A state update causes the relevant component to render again and React processes its subtree. Reconciliation then determines what actually needs to change in the DOM. React doesn't blindly recreate the entire DOM."

# 7. What happens when the key of a React component changes?

This is extremely important.

Consider:

<User key={userId} />

Suppose:

key = 1

and later:

key = 2

React sees:

Previous:
<User key={1} />


New:
<User key={2} />

The key identifies the component's identity in that position.

Changing the key tells React:

"This is a different component, not the same component with updated data."

Therefore React will typically:

Old component
     ↓
Unmount
     ↓
New component
     ↓
Mount

Example
function User() {
  const [count, setCount] = useState(0);


  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        Count: {count}
      </button>
    </>
  );
}

Suppose:

<User key={1} />

You click:

Count: 0 → 1 → 2

Now change:

<User key={2} />

React treats it as a new component.

The state resets:

Count: 2
    ↓
Component replaced
    ↓
Count: 0
Why?

Because React uses keys as part of determining component identity.

This is why changing a key can intentionally reset component state.

For example:

<Form key={userId} />

If userId changes:

Old user
   ↓
key changes
   ↓
Form remounts
   ↓
Form state resets

This can actually be useful.

# 8. Why should you avoid using array indexes as keys?

Suppose you have:

const users = [
  { id: 1, name: "A" },
  { id: 2, name: "B" },
  { id: 3, name: "C" }
];

You render:

{users.map((user, index) => (
  <User key={index} user={user} />
))}

Initially:

Index     User


0         A
1         B
2         C

Now remove A.

The array becomes:

Index     User


0         B
1         C

Notice what happened.

Previously:

key 0 → A
key 1 → B
key 2 → C

After removing A:

key 0 → B
key 1 → C

The keys now represent different users.

React may interpret this as:

key 0
A → B

key 1
B → C

rather than simply:

A removed
B remains
C remains

This can cause incorrect component state preservation and unnecessary DOM work.

Better approach

Use a stable unique identifier:

{users.map(user => (
  <User key={user.id} user={user} />
))}

Now:

Before:
key 1 → A
key 2 → B
key 3 → C


After removing A:
key 2 → B
key 3 → C

React can correctly identify:

A → removed
B → same component
C → same component
Important: Why is this especially dangerous with component state?

Imagine:

function User({ user }) {
  const [isEditing, setIsEditing] = useState(false);


  return (
    <div>
      {user.name}


      <button onClick={() => setIsEditing(!isEditing)}>
        Edit
      </button>
    </div>
  );
}

Suppose you have:

A → editing = false
B → editing = true
C → editing = false

If A is removed and you're using indexes:

Old:
key 0 → A
key 1 → B (editing = true)
key 2 → C


New:
key 0 → B
key 1 → C

React may preserve state according to the keys.

Now C could incorrectly inherit the state that belonged to B.

That's one reason stable keys matter.

Interview answer

"We should avoid array indexes as keys when the list can be reordered, inserted into, or deleted from. Indexes can change when the list changes, which can cause React to associate the wrong component instance with the data and lead to incorrect state preservation. A stable unique ID is preferred."

# 9. What is batching in React?

Batching means:

React groups multiple state updates together and processes them in a single render instead of rendering after every individual update.

Consider:

function App() {
  const [count, setCount] = useState(0);
  const [name, setName] = useState("");


  function handleClick() {
    setCount(1);
    setName("Ajay");
  }


  return (
    <button onClick={handleClick}>
      Update
    </button>
  );
}

There are two state updates:

setCount()
setName()

React can batch them:

setCount()
     +
setName()
     ↓
ONE render

Instead of:

setCount()
 ↓
render


setName()
 ↓
render

This reduces unnecessary rendering work.

Important point

Batching doesn't mean:

"React combines the two state values into one state."

No.

The states remain separate:

count
name

React is simply grouping their updates into one rendering cycle.

NOTE: React does batching automatically. We usually don't have to do it manually.
React can batch state updates from different components in the same update/event.

# 10. What is automatic batching in React 18?

Before React 18, batching had more limited behavior.

For example, React commonly batched updates inside React event handlers:

function handleClick() {
  setCount(c => c + 1);
  setName("Ajay");
}

But updates occurring in some asynchronous contexts were not automatically batched in the same way.

React 18 expanded automatic batching so that updates from many asynchronous contexts can also be batched.

For example:

setTimeout(() => {
  setCount(c => c + 1);
  setName("Ajay");
}, 1000);

With React 18's automatic batching, these updates can be processed together.

Conceptually:

React event
     ↓
multiple updates
     ↓
one render




Promise / timeout / async callback
     ↓
multiple updates
     ↓
one render

"Batching means React groups multiple state updates into a single render to improve performance. React 18 introduced automatic batching, which extended this behavior to updates occurring in more asynchronous contexts such as promises, timeouts, and native event handlers."

One subtle interview point

Suppose:

setCount(count + 1);
setCount(count + 1);

You might expect:

0 → 1 → 2

But that's not necessarily what happens.

Both updates can use the same count value from the current render.

So you should use the functional form when the next state depends on the previous state:

setCount(c => c + 1);
setCount(c => c + 1);

Now React processes them sequentially:

0
 ↓
1
 ↓
2

This is a very useful cross-question around batching.

Cross-questioning
Q: If React batches updates, does that mean state updates happen immediately?

Not necessarily.

React schedules state updates and processes them according to its rendering model.

That's why you shouldn't assume:

setCount(count + 1);


console.log(count);

will immediately show the new value.

The current render's count is still the value from that render.

Q: Does batching happen only with useState()?

No.

The concept applies to React state updates generally, including updates from hooks such as useState and useReducer.

Q: Does React.memo prevent a parent from re-rendering?

No.

React.memo is used to potentially skip rendering a memoized child when its props haven't changed.

The parent still re-renders.

Parent
  ↓ state changes
Parent renders
  ↓
Memoized Child
  ↓
props unchanged
  ↓
Child render can be skipped
Q: Why does changing a key cause a remount?

Because the key contributes to the component's identity.

When React sees a different key, it treats it as a different component instance.

key = 1
   ↓
Component A


key = 2
   ↓
Different identity
   ↓
Component A removed
   ↓
New component mounted
Q: Is using index as a key always wrong?

No.

This is a good interview nuance.

Using an index can be acceptable when the list is:

static
never reordered
never filtered
never inserted/deleted

But if the list can change, a stable unique ID is much safer.

# PART 3 — Lifecycle & Strict Mode

We have 3 questions here. They are closely connected, so understanding one makes the next two easier.

# 11. How does React handle component lifecycle in functional components?

In functional components, React doesn't use lifecycle methods like class components did. 
Instead, the lifecycle is mainly handled through rendering and Hooks such as useEffect(). 
We generally think of a component's lifecycle in three stages: mounting, updating, and unmounting.

Let's understand each.

1. Mounting

When the component appears on the screen for the first time.

Component created
      ↓
Render
      ↓
DOM updated
      ↓
Effects run

Example:

useEffect(() => {
  console.log("Component mounted");
}, []);

The empty dependency array means the effect runs after the initial render.

2. Updating

When the component re-renders because of:

state change
prop change
context change

Example:

const [count, setCount] = useState(0);


useEffect(() => {
  console.log("Count changed");
}, [count]);

Whenever count changes:

count changes
   ↓
component renders
   ↓
effect runs
3. Unmounting

When the component is removed from the UI.

This is where the cleanup function is important.

useEffect(() => {
  console.log("Effect started");


  return () => {
    console.log("Cleanup");
  };
}, []);

or with actual cleanup
useEffect(() => {
  const timer = setInterval(() => {
    console.log("Running");
  }, 1000);

  return () => {
    clearInterval(timer);
  };
}, []);

The cleanup can be used for things like:

removing event listeners
clearing timers
unsubscribing
cancelling/cleaning up resources

So:

Mount
 ↓
Effect


Update
 ↓
Cleanup previous effect
 ↓
Effect again


Unmount
 ↓
Cleanup


Important: Functional components don't have componentDidMount()

In class components, you had:

componentDidMount()
componentDidUpdate()
componentWillUnmount()

In functional components, these behaviors are generally handled using:

useEffect()

But don't say:

"useEffect() is exactly the same as all three lifecycle methods."

That's not technically correct.

A better answer:

"Functional components don't have class lifecycle methods. React provides Hooks, especially useEffect, to perform side effects and cleanup at different points in a component's lifecycle."

# 12. What is React Strict Mode?

React Strict Mode is a development-only feature that helps identify potential problems in a React application. It can intentionally re-run certain parts of a component's logic and effects during development to help detect unsafe side effects and missing cleanup. It does not affect the production build in the same way.

You usually enable it like this:

<React.StrictMode>
  <App />
</React.StrictMode>

Its purpose is basically:

Help developers find problems early.

For example, if your effect creates a subscription but doesn't clean it up, Strict Mode can make that problem easier to notice.

Note:"subscription" doesn't mean subscribing to a YouTube channel.

It means your component is subscribing to some ongoing external source to receive updates.

For example:

useEffect(() => {
  const subscription = chatService.subscribe(message => {
    console.log(message);
  });


  return () => {
    subscription.unsubscribe();
  };
}, []);

Think of it like:

Component mounts
      ↓
"Hey chat service, send me new messages"
      ↓
Messages keep coming

Then the component is removed:

Component unmounts
      ↓
"Stop sending messages to this component"
      ↓
unsubscribe()

Why is this necessary?

Suppose you have:

useEffect(() => {
  chatService.subscribe(message => {
    console.log(message);
  });
}, []);

You forget the cleanup.

Then:

Component mounts
    ↓
Subscription #1 created


Component unmounts
    ↓
Subscription #1 STILL EXISTS ❌


Component mounts again
    ↓
Subscription #2 created


Component unmounts
    ↓
Subscription #2 STILL EXISTS ❌

Now old subscriptions are still running even though their component is gone.

That can cause:

unnecessary memory usage
duplicate events
unexpected behavior
memory leaks

So cleanup basically means:

"I started this external activity when the component appeared; stop it when the component no longer needs it."

And that's why we have:

useEffect(() => {
  // Start something


  return () => {
    // Stop/clean up that something
  };
}, []);

# 13. Why does useEffect() sometimes run twice in development?

This is where people often get confused.

Consider:

useEffect(() => {
  console.log("Effect");
}, []);

You might expect:

Effect

once.

But with Strict Mode in development, you may see:

Effect
Effect

Why?

React intentionally performs an extra development-time setup/cleanup cycle to help detect effects that aren't properly written or cleaned up.

Conceptually:

Development + Strict Mode


Mount
 ↓
Effect runs
 ↓
Cleanup
 ↓
Effect runs again

This is not because your dependency array is broken.

And it does not mean production will behave identically.

Example with cleanup
useEffect(() => {
  console.log("Effect");


  return () => {
    console.log("Cleanup");
  };
}, []);

With Strict Mode in development, you may see something conceptually like:

Effect
Cleanup
Effect

This helps expose code that incorrectly assumes:

"This effect will only ever run once."

Why is React doing this?

Imagine you have:

useEffect(() => {
  window.addEventListener("resize", handleResize);
}, []);

But you forgot:

return () => {
  window.removeEventListener("resize", handleResize);
};

Now every setup adds another listener.

Strict Mode's extra development cycle can expose this kind of problem.

The correct version is:

useEffect(() => {
  window.addEventListener("resize", handleResize);


  return () => {
    window.removeEventListener("resize", handleResize);
  };
}, []);
Cross-questioning
Q: Does Strict Mode cause useEffect() to run twice in production?

No. The extra development behavior is associated with Strict Mode's development checks. You shouldn't design your application around the assumption that effects will run twice in production.

Q: Does an empty dependency array guarantee an effect will execute exactly once?

Not universally.

A better interview answer:

"An empty dependency array means the effect doesn't re-run because of dependency changes. However, in development with Strict Mode, React may perform an additional setup/cleanup cycle."

Q: Should we remove Strict Mode to stop the double effect?

Usually, no.

The better solution is to write effects correctly and provide proper cleanup where necessary.

# PART 4 — useReducer, Custom Hooks & Rules of Hooks

# 14. What is useReducer()?

useReducer() is a React Hook used for managing state when the state logic is more complex or involves multiple related state updates. Instead of directly updating the state, we dispatch an action, and a reducer function decides what the next state should be.

Note: Action- An action is simply a description of what happened.
reducer-The reducer is a function that decides what the new state should be.

The basic structure is:

const [state, dispatch] = useReducer(reducer, initialState);

There are three important things:

state
 ↓
Current state


dispatch
 ↓
Sends an action


reducer
 ↓
Decides the next state

Simple example:
import { useReducer } from "react";

function reducer(state, action) {
  if (action.type === "increment") {
    return { count: state.count + 1 };
  }

  if (action.type === "decrement") {
    return { count: state.count - 1 };
  }

  return state;
}


function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 }); 

   //useReducer() returns an array containing: [currentState, dispatchFunction]


  return (
    <>
      <h2>{state.count}</h2>


      <button onClick={() => dispatch({ type: "increment" })}>
        +
      </button>


      <button onClick={() => dispatch({ type: "decrement" })}>
        -
      </button>
    </>
  );
}

The flow is:

User clicks +
      ↓
dispatch({ type: "increment" })
      ↓
reducer receives state + action
      ↓
reducer returns new state
      ↓
Component re-renders

Why not just useState?

For a simple counter:

const [count, setCount] = useState(0);

useState is much simpler.

But imagine a form:

name
email
password
loading
error
success

and several actions can change these values.

A reducer can put the state transition logic in one place.

# 15. When would you use useReducer() instead of useState()?
Interview answer

I would use useReducer() when the state has multiple related values or when there are several ways the state can change. 
For simple independent state, I would normally prefer useState() because it's simpler.

useState() example
const [count, setCount] = useState(0);

Simple.

useReducer() example

loading

error

You might have actions like:

That becomes easier to organize with a reducer.

Simple rule

   ↓

   ↓

Don't say:

"useReducer is for large applications."

That's not the main distinction.

The real question is:

You can use useReducer in a small application and useState in a large application.

# 16. What is a custom Hook?
As we know. React Hooks are built-in functions provided by React that let functional components use features like state, effects, and context.

Custom Hooks are JavaScript functions created by developers to reuse stateful logic between components.
Custom Hooks normally start with use, like useFetch() or useAuth(). 
It helps us avoid duplicating the same Hook-related logic.

For example, suppose multiple components need to fetch users.

Instead of repeating:

useState()
useEffect()
fetch()

in every component, we can create:

useUsers()

## How do you create a custom Hook?

A custom Hook is simply a function whose name starts with use and which can call other Hooks.

Example:

import { useEffect, useState } from "react";


function useUsers() {
  const [users, setUsers] = useState([]);


  useEffect(() => {
    fetch("https://jsonplaceholder.typicode.com/users")
      .then(res => res.json())
      .then(data => setUsers(data));
  }, []);


  return users;
}

Now a component can use it:

function UserList() {
  const users = useUsers();


  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>
        {user.name}
        </li>
      ))}
    </ul>
  );
}

Another component can use the same logic:

function UserDropdown() {
  const users = useUsers();


  return (
    <select>
      {users.map(user => (
        <option key={user.id}>
        {user.name}
        </option>
      ))}
    </select>
  );
}

The important point is:

We're reusing the logic, not sharing the same state between the two components.

This is a very common interview follow-up.

If:

UserList → useUsers()
UserDropdown → useUsers()

each component gets its own state instance.

A custom Hook does not automatically create global/shared state.

# 18. What are the Rules of Hooks?

There are two main rules you should know.

Rule 1 — Only call Hooks at the top level

Don't call Hooks inside:
if
for
while
nested functions
conditions

Correct:
function App() {
  const [count, setCount] = useState(0);


  if (count > 5) {
    console.log("Greater than 5");
  }


  return <div>{count}</div>;
}

Incorrect:

function App() {
  const [count, setCount] = useState(0);


  if (count > 5) {
    useEffect(() => {
      console.log("Hello");
    }, []);
  }


  return <div>{count}</div>;
}
Rule 2 — Only call Hooks from React functions

Hooks should be called from:

React function components
Custom Hooks

For example:

function User() {
  const [name, setName] = useState("");
}

or:

function useUser() {
  const [user, setUser] = useState(null);
}

You shouldn't call Hooks from an ordinary JavaScript function that isn't a component or custom Hook.

# 19. Why can't Hooks be called inside loops or conditions?

This is one of the most important conceptual questions.


Hooks must always be called in the same order on every render. React relies on that consistent order to associate each Hook call with its stored state and other internal data. If we call Hooks conditionally or inside loops, the order or number of Hook calls can change between renders, which can cause React to associate the wrong state with the wrong Hook.

Let's make this very simple.

Suppose:

function App() {
  const [name, setName] = useState("Ajay");
  const [age, setAge] = useState(25);
}

React internally needs to keep track of:

Hook #1 → name
Hook #2 → age

Now imagine:

if (someCondition) {
  useState(...)
}


useState(...)

On one render:

Hook #1
Hook #2

But on another:

Hook #1

Now React can't reliably associate the Hook calls with the same positions.

That's why Hooks must have a consistent order.

Example of the problem

Don't do this:

function App({ loggedIn }) {
  if (loggedIn) {
    const [user, setUser] = useState(null);
  }


  const [count, setCount] = useState(0);


  return <div>{count}</div>;
}

If loggedIn changes:

Render 1:
useState(user)
useState(count)


Render 2:
useState(count)

The order changed.

That's exactly what the Rules of Hooks are designed to prevent.

Important trick: You CAN put conditions around the logic

You just can't put the Hook call inside the condition.

Wrong:

if (user) {
  useEffect(() => {
    console.log("User exists");
  }, []);
}

Correct:

useEffect(() => {
  if (user) {
    console.log("User exists");
  }
}, [user]);

The Hook is always called.

Only the logic inside it is conditional.

Q: Can a custom Hook share state between components?

Not by itself.

If two components call:

they normally get separate state.

Component A
  ↓

  ↓
State A




Component B
  ↓
useCounter()

A custom Hook shares logic, not automatically the state.

Q: Does a custom Hook have to use another Hook?

In practice, a custom Hook is intended to encapsulate reusable Hook-related logic, so it normally calls one or more Hooks.

Its name should start with use.

Examples:

useFetch()
useAuth()
useLocalStorage()

Q: Can I call a custom Hook conditionally?

No.

if (loggedIn) {
  useAuth(); // ❌
}

Instead:

const auth = useAuth();


if (loggedIn) {
  // use auth here
}

The custom Hook itself follows the same Rules of Hooks.

A good answer:
