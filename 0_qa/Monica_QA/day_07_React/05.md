# 57. What is Client-Side Rendering (CSR)?

This is the traditional React approach with applications created using tools like Vite.

The server initially sends something like:

HTML
  ↓
JavaScript files
  ↓
Browser downloads React
  ↓
React runs
  ↓
React creates the UI

For example, initially the browser may receive:

<div id="root"></div>

Then JavaScript loads and React does:

createRoot(document.getElementById("root")).render(<App />);

React creates the actual UI inside root.

Example
Browser requests /products
        ↓
Server sends HTML + JS
        ↓
Browser downloads JS
        ↓
React executes
        ↓
Products component renders
        ↓
User sees page

This is Client-Side Rendering because the browser is responsible for rendering the application UI.

Advantages
Very good for highly interactive applications like admin dashboards, social media apps, chat applications, project management tools, and online editors.

CSR is fast after initial load because you usually don't reload the entire HTML page when navigating. But lazy-loaded code or API data can still take time.

After the initial load, navigation can be fast
Server doesn't need to render every page's HTML

Disadvantages
The initial page can take longer to become meaningful because the browser may need to:

Download JS
   ↓
Parse JS
   ↓
Execute React
   ↓
Render UI

SEO can also be more challenging for pure CSR applications, although modern search engines can execute JavaScript.


"In Client-Side Rendering, the server initially sends the application shell and JavaScript to the browser. React then runs in the browser and generates the UI. Vite-based React applications are commonly CSR applications."
shell is like basic structure of the app.

# 58. What is Server-Side Rendering (SSR)?

With SSR, the server generates the HTML for the page before sending it to the browser.

Instead of:

Browser gets empty root
        ↓
React renders

we have:

Browser requests page
        ↓
Server runs React
        ↓
Server generates HTML
        ↓
Browser receives HTML
        ↓
User can see rendered content

For example, the server might send:

<div>
  <h1>Products</h1>
  <p>iPhone</p>
  <p>Laptop</p>
</div>

The browser can display that HTML immediately.

Later, JavaScript loads and React hydrates that HTML to make it interactive.

We'll discuss hydration in Q60.

Why use SSR?

One major benefit is that the initial HTML contains actual page content.

This can help with:

Initial page load experience
SEO
Social sharing previews
Content-heavy websites
Interview answer

"In Server-Side Rendering, React generates the HTML for a page on the server and sends that rendered HTML to the browser. The browser can display the content before the client-side JavaScript has fully taken over, and React later hydrates that HTML to make it interactive."

# 60. What is Hydration?

This is where many people get confused.

Suppose SSR sends:

<button>Buy Now</button>

The browser can see the button, but the HTML itself doesn't contain React's event-handling behavior.
Then React loads in the browser and connects its logic to the existing HTML.
That process is called hydration.

or 

"Hydration is the process where React attaches its logic and event handlers to the HTML that was already rendered by the server, making the page interactive. In SSR, the user can see the HTML content before the React JavaScript fully runs. Once the JavaScript loads, React hydrates that HTML instead of rendering everything from scratch. This allows the server-rendered page to become a fully interactive React application."

SSR
 ↓
Server generates HTML
 ↓
Browser receives HTML
 ↓
User sees content
 ↓
React JavaScript loads
 ↓
React hydrates HTML
 ↓
Page becomes interactive

So:

Rendering creates the UI. Hydration makes server-rendered UI interactive with React.

Simple example

Server sends:

<button>Buy Now</button>

After hydration:

<button onClick={handleBuy}>
  Buy Now
</button>

Now clicking the button can trigger the React event handler.

Hydration mismatch

What is a hydration mismatch?

It happens when the HTML generated by the server doesn't match what React expects to render on the client.

For example, server:

Time: 10:00

Client immediately renders:

Time: 10:01

React can detect that the server HTML and client output don't match.

This is called a hydration mismatch.

"Hydration is the process where React attaches its functionality and event handling to HTML that was already rendered on the server. SSR gives us the initial HTML, and hydration makes that HTML interactive on the client."

# 62. What are Server Components in React?

The easiest way to understand Server Components is:

A Server Component is a React component whose code runs on the server, not in the browser.

This is different from SSR.

Important distinction

SSR answers:

Where is the initial HTML generated?

Server Components answer:

Where does the component's code execute?

They are related, but not the same thing.

Why Server Components?

Normally, a client-side React component's JavaScript eventually needs to be sent to the browser.

Imagine:

ProductPage
   ↓
ProductList
   ↓
ProductCard

If these components don't need browser interaction, sending all their JavaScript to the browser may be unnecessary.



A Server Component can execute on the server:

Server
  ↓
Server Component
  ↓
Fetch database/API data
  ↓
Generate React output
  ↓
Send result to browser

This can reduce the amount of JavaScript that needs to run on the client.

Example

Imagine a product page:

async function ProductList() {
  const products = await getProducts();


  return (
    <div>
      {products.map((product) => (
        <p key={product.id}>
          {product.name}
        </p>
      ))}
    </div>
  );
}


export default ProductList;

If this is a Server Component, the data can be fetched on the server.

The browser doesn't need to receive all the server-side code used to fetch that data.

What can Server Components do?

They are useful for:

Fetching data on the server
Accessing server-side resources
Keeping server-only logic away from the browser
Reducing client-side JavaScript

For example:

Server Component
      ↓
Database
      ↓
Get products
      ↓
Render product list

The browser doesn't need direct access to the database.

What can't Server Components do?

They cannot directly use browser-only interactive features such as:

useState()
useEffect()
onClick

For example:

function Counter() {
  const [count, setCount] = useState(0);


  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}

This requires client-side interaction, so it needs to be a Client Component in a Server Components framework.

Important: Server Components are not the same as backend APIs

A Server Component is still a React component.

It's simply a component whose execution happens on the server.

Think:

Server Component
      ↓
React component running on server

not:

Server Component = Express API

They are different concepts.

Interview answer

"Server Components are React components that execute on the server instead of the browser. They're useful for server-side data fetching and keeping server-only logic out of the client bundle. They can reduce the amount of JavaScript sent to the browser, but they can't directly use client-side features such as state, effects, or event handlers."

# 64. What is Concurrent Rendering in React?
First understand it

Imagine you have a search box with 10,000 products.

The user types:

a

React needs to:

Update the input.
Filter 10,000 products.
Render the results.

If filtering/rendering takes time, the input itself can feel slow.

Older React rendering was more synchronous:

Start rendering
      ↓
Keep working until finished
      ↓
Browser gets control

Concurrent rendering allows React to work on rendering, pause it, and prioritize more important updates.

Conceptually:

User types
    ↓
Urgent update → update input immediately
    ↓
Less urgent update → render later

So the important point is:

Concurrent rendering allows React to interrupt and prioritize rendering work instead of treating every update as equally urgent.

React can decide which work should happen first.

Is this multiple threads?

No.

Concurrent rendering does not mean React is simply rendering on multiple JavaScript threads.

It's about React's ability to schedule, pause, resume, and abandon rendering work.

Why is this useful?

Especially for expensive UI updates:

Search
Large lists
Complex filtering
Large tables
Heavy rendering

The goal is to keep the UI responsive.

Interview answer

"Concurrent rendering is React's ability to work on rendering tasks in a way that allows it to prioritize more important updates. React can pause or interrupt less urgent rendering work so urgent interactions, like typing or clicking, remain responsive."

# 65. What is useTransition()?

useTransition() lets us tell React:

"This state update is not urgent. You can render it with lower priority."

It gives us:

const [isPending, startTransition] = useTransition();

There are two values:

isPending

Tells us whether the transition is currently being processed.

startTransition

Used to mark a state update as non-urgent.

Example

Imagine a search page:

import { useState, useTransition } from "react";


function Search() {
  const [query, setQuery] = useState("");
  const [results, setResults] = useState([]);


  const [isPending, startTransition] = useTransition();


  const handleChange = (e) => {
    const value = e.target.value;


    // Urgent update
    setQuery(value);


    // Non-urgent update
    startTransition(() => {
      const filtered = largeProductList.filter((product) =>
        product.name.toLowerCase().includes(value.toLowerCase())
      );


      setResults(filtered);
    });
  };


  return (
    <div>
      <input
        value={query}
        onChange={handleChange}
      />


      {isPending && <p>Updating results...</p>}


      {results.map((product) => (
        <p key={product.id}>
          {product.name}
        </p>
      ))}
    </div>
  );
}

The important part is:

startTransition(() => {
  setResults(filtered);
});

We're telling React:

Updating the search results is less urgent than updating the input.

Important rule

Don't put the urgent update inside the transition.

Good:

setQuery(value);


startTransition(() => {
  setResults(filtered);
});

Because:

Input update → urgent
Search results → lower priority
When would I use it?

Use useTransition() when:

A state update causes an expensive UI update, but the user should still be able to interact with the application smoothly.

Examples:

Large search results
Tabs containing expensive content
Large lists
Complex filtering
Interview answer

"useTransition lets me mark a state update as non-urgent. React can prioritize urgent interactions, like typing, while rendering the transition in the background. It also gives me isPending so I can show a loading indicator while the transition is in progress."

# 66. What is useDeferredValue()?

useDeferredValue() is similar, but the approach is different.

Instead of saying:

"Make this particular state update low priority."

we say:

"Give me a deferred version of this value."

Syntax:

const deferredQuery = useDeferredValue(query);
Example
import {
  useState,
  useDeferredValue,
} from "react";


function Search() {
  const [query, setQuery] = useState("");


  const deferredQuery = useDeferredValue(query);


  return (
    <div>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
      />


      <ProductList search={deferredQuery} />
    </div>
  );
}

Now there are two values:

query
  ↓
Latest value immediately


deferredQuery
  ↓
May temporarily lag behind

So while the user types:

query:          "laptop"
deferredQuery:  "lapt"

for a short time, and then React catches it up.

The expensive component can use:

<ProductList search={deferredQuery} />

while the input stays responsive.

Important distinction

useDeferredValue() does not create a new state.

It gives you a deferred version of an existing value.

const deferredQuery = useDeferredValue(query);

You still update:

setQuery(...)

normally.

Interview answer

"useDeferredValue lets me create a lower-priority version of an existing value. The original value updates immediately, while the deferred value can lag slightly, allowing expensive components that depend on it to update without making the UI feel blocked."

# 67. useTransition() vs useDeferredValue()

They solve similar performance problems, but from different directions.

| **Point**                | **useTransition()**                          | **useDeferredValue()**                         |
| ------------------------ | -------------------------------------------- | ---------------------------------------------- |
| **Works with**           | State update                                 | Existing value                                 |
| **Main API**             | `startTransition()`                          | `useDeferredValue()`                           |
| **You control**          | Which update is non-urgent                   | Which value can be delayed                     |
| **Pending state?**       | ✅ Yes — `isPending`                          | ❌ No direct `isPending`                        |
| **Typical use**          | Mark an expensive state update as non-urgent | Pass a delayed value to an expensive component |
| **Easy way to remember** | **"Delay this update"**                      | **"Delay this value"**                         |


useTransition:

"This update is not urgent."

startTransition(() => {
  setResults(data);
});

useDeferredValue:

"This value doesn't need to update immediately."

const deferredQuery = useDeferredValue(query);

   ↓

startTransition()
   ↓

# 68. What is Suspense-based data fetching?

You already know Suspense from Q38 for lazy-loaded components.

The same general idea can be used for data loading:

Component needs data
       ↓
Data isn't ready
       ↓
Suspend
       ↓
Show fallback
       ↓
Data becomes available
       ↓
Render component

For example, conceptually:

<Suspense fallback={<p>Loading...</p>}>
  <ProductList />
</Suspense>

If ProductList suspends while waiting for data, React can display:

Loading...

and then render the component once the data is ready.

Important modern React point

Suspense itself doesn't magically fetch data.

The data source/framework must support React's Suspense mechanism.

This is important because you shouldn't say:

"Suspense automatically fetches API data."

That's not correct.

Instead:

Suspense provides the mechanism for React to display fallback UI while something is not ready, and supported data-fetching frameworks/libraries can integrate with it.

Example conceptually
<App>
   │
   ▼
<Suspense fallback="Loading...">
   │
   ▼
<ProductList />
   │
   ▼
Data not ready
   │
   ▼
React shows fallback
   │
   ▼
Data ready
   │
   ▼
ProductList renders

"Suspense-based data fetching allows React to show fallback UI while a component is waiting for data from a Suspense-enabled data source. React temporarily suspends rendering that part of the tree and shows the fallback, then renders the component when the data is ready. Suspense itself doesn't perform the API request; the data-fetching mechanism needs to support Suspense."

# 69. How do you implement an accessible React application?

Accessibility means making your application usable by as many people as possible, including people who use:

Screen readers
Keyboard navigation
Voice control
Other assistive technologies

React itself doesn't automatically make an application accessible. We need to follow web accessibility practices.

1. Use semantic HTML

Instead of using:

<div onClick={handleClick}>
  Submit
</div>

prefer:

<button onClick={handleClick}>
  Submit
</button>

Why?

A <button> already provides:

Keyboard support
Proper semantics
Screen-reader information
Expected browser behavior

Similarly, use:

<header>
<nav>
<main>
<section>
<footer>
<form>
<button>

instead of using <div> for everything.

2. Provide labels for form fields

Bad:

<input type="text" />

Better:

<label htmlFor="email">
  Email
</label>

<input
  id="email"
  type="email"
/>

Now a screen reader can understand what the input represents.

3. Use alt text for meaningful images
<img
  src="/profile.jpg"
  alt="User profile"
/>

If an image is purely decorative:

<img
  src="/decoration.png"
  alt=""
/>

4. Make the application keyboard accessible

Users should be able to navigate important controls using the keyboard.

For example:

Tab
 ↓
Button
 ↓
Input
 ↓
Link

Avoid building clickable UI using non-interactive elements like <div> when a <button> or <a> is appropriate.

5. Use ARIA when necessary

ARIA can provide additional accessibility information.

For example:

<button
  aria-label="Close menu"
  onClick={closeMenu}
>
  X
</button>

But an important rule is:

Use semantic HTML first. Use ARIA when native HTML doesn't provide enough information.

Don't add ARIA unnecessarily.

6. Handle accessible form errors

For example:

<input
  id="email"
  aria-describedby="email-error"
/>


<p id="email-error">
  Please enter a valid email.
</p>

Now assistive technologies can associate the error with the input.

Interview answer

"For accessibility in React, I use semantic HTML, proper labels for form fields, meaningful alt text for images, keyboard-accessible controls. we prefer native HTML elements like button and input instead of creating custom behavior with divs."

# 70. How do you improve the SEO of a React application?
First understand the problem

Search engines need to understand the content of your pages.

A pure client-side React application may initially send something like:

<div id="root"></div>

and then JavaScript generates the actual content.

Modern search engines can execute JavaScript, but for content-heavy/public applications, relying entirely on client-side rendering can make SEO more complicated.

So we can improve SEO using proper HTML, metadata, URLs, rendering strategies, and performance.

1. Use meaningful page titles and meta descriptions

For example:

<title>Best Running Shoes | My Store</title>


<meta
  name="description"
  content="Explore our collection of running shoes."
/>

These help search engines understand the page and can influence how the page appears in search results.

2. Use semantic HTML

Instead of:

<div>
  <div>Products</div>
  <div>...</div>
</div>

use meaningful elements:

<main>
  <h1>Products</h1>


  <section>
    ...
  </section>
</main>

Headings are particularly important.

A page should generally have a clear primary heading:

<h1>Running Shoes</h1>

3. Use SSR or static generation when appropriate

For public pages where SEO is important:

Server
 ↓
Generate HTML
 ↓
Browser

The search engine can receive meaningful HTML content without depending entirely on client-side rendering.

Frameworks such as Next.js support server rendering and static generation.

4. Use clean URLs

Prefer:

/products/running-shoes

over something difficult to understand like:

/page?id=938472&cat=4

Clean URLs make the site's structure easier to understand.

5. Optimize performance

Performance is also important for user experience and search visibility.

Things we already discussed include:

Code splitting
Lazy loading
Optimized images
Reducing unnecessary JavaScript
Caching
Fast API responses

For example:

const ProductPage = lazy(() => import("./ProductPage"));

can reduce the initial JavaScript required for a page.

6. Make pages mobile-friendly

The application should work properly on different screen sizes.

For example:

Desktop
Tablet
Mobile

Responsive design is important for modern websites.

7. Use proper links

Prefer:

<a href="/products">
  Products
</a>

or the appropriate routing component for your framework.

Search engines can understand actual links and crawl the site structure.

8. Add sitemap and robots.txt

A production website can provide:

sitemap.xml
robots.txt
Sitemap

Helps search engines discover important URLs.

robots.txt

Provides crawling instructions to search-engine bots.

Interview answer

"For SEO in a React application, I'd use semantic HTML, proper page titles and meta descriptions, meaningful headings and URLs, optimized images and performance, and make sure the site is mobile-friendly. For public content-heavy pages, I'd also consider SSR or static generation using a framework like Next.js so search engines can receive meaningful HTML content."

Because the server can send HTML containing the actual page content.

       ↓

       ↓

SSR:

This makes the initial content easier for crawlers and users to consume.
