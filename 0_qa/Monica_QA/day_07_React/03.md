# 39. How do you handle API loading, success, and error states?

When a React component calls an API, there are normally three important states:

Loading
   ↓
API request is happening


Success
   ↓
Data received


Error
   ↓
Something went wrong
Interview answer

"I usually maintain separate loading, data, and error states. I set loading to true before the request, store the response data on success, and store an error message if the request fails. 
Finally, I set loading back to false in both success and failure cases."

Complete example

Let's create:

src/
├── components/
│   └── UserList.jsx
└── App.jsx
src/components/UserList.jsx
import { useEffect, useState } from "react";


function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState("");


  useEffect(() => {
    async function fetchUsers() {
      try {
        setLoading(true);
        setError("");


        const response = await fetch(
          "https://jsonplaceholder.typicode.com/users"
        );


        if (!response.ok) {
          throw new Error("Failed to fetch users");
        }


        const data = await response.json();


        setUsers(data);


      } catch (error) {
        setError(error.message);
      } 
      finally {
        setLoading(false);
      }
    }


    fetchUsers();
  }, []);


  if (loading) {
    return <p>Loading users...</p>;

Then:

src/App.jsx
import UserList from "./components/UserList";


function App() {
  return (
    <div>
      <h1>My Application</h1>


      <UserList />
    </div>
  );
}


export default App;
Understand the flow

Initially:

const [users, setUsers] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState("");

So:

users   → []
loading → true
error   → ""

React displays:

Loading users...

Then API request happens.

If successful:
API
 ↓
data received
 ↓
setUsers(data)
 ↓
setLoading(false)
 ↓
show users
If it fails:
API
 ↓
error
 ↓
setError(...)
 ↓
setLoading(false)
 ↓
show error
Why finally?

We have:

finally {
  setLoading(false);
}

finally executes whether the request:

succeeds
OR
fails

Without it, you might accidentally leave:

loading = true

after an error.

Why check response.ok?

This is a common beginner mistake.

fetch() does not automatically throw an error for HTTP errors like 404 or 500.

So:

const response = await fetch(url);

may successfully return a Response even when the server says:

404 Not Found

That's why we check:

if (!response.ok) {
  throw new Error("Failed to fetch users");
}

Then catch handles it.

A better mental model

For most API calls, think:

          API REQUEST
               │
        ┌──────┴──────┐
        ↓             ↓
     SUCCESS         ERROR
        ↓             ↓
     setData()     setError()
        │             │
        └──────┬──────┘
               ↓
        setLoading(false)

The Controller contains the application/business logic.

MERN is not itself an MVC framework.

M → Mongoose/MongoDB
V → React
C → Node.js + Express

But this mapping is not perfectly strict. For example, Express handles routing and HTTP concerns, while React is the frontend UI layer. In a typical MERN project, MVC is mainly an organizational architecture you choose to follow.


# 40. How do you cancel an API request in React?

Suppose the component starts an API request:

User opens /users
      ↓
Users component mounts
      ↓
useEffect runs
      ↓
API request starts
      ↓
User goes to /products
      ↓
Users component is removed
      ↓
Users component unmounts

Note:
Mount = component is added/appears in the UI.
Unmount = component is removed/disappears from the UI.


The request might still be running.

We can cancel a fetch() request using AbortController.

"I use AbortController with the Fetch API. I create an AbortController before starting the request and pass its signal to fetch. In the effect cleanup function, I call controller.abort() so the request is cancelled when the component unmounts or before a new request starts."

Complete example
src/components/UserList.jsx
import { useEffect, useState } from "react";


function UserList() {
  const [users, setUsers] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState("");


  useEffect(() => {
    const controller = new AbortController();


    async function fetchUsers() {
      try {
        setLoading(true);
        setError("");


        const response = await fetch(
          "https://jsonplaceholder.typicode.com/users",
          {
            signal: controller.signal,
          }
        );


        if (!response.ok) {
          throw new Error("Failed to fetch users");
        }


        const data = await response.json();


        setUsers(data);
      } catch (error) {
        if (error.name === "AbortError") {
          console.log("Request was cancelled");
          return;
        }


        setError(error.message);
      } finally {
        setLoading(false);
      }
    }

    fetchUsers();


    return () => {
      controller.abort();
    };
  }, []);


  if (loading) {
    return <p>Loading...</p>;
  }


  if (error) {
    return <p>Error: {error}</p>;
  }


  return (
    <div>
      {users.map((user) => (
        <p key={user.id}>{user.name}</p>
      ))}
    </div>
  );
}


export default UserList;

Understand AbortController
We create:

const controller = new AbortController();

Then:

fetch(url, {
  signal: controller.signal,
});

This connects the request to the controller.

Then cleanup:

return () => {
  controller.abort();
};

means:

"Cancel this request when this effect is cleaned up."

Why do we check AbortError?

When we intentionally cancel the request:

controller.abort();

the fetch promise rejects.

But cancellation isn't really an application error.

So:

if (error.name === "AbortError") {
  return;
}

prevents us from displaying:

Error: The user cancelled the request

as though something went wrong.

Very important connection with useEffect

Remember:

useEffect(() => {


  // start request


  return () => {
    // cleanup
  };


}, []);

The cleanup runs when the component unmounts.

So:

Component mounts
    ↓
Effect runs
    ↓
Request starts
    ↓
Component unmounts
    ↓
Cleanup runs
    ↓
abort()

# 41. How do you handle API errors globally?

API errors can be handled globally at both the backend and frontend levels.

BACKEND:
I use Express error-handling middleware. If an error occurs in a controller, I pass it using next(error). The global error middleware catches it, logs it, and sends a consistent response with the appropriate HTTP status code and message.

FRONTEND:
I usually create one common Axios instance and use a response interceptor to handle common API errors in one place, like 401 Unauthorized, 403 Forbidden, token expiration, or 500 Server Error. If an error is specific to a particular screen, I handle that separately in the component.

The overall flow is:

Frontend
    ↓
Axios Request
    ↓
Backend API
    ↓
Controller
    ↓
Error occurs
    ↓
next(error)
    ↓
Global Error Middleware
    ↓
HTTP Error Response
    ↓
Axios Interceptor
    ↓
Component-specific handling if required

42. How do you implement pagination in React?

Pagination means:

Instead of loading all records at once, load a limited number of records for a particular page.

Example:

Page 1 → users 1–10
Page 2 → users 11–20
Page 3 → users 21–30

This reduces the amount of data loaded and rendered at once.

Typical API

A backend might support:

GET /users?page=1&limit=10

Meaning:

page = 1
limit = 10 users
Complete React example
Folder structure
src/
├── components/
│   └── UserPagination.jsx
└── App.jsx
src/components/UserPagination.jsx
import { useEffect, useState } from "react";


function UserPagination() {
  const [users, setUsers] = useState([]);
  const [page, setPage] = useState(1);
  const [loading, setLoading] = useState(false);


  const limit = 10;


  useEffect(() => {
    async function fetchUsers() {
      try {
        setLoading(true);


        const response = await fetch(
          `https://api.example.com/users?page=${page}&limit=${limit}`
        );


        if (!response.ok) {
          throw new Error("Failed to fetch users");
        }


        const data = await response.json();


        setUsers(data);
      } catch (error) {
        console.error(error);
      } finally {
        setLoading(false);
      }
    }


    fetchUsers();
  }, [page]);


  return (
    <div>
      <h2>Users - Page {page}</h2>


      {loading ? (
        <p>Loading...</p>
      ) : (
        users.map((user) => (
          <p key={user.id}>{user.name}</p>
        ))
      )}


      <button
        disabled={page === 1 || loading}
        onClick={() => setPage(page - 1)}
      >
        Previous
      </button>


      <span> Page {page} </span>


      <button
        disabled={loading}
        onClick={() => setPage(page + 1)}
      >
        Next
      </button>
    </div>
  );
}


export default UserPagination;
Understand the important part

We have:

const [page, setPage] = useState(1);

And:

useEffect(() => {
   fetchUsers();
}, [page]);

So when:

setPage(2);

happens:

page changes
   ↓
useEffect runs again
   ↓
API request for page 2
   ↓
users updated
   ↓
UI updates

That's the basic pagination flow.

Backend responsibility

Pagination normally requires backend support.

For example:

GET /users?page=2&limit=10

Backend might return:

{
  "data": [
    ...
  ],
  "page": 2,
  "limit": 10,
  "totalPages": 10,
  "totalItems": 100
}

Then React can know whether to disable:

Next

when the last page is reached.

      ↓

43. How do you implement infinite scrolling in React?

Infinite scrolling means:

Instead of showing page buttons, we automatically load the next set of data when the user reaches near the bottom of the page.

Example:

Load page 1
     ↓
User scrolls
     ↓
Near bottom
     ↓
Load page 2
     ↓
Append page 2
     ↓
User continues
     ↓
Load page 3
Important difference from pagination

Pagination:

Page 1
[Next]
   ↓
Page 2 replaces Page 1

Infinite scrolling:

Page 1
   ↓
Page 2 appended
   ↓
Page 3 appended

So we normally do:

setUsers((previousUsers) => [
  ...previousUsers,
  ...newUsers
]);

rather than:

setUsers(newUsers);
Better way: Intersection Observer

Instead of manually listening to every scroll event, we can use the browser's Intersection Observer API.

The idea:

sentinel element
      ↓
comes into viewport
      ↓
load next page
Complete example

src/

import { useEffect, useRef, useState } from "react";


function InfiniteUsers() {
  const [users, setUsers] = useState([]);
  const [page, setPage] = useState(1);
  const [loading, setLoading] = useState(false);
  const [hasMore, setHasMore] = useState(true);


  const observerRef = useRef(null);


  useEffect(() => {
    async function fetchUsers() {
      if (loading || !hasMore) {
        return;
      }


      try {
        setLoading(true);


        const response = await fetch(
          `https://api.example.com/users?page=${page}&limit=10`
        );


        if (!response.ok) {
          throw new Error("Failed to fetch users");
        }


        const data = await response.json();


        setUsers((previousUsers) => [
          ...previousUsers,
          ...data.users,
        ]);


        if (data.users.length < 10) {
          setHasMore(false);

Pagination vs Infinite Scrolling
Pagination	Infinite Scrolling
User controls page navigation	Loading happens automatically
Usually replaces current list	Usually appends new items
Easy to navigate to a specific page	Harder to jump to a specific position
Good for tables/search results	Good for feeds/social media
Uses page controls	Often uses Intersection Observer
Cross-question: Why not use a scroll event for infinite scrolling?

You can.

For example:

window.addEventListener("scroll", ...)

But scroll events can fire very frequently.

You then often need throttling/debouncing and careful calculations.

Intersection Observer is usually cleaner:

Scroll event
→ continuously calculate position


Intersection Observer
→ browser tells us when element enters viewport
Cross-question: What problems can infinite scrolling have?

Important interview points:

1. Duplicate requests

If the observer fires multiple times:

page 2
page 2
page 2

You need:

if (loading) return;

or another guard.

2. No more data

You need:

hasMore

to stop requests.

3. Large DOM

If you keep adding thousands of items:

Page 1
Page 2
...
Page 100

the DOM can become huge.

For very large datasets, virtualization can help.
