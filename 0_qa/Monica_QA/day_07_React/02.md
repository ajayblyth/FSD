# 20. What is useLayoutEffect()?

useLayoutEffect() is a React Hook used for side effects that need to happen after React has updated the DOM but before the browser paints the updated screen. It's mainly useful when we need to measure or synchronously modify the DOM before the user sees it.

The key phrase is:

After DOM update, but before browser paint.

For example, suppose you need to measure an element's size:

const boxRef = useRef(null);


useLayoutEffect(() => {
  const height = boxRef.current.getBoundingClientRect().height;
  console.log(height);
}, []);

Here, React has already put the element into the DOM, so you can measure it before the browser paints the result.

# 21. useEffect() vs useLayoutEffect()

This is the important part.

useEffect()

Generally:

Render
  ↓
DOM updated
  ↓
Browser paints
  ↓
useEffect runs

useLayoutEffect()
Generally:

Render
  ↓
DOM updated
  ↓
useLayoutEffect runs
  ↓
Browser paints
----------------------------------
or
With useEffect
React updates DOM
       ↓
Browser paints
       ↓
User sees intermediate state 👀
       ↓
useEffect runs
       ↓
measure / modify DOM
       ↓
Browser paints again
       ↓
User sees final state

So you can get:

wrong UI → correct UI

very quickly, but potentially visibly.
That's called flickering.


So the main difference is timing.

useEffect	                                              useLayoutEffect
Runs after the browser has painted in the usual case	Runs before the browser paints
Doesn't block painting in the same way	                Can block painting
Preferred for most side effects                       	Used when DOM measurement/layout timing matters
API calls, subscriptions, logging, etc.	                Measuring DOM, preventing visual flicker

Example

Suppose you want to fetch data:

useEffect(() => {
  fetchUsers();
}, []);

Use useEffect.

You normally don't need:

useLayoutEffect(() => {
  fetchUsers();
}, []);
When would useLayoutEffect actually be useful?

Imagine a tooltip:

1. Render tooltip
2. Measure its position
3. Calculate where it should go
4. Position it
5. Browser paints

If you do this with useEffect, the browser may briefly show the tooltip in the wrong position before it gets corrected.

useLayoutEffect allows you to perform the measurement/update before the browser paints.

Interview answer

"useEffect is preferred for most side effects because it doesn't block the browser's paint. useLayoutEffect runs synchronously after the DOM has been updated but before the browser paints, so I would use it when I need to measure or modify the DOM and want to avoid visible flickering."

Cross-question

Q: Should we always use useLayoutEffect because it runs earlier?

No.

That's a common mistake.

useLayoutEffect can block the browser from painting, so unnecessary use can hurt performance.

→ useEffect


Need DOM measurement / visual adjustment before paint
→ useLayoutEffect

# 22. What is Context API?

Now we move to state/data sharing.

First, understand the problem.

Suppose:

<App>
   <Navbar>
      <UserMenu>
         <Profile>
            <Avatar />

And App has:

const user = {
  name: "Ajay"
};

But Avatar needs the user.

Without Context, you might do:

App
 ↓ user
Navbar
 ↓ user
UserMenu
 ↓ user
Profile
 ↓ user
Avatar

Even though Navbar, UserMenu, and Profile don't actually need the user.

This is called prop drilling.

Context solves this

Context lets you provide a value to a component tree so that components deeper in that tree can access it without manually passing the value through every intermediate component.

Conceptually:

Provider
   ↓
   ↓
   ↓
Consumer

example:

src/
│
├── context/
│   └── UserContext.jsx
│
├── components/
│   └── User.jsx
│
└── App.jsx


// 1. src/context/UserContext.jsx

import { createContext } from "react";

const UserContext = createContext();

export default UserContext;


// 2. src/components/User.jsx

import { useContext } from "react";
import UserContext from "../context/UserContext";

function User() {
  const user = useContext(UserContext);

  return <h2>Hello, {user.name}</h2>;
}

export default User;


// 3. src/App.jsx

import UserContext from "./context/UserContext";
import User from "./components/User";

function App() {
  const user = {
    name: "Ajay"
  };

  return (
    <UserContext.Provider value={user}>
      <User />
    </UserContext.Provider>
  );
}

export default App;


// Flow:
//
// UserContext.jsx
//      ↓
// createContext()
//      ↓
// App.jsx
//      ↓
// UserContext.Provider
//      ↓
// User.jsx
//      ↓
// useContext(UserContext)
//      ↓
// user.name


No need for:

App → Navbar → UserMenu → Profile → Avatar

to manually pass user.

The three things to understand
1. Create Context
const UserContext = createContext();
2. Provide a value
<UserContext.Provider value={user}>
   ...
</UserContext.Provider>
3. Consume the value
const user = useContext(UserContext);

That's the basic Context API.

Is Context API a state management library?

This is a common interview question.

Not exactly.

Context itself mainly provides a mechanism for sharing values across a component tree.

For example:

Theme
Logged-in user
Language
Configuration

You can combine Context with useState or useReducer to manage state.

For example:

const [user, setUser] = useState(null);


<UserContext.Provider value={{ user, setUser }}>

Now you have:

State management → useState
Sharing → Context

This distinction becomes important when comparing Context with Redux.

# 23. What are the disadvantages of Context API?



Context is useful, but it isn't a replacement for every state-management solution.

## 1. Unnecessary re-renders

Suppose:

<UserContext.Provider value={user}>

The context value changes.

Components consuming that context may re-render.

With a large application and frequently changing context values, this can become a performance concern.

## 2. Can become difficult to manage

Imagine your application has:

AuthContext
ThemeContext
CartContext
NotificationContext
ProductContext
SettingsContext

You can end up with lots of providers:

<AuthProvider>
  <ThemeProvider>
    <CartProvider>
      <NotificationProvider>
        <App />
      </NotificationProvider>
    </CartProvider>
  </ThemeProvider>
</AuthProvider>

This is sometimes called Provider Hell.

## 3. Not ideal for complex global state

If you have:

Users
Products
Cart
Orders
Filters
Notifications
Authentication
Async operations

with many actions and relationships, managing everything through Context can become difficult.

A dedicated state-management solution such as Redux Toolkit may provide better structure.

## 4. Context can make dependencies less obvious

With props:

<UserProfile user={user} />

you can immediately see:

This component needs user.

With Context:

function UserProfile() {
  const user = useContext(UserContext);
}

the dependency is hidden inside the component.

Not necessarily bad, but something to consider.

Cross-questioning
Q: Does Context eliminate props?

No.

You should still use props when data is being passed directly between related components.

Context is useful when many components at different levels need the same value.

Q: Is Context better than prop drilling in every situation?

No.

If you have:

Parent
 ↓
Child

and the child needs one value, just use props.

Context becomes useful when passing the same data through many intermediate levels becomes inconvenient.

Q: Can Context API manage state?

Context itself doesn't create or manage state.

You can combine it with:

useState()

or:

useReducer()

For example:

const [user, setUser] = useState(null);


<UserContext.Provider value={{ user, setUser }}>

So:

Context provides/shares the value; useState or useReducer manages the state.

Q: Why not use Context for everything?

A good interview answer:

"Context is great for relatively global values that don't change too frequently, such as theme or authentication information. For large and frequently changing application state, a dedicated state-management solution can provide better organization, debugging, and performance control."

So Context and Redux aren't simply two different ways of passing props.

# Redux & Redux Toolkit

## 1. WHAT IS REDUX?

Redux is a state management library used when an application has data that needs to be shared and managed by many components.

Instead of keeping that shared data separately inside different components, Redux keeps it in one central store.
Suppose several components need the same data:

Instead of managing the same shared data separately in different components, Redux keeps that shared state centrally.

Example:

{
  user: {...},
  cart: {...},
  products: [...]
}

Components can:

* read data from the Redux store
* dispatch actions
* receive updated state

# 2. WHY DO WE NEED REDUX?

React already has `useState` and Context API, so why Redux?

For small applications, local state or Context may be enough.

Redux becomes useful when:

* many components need the same state
* state is updated from many places
* application state becomes complex
* we want predictable state updates
* we want centralized state management

Example:

                    Redux Store
                        ↓
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
      Navbar          Products          Cart
        ↓               ↓               ↓
      user            products          items

All components can work with the same centralized state.

7. WHAT IS PAYLOAD?

8. WHAT IS A REDUCER?

A reducer is a function that determines how the Redux state should change when an action is dispatched.

Conceptually:

current state + action
          ↓
       reducer
          ↓
      new state

Example:

function counterReducer(state, action) {
  // decide how state should change
}

The reducer receives:

state

and returns the next state.

## 9. IMPORTANT REDUCER RULE — IMMUTABILITY

In Traditional Redux, we should not directly modify the existing state.

Do NOT do:

state.value = state.value + 1;

Instead:

return {
  ...state,
  value: state.value + 1
};

Why?
The main issue is that Redux relies on detecting whether the state changed by comparing object references.

Redux follows immutable state updates.

Instead of modifying the existing object, we create and return a new state object.

This becomes easier with Redux Toolkit because Redux Toolkit uses Immer internally.

# 20. CREATE REDUCER

File:

src/redux/reducers/counterReducer.js

Code:

import {
  INCREMENT,
  DECREMENT,
  INCREMENT_BY_AMOUNT
} from "../actions/counterActions";

const initialState = {

  value: 0

};

function counterReducer(state = initialState, action) {

  switch (action.type) {

    case INCREMENT:

      return {

        ...state,

        value: state.value + 1

      };

    case DECREMENT:

      return {

        ...state,

        value: state.value - 1

      };

    case INCREMENT_BY_AMOUNT:

      return {

        ...state,

        value: state.value + action.payload

      };

    default:

      return state;

  }

}

export default counterReducer;

# 34. WHY CAN WE WRITE state.value += 1?

You may notice:

Traditional Redux:

return {
  ...state,
  value: state.value + 1
};

RTK:

state.value += 1;

Why is this allowed?

Redux Toolkit uses **Immer** internally.

Immer lets us write code that looks like we are mutating the state, while internally it produces the required immutable update.

Therefore this:

state.value += 1;

is safe inside a Redux Toolkit reducer.

Important:

> This does NOT mean Redux has abandoned immutability.

The final Redux state update is still handled immutably.

# 30. Why does React sometimes re-render a component unnecessarily?

A component re-renders when its state changes, its props change, its parent re-renders, or a context value it consumes changes. Sometimes the component itself doesn't have any meaningful data change, but it still re-renders because its parent rendered again or because a new object, array, or function was created.

First, understand something important:

Re-render does NOT mean DOM update

Suppose:

function Counter() {
  const [count, setCount] = useState(0);


  console.log("Counter rendered");


  return <h1>{count}</h1>;
}

When:

setCount(1);

React runs the component again:

Counter function
      ↓
runs again
      ↓
new JSX
      ↓
React compares it with previous result
      ↓
only necessary DOM changes

So:

Re-render = React executes the component again.

It doesn't necessarily mean React changes the actual DOM.

Main reasons for re-rendering
1. State changes
const [count, setCount] = useState(0);


setCount(1);

The component re-renders.

That's expected.

2. Parent re-renders

This one is important.

function Parent() {
  const [count, setCount] = useState(0);


  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>


      <Child />
    </>
  );
}

When Parent re-renders:

Parent
  ↓
Child

By default, React may also re-render Child.

Even if Child doesn't use count.

3. Props change
<Child name="Ajay" />

If the prop changes:

<Child name="Rahul" />

Child needs to render again.

4. New object / array / function references

This is a very common interview topic.

Consider:

function Parent() {
  const user = {
    name: "Ajay"
  };


  return <Child user={user} />;
}

Every time Parent renders, this:

{
  name: "Ajay"
}

is a new object in memory.

Even though the contents look the same.

Render 2 → object B

React compares references:

object A !== object B

So React considers the prop changed.

Same issue with functions:

  console.log("clicked");
};

Every render creates a new function reference.

     ↓

# 33. What is debouncing in React?

Debouncing isn't actually a React-specific concept.

It's a JavaScript technique commonly used in React.

Interview answer

Debouncing delays function execution until a specified amount of time has passed since the last event. If another event happens before completion of time, the timer  will resets.

Classic example:

Search box

User types:

A
Aj
Aja
Ajay

Without debouncing:

A    → API call
Aj   → API call
Aja  → API call
Ajay → API call

That's 4 API calls.

With debouncing:

A
 ↓
wait


Aj
 ↓
reset timer


Aja
 ↓
reset timer


Ajay
 ↓
reset timer


User stops typing
 ↓
wait 500ms
 ↓
API call

Only one request.

Simple JavaScript debounce
function debounce(callback, delay) {
  let timer;


  return (...args) => {
    clearTimeout(timer);


    timer = setTimeout(() => {
      callback(...args);
    }, delay);
  };
}

The key idea:

clearTimeout(timer);

cancels the previous scheduled execution.

Then:

setTimeout(...)

creates a new one.

React example

A simple React implementation:

import { useEffect, useState } from "react";


function SearchBox() {
  const [search, setSearch] = useState("");
  const [debouncedSearch, setDebouncedSearch] = useState("");


  useEffect(() => {
    const timer = setTimeout(() => {
      setDebouncedSearch(search);
    }, 500);


    return () => {
      clearTimeout(timer);
    };
  }, [search]);


  useEffect(() => {
    if (!debouncedSearch) return;


    console.log("API call:", debouncedSearch);
  }, [debouncedSearch]);


  return (
    <input
      value={search}
      onChange={(e) => setSearch(e.target.value)}
      placeholder="Search..."
    />
  );
}


export default SearchBox;
What's happening?

Every time the user types:

search changes
     ↓
useEffect runs
     ↓
setTimeout starts

If they type again before 500ms:

cleanup runs
     ↓
clearTimeout()
     ↓
old timer cancelled
     ↓
new timer starts

When they stop typing:

500ms passes
     ↓
debouncedSearch changes
     ↓
API effect runs

# 34. What is throttling in React?

Throttling ensures that a function executes at most once within a specified time interval, even if the event keeps happening continuously.

The difference from debouncing is extremely important.

Debouncing

Wait until the activity stops.

Example:

Typing:


A → Aj → Aja → Ajay
                  ↓
              stop typing
                  ↓
               wait 500ms
                  ↓
               execute
Throttling

Execute at controlled intervals while the activity continues.

Imagine scrolling:

Scroll event
 ↓
execute


scroll
scroll
scroll
 ↓
wait


100ms
 ↓
execute


scroll
scroll
scroll
 ↓
wait


100ms
 ↓
execute

So:

Debounce
→ after activity stops


Throttle
→ periodically during activity
Real-world examples
Debouncing

Best for situations where you care about the final value:

Search input
Autocomplete
Form validation

Example:

User typing
     ↓
wait until typing stops
     ↓
API request
Throttling

Best for continuously firing events:

Window resize
Dragging

Example:

User scrolls continuously
        ↓
Run handler every 100ms

Good for search	Good for scrolling
Final action/value matters	Continuous updates matter
⭐ Very common interview question
"Give a real-world example of both."

Answer naturally:

"For debouncing, I would use a search box. I don't want to call the API for every keystroke, so I wait until the user stops typing for, say, 500 milliseconds. For throttling, I would use something like a scroll event, where I may want to run a function at most once every 100 milliseconds while the user is continuously scrolling."

#  35. What is Lazy Loading?

Lazy loading means loading a resource only when it is actually needed instead of loading everything upfront. In React, we commonly use lazy loading to load components only when the user needs them.

Imagine your application has:

App
├── Home
├── Products
├── Orders
├── Admin
├── Reports
└── Settings

Without lazy loading, the browser may need to download JavaScript for all these features during the initial application load.

But suppose the user only visits:

Home

Why download the Admin and Reports code immediately?

With lazy loading:

Initial load
   ↓
Home code


User opens Reports
   ↓
Reports code downloaded

So the initial load can be smaller.

Simple real-world analogy

# 36. What is Code Splitting in React?
Interview answer

Code splitting is the process of splitting a large JavaScript bundle into smaller chunks that can be loaded separately when needed. Lazy loading is one common way of triggering those chunks to load on demand.

This distinction is important.

Without code splitting

Imagine:

app.js
──────────────────────────────
Home
Products
Orders
Admin
Reports
Settings
──────────────────────────────

Everything is bundled together.

With code splitting
main.js
   │
   ├── Home chunk
   ├── Products chunk
   ├── Orders chunk
   ├── Admin chunk
   └── Reports chunk

The browser doesn't necessarily download all of those chunks immediately.

Code splitting vs Lazy Loading

They are related but not exactly the same thing.

Code splitting
→ Break application code into separate chunks.


Lazy loading
→ Load a particular chunk/resource only when needed.

Think:

Code splitting = divide


Lazy loading = load later
Why do we care?

Suppose your application has:

2 MB JavaScript

and the user only needs the Home page.

If everything is loaded immediately:

 ↓
Show application

With code splitting:

Download required initial code

Show Home

User opens Admin

Download Admin chunk

This can improve the initial loading experience.

# 37. What is React.lazy()?

React.lazy() is used to lazy-load components, and it enables component-level code splitting by importing the component only when it is needed.

Let's create a complete example.

Project structure

Suppose:

src/
│
├── App.jsx
├── main.jsx
│
└── pages/
    ├── Home.jsx
    └── About.jsx
src/pages/About.jsx
function About() {
  return (
    <div>
      <h1>About Page</h1>
      <p>This is the About page.</p>
    </div>
  );
}


export default About;

Now in:

src/App.jsx

Instead of:

import About from "./pages/About";

we can write:

import { lazy, Suspense } from "react";


const About = lazy(() => import("./pages/About"));


function App() {
  return (
    <div>
      <h1>My App</h1>
      <About />
    </div>
  );
}


export default App;

But there's a problem.

React needs something to display while About is being downloaded.

That's where Suspense comes in.

# 38. What is Suspense?

Suspense allows React to display fallback UI(temporary UI shown while something is loading.).
With React.lazy(), Suspense can show a loading UI while the lazy component's JavaScript chunk is being downloaded.

Complete example:

src/App.jsx
import { lazy, Suspense } from "react";


const About = lazy(() => import("./pages/About"));


function App() {
  return (
    <div>
      <h1>My App</h1>
      <Suspense fallback={<p>Loading About page...</p>}>
        <About />
      </Suspense>
    </div>
  );
}

Think:

lazy()
→ "Load this later."


Suspense
→ "What should I show while it loads?"
Cross-question: Can Suspense only be used with React.lazy()?

No.

This is an important modern React point.

Suspense is a broader React mechanism and can work with other Suspense-enabled features, including certain data-fetching mechanisms and framework features.

But for your current interview preparation, the most straightforward example is:

React.lazy()
+
Suspense

We'll encounter Suspense-based data fetching later in your list.

Cross-question: Is lazy loading always better?

Not necessarily.

If a tiny component is always needed immediately, splitting it into a separate chunk can add another network request without providing much benefit.

So the goal isn't:

"Lazy load everything."

The goal is:

Load important initial code first and defer code that isn't immediately needed.

Good candidates:

Admin pages
Reports
Large dashboards
Rarely visited routes
Heavy components
Route-level lazy loading

This is one of the most common practical uses.

Imagine:

Home
Products
Orders
Admin

You might lazy-load:

const Admin = lazy(() => import("./pages/Admin"));

Then:

<Suspense fallback={<p>Loading...</p>}>
  <Admin />
</Suspense>

So a normal user doesn't necessarily need to download the Admin page's code during initial loading.
