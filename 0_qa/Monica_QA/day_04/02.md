# NODE.JS

## 1. What is Node.js?

Node.js is a JavaScript runtime environment that allows us to run JavaScript outside the browser, mainly for server-side applications. It is built on Chrome’s V8 JavaScript engine and is mainly used to build backend applications such as REST APIs and real-time applications.”

“Its key features include a non-blocking I/O and asynchronous model, event-driven architecture, JavaScript execution, and a large npm ecosystem.”

“Why do we say Node.js is event-driven?”

You can say:

“Node.js follows an event-driven architecture where different operations can emit events, and we can register listeners that execute when those events occur. Node.js itself provides many event-based APIs, such as streams, HTTP servers, and sockets, and we can also create our own events using EventEmitter.”

That's a strong answer because it shows you understand that EventEmitter is part of the model, not the entire reason Node.js is called event-driven.

### What is a runtime environment?

A **runtime environment** is the environment that provides everything needed to **execute a program**.

For JavaScript, the runtime provides things like:

* A JavaScript engine to execute the code
* APIs for interacting with the environment
* Mechanisms for handling asynchronous operations

For example:

### Browser

The browser provides JavaScript with APIs such as:

document
window
localStorage
fetch()

### Node.js

Node.js provides APIs such as:

fs
os
http
process
Buffer
path

So JavaScript itself is the language, while **Node.js is an environment in which JavaScript can run**.

## Why was Node.js created?

Originally, JavaScript was mainly associated with browsers.

You could write:
console.log("Hello");


and the browser's JavaScript engine would execute it.

But JavaScript couldn't traditionally be used directly to build things like:

* Backend servers
* REST APIs
* File-processing applications
* Command-line tools
* Network services

Node.js made it possible to use JavaScript for these kinds of tasks.

For example, you can create an HTTP server:

const http = require("http");

const server = http.createServer((req, res) => {
    res.end("Hello from Node.js");
});

server.listen(3000);

Now JavaScript is running as a **server-side application**, not inside a webpage.

For example:

JavaScript
    ↓
Programming language

Node.js
    ↓
Runtime environment
    ↓
Executes JavaScript

# 2. What is the V8 Engine?


“V8 is a JavaScript engine developed by Google and used by Chrome and Node.js. It executes JavaScript code by compiling it into machine code that the computer can understand and run, which makes JavaScript execution fast and efficient.”

“The main tasks of V8 are parsing, compiling, and executing JavaScript, while Node.js provides additional runtime features and APIs such as the file system, networking, and timers.”


## What is a JavaScript engine?

A **JavaScript engine** is software that takes JavaScript code and executes it.

For example:

| Environment | JavaScript Engine |
| ----------- | ----------------- |
| Chrome      | V8                |
| Node.js     | V8                |
| Firefox     | SpiderMonkey      |
| Safari      | JavaScriptCore    |

So when you write:

const x = 10;
console.log(x);

something has to actually execute that JavaScript.

That is the job of the JavaScript engine.

## What does V8 actually do?

Suppose you write:

function add(a, b) {
    return a + b;
}

console.log(add(10, 20));

V8:

1. Reads/parses the JavaScript code.
2. Converts it into an internal representation.
3. Compiles and optimizes code as it executes.
4. Produces machine-level instructions that the CPU can execute.

You don't need to memorize the internal compiler architecture for a normal Node.js interview.

The key understanding is:

> **V8 is responsible for executing JavaScript; it is not responsible for providing all of Node.js's APIs.**

## Very important distinction: V8 vs Node.js

This is where interviewers may cross-question you.

Suppose you write:

const fs = require("fs");

fs.readFile("data.txt", callback);

Does V8 provide fs?

**No.**

V8 executes the JavaScript code.

Node.js provides the fs API.

Conceptually:

               Node.js
                 │
        ┌─────────┴──────────┐
        │                    │
       V8              Node.js APIs
        │                    │
JavaScript execution   fs, http, path,
                       process, streams...


So:

> **V8 = JavaScript execution engine**

> **Node.js = runtime built around V8 with additional APIs and infrastructure**

This distinction is extremely important.

# 3. What is the difference between Node.js and JavaScript?

### Interview-style answer

> **JavaScript is a programming language, whereas Node.js is a runtime environment that provides the ability to execute JavaScript outside the browser. Node.js uses the V8 engine to execute JavaScript and provides additional APIs for server-side and system-level operations.**

Let's break that down.

## JavaScript

JavaScript defines the language features and rules.

For example:

let name = "Ajay";

const numbers = [1, 2, 3];

function add(a, b) {
    return a + b;
}

const result = numbers.map(n => n * 2);

These are JavaScript language features.

## Node.js

Node.js gives JavaScript access to capabilities outside the language itself.

For example:

### File system

const fs = require("fs");

You can read files:

fs.readFile("data.txt", callback);

### HTTP

const http = require("http");

You can create a server:

http.createServer(...)

### Process

console.log(process.env.PORT);

### Operating system

const os = require("os");

console.log(os.cpus());

These capabilities come from the **Node.js runtime**, not from JavaScript itself.

# Browser JavaScript vs Node.js
“Initially, JavaScript was mainly used inside the browser to make web pages interactive—for example, handling button clicks, form events, changing the DOM. But JavaScript in the browser was limited to what the browser allowed it to do.”

“Node.js was introduced to take JavaScript outside the browser and use it for server-side development. It provides runtime APIs for things like file handling, networking, HTTP servers, and databases through libraries, along with the npm ecosystem. So today, browser JavaScript is mainly used on the client side, while Node.js allows us to use JavaScript on the backend as well.”

Browser JavaScript APIs vs Node.js APIs

“Both the browser and Node.js provide APIs, but they provide APIs for different environments and purposes. The browser provides APIs mainly for working with web pages and browser capabilities, such as the DOM API, Fetch API, Web Storage API, and browser events. Node.js provides APIs mainly for server-side and system-level operations, such as the File System API (fs), HTTP API, Streams, and the process API.”

“So the main difference is that browser JavaScript is mainly used to interact with the webpage and the browser, while Node.js provides APIs that allow JavaScript to work with things like files, servers, networking, and the operating system.”

Simple examples

Browser APIs:

DOM API          → manipulate HTML
Fetch API        → make HTTP requests
localStorage     → store data in browser
Browser Events   → click, submit, etc.

Node.js APIs:

fs               → work with files
http             → create HTTP servers
path             → work with file paths
process          → access process/runtime information
streams          → handle data efficiently

One small terminology point: fs is usually called the Node.js File System module/API, rather than “File System API” in the same standardized sense as browser APIs. For interviews, saying “Node.js fs module” is safest.

# 4. What are the main features of Node.js?

> **The main features of Node.js include its event-driven architecture, non-blocking I/O, asynchronous programming model, V8-based JavaScript execution, rich package ecosystem through npm & built-in APIs.**

Let's understand each rather than memorizing the list.

## 1. V8 JavaScript Engine

Node.js uses V8 to execute JavaScript.


JavaScript
    ↓
V8
    ↓
Machine-level execution

This provides fast JavaScript execution.

## 2. Event-driven architecture

Node.js heavily uses an **event-driven model**.

An **event** is something that happens that the application can respond to.

Examples:

User logged in
Data received
Request received


Node.js can register a function to respond when something happens.

For example:

server.on("request", () => {
    console.log("Request received");
});

This concept becomes much more important when we study **EventEmitter and the Event Loop**.

## 3. Non-blocking I/O

**I/O** means **Input/Output**.

Examples:

* Reading a file
* Sending a network request
* Communicating with a database

**Non-blocking** means Node.js doesn't normally stop the JavaScript execution flow and sit idle waiting for an I/O operation to finish.

Conceptually:


Start database request
        ↓
Don't sit waiting
        ↓
Continue other work
        ↓
Database finishes
        ↓
Handle the result

This is one of the major reasons Node.js is well suited to applications involving lots of network or I/O operations.

We'll study this deeply when we reach **non-blocking I/O and the Event Loop**.

## 4. Asynchronous programming

Node.js makes extensive use of asynchronous APIs.

For example:

fs.readFile("data.txt", (error, data) => {
    console.log(data);
});

The application can initiate the file operation and provide a callback to handle the result later.

Modern Node.js code can also use:

const data = await fs.promises.readFile("data.txt");

which uses the Promise-based API.

You've already learned the JavaScript foundation for this.

## 5. npm ecosystem

Node.js has access to **npm**, the Node.js package ecosystem and package manager.

This allows developers to install reusable packages.

For example:

npm install express

Then:

const express = require("express");

Instead of building everything from scratch, developers can use existing libraries.

## 6. Built-in modules/APIs

Node.js comes with many built-in modules.

Examples:

fs       → File system
http     → HTTP functionality
path     → File/directory paths
os       → Operating system information
events   → EventEmitter
crypto   → Cryptographic functionality
stream   → Streams

This means Node.js can perform many backend/system operations without requiring an external package for every task.

## 7. Cross-platform

Node.js applications can run on different operating systems, including:

* Windows
* Linux
* macOS

So the same Node.js application can generally be developed and deployed across different operating systems, subject to OS-specific behavior where applicable.

# 1. What is synchronous vs asynchronous code?

“Synchronous execution means the code runs one operation at a time, in sequence. We have to wait for the current operation to finish before moving to the next one. So if one operation takes a long time, it can block the execution of the code after it.”

“Asynchronous execution means we can start an operation that may take some time, such as a database query or file operation, without making the main JavaScript execution wait for it. Once the operation is completed, its result can be handled later through a callback, Promise, or async/await.”

### Synchronous

Imagine:


console.log("A");

const result = someOperation();

console.log("B");

Conceptually:


A
↓
someOperation()
↓
wait until it finishes
↓
B

The next statement cannot execute until `someOperation()` finishes.

---

## Asynchronous

For example:

console.log("A");

setTimeout(() => {
    console.log("B");
}, 2000);

console.log("C");

Output:


A
C
B

Why?

`setTimeout()` schedules a function to run later. JavaScript doesn't sit there for two seconds doing nothing.

Conceptually:


console.log("A")
       ↓
schedule timer
       ↓
console.log("C")
       ↓
later → callback executes
       ↓
console.log("B")

### Important distinction

Asynchronous does **not** mean:

> "JavaScript executes everything simultaneously."

JavaScript execution is still coordinated through the **Call Stack and Event Loop**.

It means:

> **An operation can be started, and its completion can be handled later instead of blocking the current execution flow.**

---

## Why is this important in Node.js?

Consider a backend server receiving requests:


Request 1 → Database query
Request 2 → API call
Request 3 → File operation
Request 4 → Database query

If Node.js synchronously waited for every I/O operation:


Request 1
   ↓
WAIT for database
   ↓
finish
   ↓
Request 2
   ↓
WAIT...

That would be inefficient for applications doing lots of I/O.

Node.js is designed to handle these operations asynchronously.

# 2. What is Non-Blocking I/O?

“Non-blocking I/O basically means that when Node.js starts an I/O operation, like reading a file, querying a database, or making a network request, it doesn't sit and wait for that operation to finish. It can continue doing other work, and once the I/O operation is completed, we can handle the result using a callback, Promise, or async/await.”

“The main advantage is that the JavaScript thread doesn't remain blocked while waiting for slower I/O operations, so Node.js can continue handling other requests efficiently.”

And if the interviewer asks “What exactly is I/O?”:

“I/O stands for Input/Output. In Node.js, it mainly refers to operations where we communicate with something outside the JavaScript execution itself, such as reading files, accessing a database, or communicating over a network.”


----
“JavaScript execution in Node.js is single-threaded, but Node.js can delegate I/O operations to the underlying operating system and runtime mechanisms. While that I/O is in progress, the JavaScript thread can continue executing other code. Once the operation completes, the Event Loop schedules the callback back for JavaScript execution.”
Examples:

* Reading a file
* Writing a file
* Database communication
* Sending an HTTP request
* Receiving network data

---

## Blocking I/O

Imagine:

const data = readFileSynchronously();
console.log(data);

console.log("Continue");

Conceptually:


Start reading file
       ↓
WAIT
↓
File finished
↓
Continue

The execution is blocked while waiting.

---

## Non-blocking I/O

Now imagine:

readFile("data.txt", (error, data) => {
    console.log(data);
});

console.log("Continue");

Conceptually:


Start file operation
       ↓
Don't wait here
       ↓
"Continue" can execute
       ↓
File finishes later
       ↓
Callback handles result

This is the key idea behind Node.js's I/O model.

---

## Very important interview clarification

**Non-blocking does not mean the file/database/network operation itself happens on the JavaScript thread without waiting.**

It means:

> **The JavaScript execution flow isn't blocked waiting for the I/O operation to complete.**

Node.js and its underlying runtime mechanisms coordinate with the operating system and **libuv** to handle asynchronous operations.

We'll come back to libuv when discussing the Event Loop in more detail.

# 3. What is Event-Driven Architecture?

“Event-driven architecture means that instead of continuously checking whether something has happened, the application reacts when an event occurs. We can register listeners for different events, and when an event is emitted or occurs, the corresponding listeners are executed.”

“Node.js follows this model heavily, especially for handling asynchronous operations. For example, when a request, file operation, or network operation completes, an event or callback can trigger the related code. We can also create our own events using EventEmitter when multiple parts of an application need to react to the same event.”

Let's understand the terms.

### Event

An **event** is something that happens.

For example:


HTTP request received
File finished reading
Database operation completed
Connection established
Data received

### Event handler / listener

A **listener** is a function that waits for a particular event and responds when it occurs.

Conceptually:


Event happens
     ↓
Listener/handler
     ↓
Execute response

---

## Simple example

server.on("request", () => {
    console.log("Request received");
});

Here:


"request"
↓
event

() => {...}
↓
listener

When the request event occurs, the listener executes.

This idea is heavily used throughout Node.js.

---

## Why is this useful?

Imagine a server handling thousands of requests.

Instead of having a separate blocking execution flow constantly waiting:


"Is there a request?"
"Is there a request?"
"Is there a request?"

the application can respond to events as they occur.

This fits naturally with Node.js's asynchronous, non-blocking architecture.

---

# Event Loop

“The Event Loop is basically what allows Node.js to handle asynchronous operations without blocking the main JavaScript thread. Since JavaScript runs on a single thread, when we start something like a database query or file operation, we don't want the JavaScript thread to just sit and wait for it. Node.js handles that operation separately, and once it's completed, the Event Loop makes sure the related callback gets a chance to run when the Call Stack is free.”

“So, in simple terms, the Event Loop keeps checking for work that is ready to be processed and coordinates when that work should go back to the JavaScript thread.”

---

# Call Stack
“The Call Stack is  where JavaScript keeps track of the functions that are currently being executed. Whenever we call a function, it gets added to the Call Stack, and once that function finishes, it is removed from the stack. Since JavaScript executes code on a single thread, the Call Stack handles one piece of JavaScript execution at a time.”

“For example, if one function calls another function, the second function is added on top of the first one. It has to finish before the first function can continue.”

JavaScript executes functions using a structure called the **Call Stack**.

Think of the Call Stack as the place where currently executing JavaScript functions are tracked.

For example:

function first() {
    second();
}

function second() {
    console.log("Hello");
}

first();

Execution conceptually looks like:


first()
↓
second()
↓
console.log()

The currently executing function is placed on the stack.

When it finishes, it is removed.

---

# 5. What is the Call Stack?

### Interview-style definition

> **The Call Stack is a data structure used by the JavaScript engine to keep track of function calls currently being executed. It follows the LIFO principle: Last In, First Out.**

### LIFO

**Last In, First Out** means the last function placed onto the stack is the first one to finish and be removed.

Example:


Call Stack

┌───────────────┐
│ second()      │ ← currently executing
├───────────────┤
│ first()       │
└───────────────┘

When `second()` finishes:


Call Stack

┌───────────────┐
│ first()       │
└───────────────┘

Then `first()` finishes.

---

# Now connect Call Stack with asynchronous code

Consider:

console.log("A");

setTimeout(() => {
    console.log("B");
}, 0);

console.log("C");

You might initially think:


A
B
C

But the output is:


A
C
B

Why?

Because `setTimeout()` doesn't simply put its callback directly onto the Call Stack.

Conceptually:


          JavaScript
              ↓
         Call Stack
              ↓
       setTimeout()
              ↓
   timer handled by runtime
              ↓
      callback waits
              ↓
         Event Loop
              ↓
         Call Stack
              ↓
      callback executes

This is where the Event Loop becomes important.

# 6. What is the Callback Queue?

### Interview-style definition

> **The Callback Queue is a queue where certain callbacks that are ready to run wait until the Call Stack is empty and the Event Loop can move them to the Call Stack.**

A **queue** generally follows:

> **FIFO — First In, First Out**

Think of people waiting in line.


First callback → gets served first
Second callback → gets served second

For example:

setTimeout(() => {
    console.log("Timer finished");
}, 0);

Once the timer is ready, its callback becomes eligible to be processed by the Event Loop.

Simplified model:


Timer completes
↓
Callback waits in queue
↓
Event Loop checks Call Stack
↓
Stack empty?
↓
Move callback to Call Stack
↓
Execute callback

---

“The Callback Queue is basically where callbacks from completed asynchronous operations wait until they are ready to be executed. For example, if we use a timer or an asynchronous I/O operation, once that operation is ready, its callback can be placed in a queue. The Event Loop then checks whether the Call Stack is free and, when it is, the callback gets moved to the Call Stack for execution.”

“So the important thing is that the callback doesn't execute directly from the queue. It waits there until the Event Loop can schedule it on the Call Stack.”

---

# 7. What is the Microtask Queue?

### Interview-style definition

> **The Microtask Queue is a queue that contains microtasks, such as Promise handlers, that are scheduled to run after the current JavaScript execution completes and before the Event Loop proceeds to ordinary asynchronous callbacks in the relevant scheduling cycle.**

The important examples are:


Promise.then()
Promise.catch()
Promise.finally()

These create **microtasks**.

---

## Example

console.log("A");

setTimeout(() => {
    console.log("B");
}, 0);

Promise.resolve().then(() => {
    console.log("C");
});

console.log("D");

Output:


A
D
C
B

Why?

First, normal synchronous JavaScript executes:


A
D

Then the Promise handler is processed as a microtask:


C

Then the timer callback can execute:


B

So:


Synchronous code
↓
Microtasks
↓
Timer/I/O callbacks

That's the simplified mental model you should remember.

---

## How everything connects

Now let's put all seven concepts together.

Consider:

console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");

### Step 1 — Synchronous execution

The Call Stack executes:


Start
End

### Step 2 — Promise microtask

The Promise handler goes into the **Microtask Queue**:


Promise

### Step 3 — Timer callback

The timer callback becomes eligible through Node's timer scheduling:


Timer

### Step 4 — Event Loop coordinates execution

The Event Loop ensures callbacks are moved into JavaScript execution when the appropriate conditions are met.

Result:


Start
End
Promise
Timer

 One crucial correction to a common misconception

Don't say this in an interview:

> ❌ "Node.js is asynchronous because it has multiple JavaScript threads running."

That's not the right explanation.

A better answer is:

> **Node.js executes JavaScript on a main thread and uses an event-driven, non-blocking architecture to handle asynchronous operations. The Event Loop coordinates when callbacks are executed, while the underlying runtime and operating system can handle I/O operations outside the JavaScript execution flow.**

There are additional threads involved in Node's underlying implementation for certain operations, but **you should not describe Node.js as simply "JavaScript running on multiple threads."**
