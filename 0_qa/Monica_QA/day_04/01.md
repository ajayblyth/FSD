
# CALLBACKS

## 1. What are Callbacks?
 As we know in js , the functions can be treated as values and passed as arguments in JavaScript. So, a callback is a function that we pass as an argument to another function, and in the receiving function, we can decide when to invoke that callback.”

“Callbacks are commonly used for both synchronous and asynchronous operations, but they became especially important in Node.js for handling asynchronous operations. But  as we use callbacks more and more for asynchronous operations, too many nested callbacks can create a problem called callback hell.”

 Very common in asynchronous programming, such as reading a file, making a network request, or querying a database.


Simple example
(synchronous)
function greet(name, callback) {
    console.log("Hello " + name);
    callback();
}

function sayBye() {
    console.log("Goodbye");
}

greet("Ajay", sayBye);


Output:

Hello Ajay
Goodbye


What's happening?

greet("Ajay", sayBye)
              ↑
        function passed
        as an argument

Inside greet():

callback();

is effectively calling:

sayBye();


So:

greet()
   ↓
prints Hello
   ↓
calls callback
   ↓
sayBye()


Important point

A callback does not automatically mean asynchronous.

Callback in asynchronous programming
------

This is where callbacks become particularly important in Node.js.

For example, conceptually:

readFile("data.txt", (error, data) => {  //readfile is an asynchronous function
    if (error) {
        console.log(error);
        return;
    }

    console.log(data);
});

Here we're saying:

"Start reading the file. When the operation finishes, execute this function."

The callback doesn't need to wait synchronously for the file operation.

Conceptually:

Start file operation
        ↓
JavaScript can continue doing other work
        ↓
File operation finishes
        ↓
Callback is executed


Why are callbacks useful?

Imagine you have an operation that takes time:

Database query
API request
File reading
Network communication

Instead of writing code that says:

"Stop everything and wait until this finishes."

you can provide a callback:

"When you're finished, call this function."

That allows asynchronous operations to be handled without blocking the current JavaScript execution flow.


## 2. What is Callback Hell?

Interview-style definition

Callback hell is a situation where multiple asynchronous operations are nested inside one another using callbacks, 
resulting in deeply nested code,which is difficult-to-read and difficult-to-maintain code.error handling is also becomes tricky here.

The important word here is nested.

Imagine:

getUser(userId, (user) => {
    getOrders(user.id, (orders) => {
        getOrderDetails(orders[0].id, (details) => {
            processPayment(details, (payment) => {
                sendConfirmation(payment, (result) => {
                    console.log("Completed");
                });
            });
        });
    });
});


Notice how every operation is inside the callback of the previous operation.

Visually:

getUser()
   ↓
getOrders()
   ↓
getOrderDetails()
   ↓
processPayment()
   ↓
sendConfirmation()


This is what people commonly call Callback Hell.

You may also hear the term:

Pyramid of Doom

because the indentation can start looking like a pyramid.


Why is callback hell a problem?

1. Readability becomes poor

Instead of reading code from top to bottom naturally, you have to keep moving deeper into nested functions.


2. Maintenance becomes difficult

Suppose you need to add another operation:

A → B → C → D → E → F

You may have to add another level of nesting.


3. Error handling becomes messy

Each asynchronous operation may have its own error:

getUser((err, user) => {
    if (err) {
        // handle error
    }

    getOrders(user, (err, orders) => {
        if (err) {
            // handle error
        }

        // ...
    });
});


As the nesting grows, error handling becomes harder to manage.


4. Code becomes tightly nested

Nesting means putting one piece of code inside another.

Deep nesting makes the structure harder to understand and modify.


## 3. How can you avoid Callback Hell?

There isn't just one solution.

The main approaches are:

1. Use named functions

Instead of putting everything inside anonymous callbacks:

getUser((user) => {
    getOrders(user, (orders) => {
        // ...
    });
});


you can separate the functions:

function handleUser(user) {
    getOrders(user, handleOrders);
}

function handleOrders(orders) {
    console.log(orders);
}

getUser(handleUser);


This reduces nesting.

However, for modern JavaScript, there is a more important solution.

2. Use Promises

Instead of:

getUser((user) => {
    getOrders(user, (orders) => {
        getOrderDetails(orders, (details) => {
            console.log(details);
        });
    });
});


we can represent the asynchronous operations using Promises:

getUser()
    .then(user => getOrders(user))
    .then(orders => getOrderDetails(orders))
    .then(details => {
        console.log(details);
    })
    .catch(error => {
        console.log(error);
    });


The nesting is significantly reduced.

A Promise is an object representing the eventual result of an asynchronous operation. 

3. Use async/await

Modern JavaScript can make the same flow look much more sequential:

async function process() {
    const user = await getUser();
    const orders = await getOrders(user);
    const details = await getOrderDetails(orders);

    console.log(details);
}


Instead of:

callback
    ↓
callback
    ↓
callback
    ↓
callback


you can write:

get user
    ↓
get orders
    ↓
get details


This is one of the main reasons async/await is widely preferred for writing readable asynchronous code.


The progression you should remember

Don't memorize these as three unrelated interview questions.

Understand the evolution:

Callbacks
    ↓
Useful for asynchronous operations
    ↓
Multiple dependent operations
    ↓
Nested callbacks
    ↓
Callback Hell
    ↓
Promises
    ↓
async/await


For example, imagine:

Get user
    ↓
Get user's orders
    ↓
Get order details
    ↓
Make payment


With callbacks:

getUser()
    ↓
getOrders()
    ↓
getDetails()
    ↓
makePayment()


If each operation depends on the previous one, callbacks can become deeply nested.

Promises flatten that structure, and async/await makes the sequential flow even easier to read.


Interview answer you can give

If the interviewer asks "What is callback hell and how do you avoid it?", a strong answer would be:

Callback hell occurs when multiple asynchronous operations are dependent on each other and their callbacks become deeply nested. This makes the code difficult to read, maintain, and handle errors in. We can reduce callback hell by using named functions, but in modern JavaScript we generally use Promises and async/await because they provide a cleaner way to handle asynchronous control flow.

# PROMISES & ASYNC/AWAIT

## 4. What are Promises?

“A Promise is an object that represents the eventual result of an asynchronous operation. Basically, when we have an operation whose result we’ll get sometime later, we use a Promise to represent that result. It can either be pending fulfilled when successful or rejected when something goes wrong.”

“The main advantage of Promises over callbacks is that Promises make asynchronous code easier to manage, especially when we have multiple operations that depend on each other. We can use multiple .then() calls to handle successful results while keeping the code flat, and one .catch() which can handle errors from the chain.”

## Why do we need Promises?
because of the callback hell issue which we face with the callbacks.

Suppose we have:

getUser((user) => {
    getOrders(user, (orders) => {
        getOrderDetails(orders, (details) => {
            console.log(details);
        });
    });
});

The problem is **nested callbacks**.

Promises allow us to represent each asynchronous operation as a value that will eventually produce a result:

getUser()
    .then(user => getOrders(user))
    .then(orders => getOrderDetails(orders))
    .then(details => {
        console.log(details);
    });

The code is flatter and easier to manage.

## Promise States

A Promise has **three states**:
             ┌───────────────┐
             │    Pending    │
             └───────┬───────┘
                     │
             operation finishes
                /           \
               /             \
              ↓               ↓
       ┌────────────┐   ┌────────────┐
       │ Fulfilled  │   │  Rejected  │
       └────────────┘   └────────────┘

### 1. Pending

The operation is still in progress.


"Database query is still running..."

### 2. Fulfilled

The operation completed successfully.


"Database query completed and returned data."

### 3. Rejected

The operation failed.


"Database query failed."

Once a Promise becomes fulfilled or rejected, it is called **settled**.

## Creating a Promise

const promise = new Promise((resolve, reject) => {

    // asynchronous operation

});

`resolve` and `reject` are functions provided by JavaScript.

* `resolve(value)` → operation succeeded
* `reject(error)` → operation failed

Example:

const promise = new Promise((resolve, reject) => {

    const success = true;

    if (success) {
        resolve("Data received");
    } else {
        reject("Something went wrong");
    }

});

Now we can consume that Promise:

promise
    .then(result => {
        console.log(result);
    })
    .catch(error => {
        console.log(error);
    });

### What are `.then()` and `.catch()`?

* `.then()` handles a **fulfilled** Promise.
* `.catch()` handles a **rejected** Promise.

So:


resolve()
   ↓
.then()

reject()
   ↓
.catch()

## Important: A Promise itself doesn't make an operation asynchronous

This is a common misunderstanding.

A Promise is primarily a **mechanism for representing and handling an eventual result**.

For example:

const promise = new Promise((resolve) => {
    resolve("Hello");
});

There isn't necessarily any meaningful asynchronous work here.

Promises are commonly used with asynchronous operations, but **creating a Promise and performing asynchronous work are separate concepts**.

## 5. Promise vs Callback

Now that we understand Promises, the comparison becomes much easier.

## Interview-style answer

> **A callback is a function passed to another function to be executed later, whereas a Promise is an object representing the eventual success or failure of an asynchronous operation. Promises provide structured mechanisms such as** **`.then()`****,** **`.catch()`****, and** **`.finally()`** **and can be chained, which generally makes complex asynchronous code easier to manage than deeply nested callbacks.**

## Main difference

### Callback

The function is passed to the operation:

getUser((user) => {
    console.log(user);
});

You're essentially saying:

> "When you're done, call this function."

### Promise

The operation gives you a Promise:

const promise = getUser();

Then you decide how to handle its result:

promise.then(user => {
    console.log(user);
});

You're saying:

> "Give me an object representing the future result, and I'll decide how to handle it."

## Side-by-side

| Callback                             | Promise                                                   |
| ------------------------------------ | --------------------------------------------------------- |
| Function passed as an argument       | Object representing eventual result                       |
| Handler is called by the operation   | Result is handled using `.then()` / `.catch()`            |
| Can lead to deep nesting             | Supports chaining                                         |
| Error handling can become repetitive | `.catch()` provides a common rejection-handling mechanism |
| Composition can become difficult     | Easier to compose multiple async operations               |
| Older/common async pattern           | Modern standard pattern                                   |

### One important clarification

Promises did **not** make callbacks disappear.

Promises themselves use functions as handlers:

promise.then(result => {
    // callback-like function
});

So the difference isn't:

> "Callbacks are old and Promises don't use functions."

Rather:

> **Promises provide a structured abstraction for managing asynchronous results, while callbacks are simply functions supplied to be invoked later.**

That's a much stronger interview understanding.

# 6. What is async/await?

“Async and await are modern JavaScript features used to handle asynchronous operations. The async keyword before a function makes it always return a Promise, no matter what operation is performed inside it. And await pauses the execution of the async function until the Promise settles. It doesn't block the main thread; only the async function pauses at that point. Once the Promise settles, the function continues from the next line. This makes asynchronous code easier to read and understand compared to chaining multiple .then() calls.and one of the main advantages is that the code looks clean & more like synchronous code while still working asynchronously.””

“We generally use try...catch with async/await to handle errors,
There are two separate keywords:

async
await

Let's understand them individually.

## `async`

When you put `async` before a function:

async function getData() {
}

that function **always returns a Promise**.

For example:

async function getData() {
    return "Hello";
}

Even though we returned a normal string:

return "Hello";

the actual result of calling the function is a Promise:

const result = getData();

console.log(result);

Conceptually:


getData()
   ↓
Promise
   ↓
"Hello"

This is important:

> **An** **`async`** **function always returns a Promise.**

 `await`

`await` is used to wait for a Promise's result **inside an async function**.

For example:

async function getData() {
    const result = await getUser();

    console.log(result);
}

Conceptually:

getUser()
    ↓
returns Promise
    ↓
await
    ↓
when Promise settles successfully
    ↓
result available

Compare this:

### Promise chaining

getUser()
    .then(user => {
        console.log(user);
    });

### async/await

async function getData() {
    const user = await getUser();

    console.log(user);
}

Both are working with a Promise.

`async/await` doesn't replace Promises.

> **`async/await`** **is built on top of Promises.**

That's one of the most important points to remember.

## Does `await` block Node.js?

This is a very common interview question.

**No,** **`await`** **does not block the Node.js thread in the traditional sense.**

Consider:

async function getData() {
    const data = await fetchData();

    console.log(data);
}

console.log("A");

getData();

console.log("B");

The `await` tells the async function:

> "Pause this async function until the Promise settles."

It does **not** mean:

> "Freeze the entire JavaScript runtime."

Other work can continue while the asynchronous operation is in progress.

Conceptually:

async function
      ↓
    await
      ↓
function pauses here
      ↓
other JavaScript work can continue
      ↓
Promise settles
      ↓
async function resumes

This distinction is extremely useful in interviews.

# 7. How does error handling work with async/await?

“For error handling with async/await, we generally use try...catch. We put the code that can reject or throw an error inside the try block, and if an error occurs, the control moves to the catch block where we can handle that error.”

“For example, if an awaited Promise gets rejected, the await expression throws that error, and the catch block can handle it.”

async function getUser() {
    try {
        const response = await fetchUser();
        console.log(response);
    } catch (error) {
        console.log("Failed to fetch user:", error.message);
    }
}

Interview point to remember: try...catch is not mandatory for every async/await function. We use it when we want to handle the error at that point. Otherwise, the rejected Promise can be propagated to the caller.

 Why does `try...catch` work with `await`?
-----

Suppose:

const user = await fetchUser();

If `fetchUser()` returns a rejected Promise, the `await` expression effectively causes the rejection to be thrown at that point within the async function.

Therefore:

try {
    const user = await fetchUser();
} catch (error) {
    // handle rejection
}

can catch that failure.

This is why `try...catch` is the standard error-handling pattern with `async/await`.

# advantage over promise / Multiple asynchronous operations 
“The main advantage of async/await over Promise chaining is readability. It makes asynchronous code look more like synchronous code, so when we have multiple dependent operations, the flow is easier to read and understand.”

“Error handling is also more straightforward because we can use a normal try...catch block instead of chaining .catch(). It also makes debugging and maintaining complex asynchronous flows easier.”

This is where `async/await` becomes particularly useful.

Suppose:

Get user
   ↓
Get orders
   ↓
Get order details

With Promise chaining:

getUser()
    .then(user => getOrders(user))
    .then(orders => getOrderDetails(orders))
    .then(details => {
        console.log(details);
    })
    .catch(error => {
        console.log(error);
    });

With `async/await`:

async function processOrder() {

    try {
        const user = await getUser();
        const orders = await getOrders(user);
        const details = await getOrderDetails(orders);

        console.log(details);

    } catch (error) {
        console.log("Error:", error);
    }
}

Notice the major advantage:

The code visually follows the actual business flow:


get user
   ↓
get orders
   ↓
get details

while still being asynchronous.

## Another important interview point: rejected Promise

Consider:

async function getData() {
    return await fetchData();
}

If `fetchData()` rejects and there is no `try...catch` inside `getData()`, then `getData()` itself returns a **rejected Promise**.

So the caller can handle it:

getData()
    .catch(error => {
        console.log(error);
    });

Or:

async function main() {

    try {
        const data = await getData();
        console.log(data);
    } catch (error) {
        console.log(error);
    }

}

This is important because **error handling doesn't necessarily have to happen inside the same function where the error originates**. The rejection can propagate to the caller.

> **Callbacks are a way of receiving a result later; Promises provide a structured representation of that future result; and** **`async/await`** **provides cleaner syntax for consuming those Promises.**

# Interview-ready answers

### What is a Promise?

> A Promise is a JavaScript object that represents the eventual result of an asynchronous operation. It can be pending, fulfilled, or rejected, and we can handle the result using methods such as `.then()`, `.catch()`, and `.finally()`.

### Promise vs callback?

> A callback is a function passed to another function to be executed later, whereas a Promise represents the eventual result of an asynchronous operation. Promises provide better support for chaining and structured error handling, which helps avoid deeply nested callback code.

### What is async/await?

> `async/await` is syntax built on top of Promises that allows asynchronous code to be written in a sequential-looking and more readable manner. An `async` function always returns a Promise, and `await` pauses the execution of that async function until the Promise settles without blocking the entire JavaScript runtime.

### How do you handle errors with async/await?

> We commonly use `try...catch` around `await` expressions. If the awaited Promise is rejected, the error can be caught by the `catch` block. If the error isn't handled there, the async function returns a rejected Promise, which the caller can handle.

## One distinction you should be able to explain confidently

If an interviewer asks:

**"Are async/await an alternative to Promises?"**

Don't say simply **yes**.

Say:

> **No.** **`async/await`** **is built on top of Promises. It provides a cleaner syntax for consuming and handling Promise-based asynchronous operations.**
