# 16. Conditional Rendering


> **"Conditional rendering in React means displaying different UI based on a condition. We can use normal JavaScript conditions like** **`if`****, ternary operators, or logical AND inside JSX."**

For example, if a user is logged in, show their profile; otherwise, show a login button.

### Using `if`

function App() {
const isLoggedIn = true;

if (isLoggedIn) {
return \<h2>Welcome back!\</h2>;
  }

return \<h2>Please log in\</h2>;
}

---

### Using ternary operator

Very common inside JSX:

function App() {
const isLoggedIn = true;

return (
\<div>
      {isLoggedIn ? \<h2>Welcome\</h2> : \<h2>Please Login\</h2>}
\</div>
  );
}

Think:

condition ? ifTrue : ifFalse

---

### Using `&&`

Useful when we only want to show something if a condition is true.

{isLoggedIn && <button>Logout</button>}

Meaning:

> If `isLoggedIn` is true, show the button.

---

### Important interview point

Conditional rendering is **not a special React feature**. React uses normal JavaScript logic to decide what JSX should be returned.

# 17. Why are Keys Used When Rendering Lists?

### Interview-style introduction

> **"Keys are unique identifiers that React uses when rendering lists. they are used for identification.
 They help React identify which items were added, removed, or changed, so it can efficiently update the UI."**

Suppose we have:

const users = [
  { id: 1, name: "Ajay" },
  { id: 2, name: "Rahul" },
  { id: 3, name: "Amit" }
];

We render them:

function UserList() {
return (
\<div>
      {users.map(user => (
\<div key={user.id}>
          {user.name}
\</div>
      ))}
\</div>
  );
}

Here:

key={user.id}

gives each element a stable identity.

---

## Why does React need this?

Imagine:

Before:
1 → Ajay
2 → Rahul
3 → Amit

Then Rahul is removed:

After:
1 → Ajay
3 → Amit

The keys help React understand:

> "The item with key 2 was removed. Items 1 and 3 are existing items."

Without stable keys, React has a harder time efficiently matching list items.

---

## Why shouldn't we normally use array index?

You might see:

users.map((user, index) => (
\<div key={index}>{user.name}\</div>
));

This works in some simple static lists, but it's not ideal when the list can be:

* reordered
* inserted into
* deleted from

Because the index can change.

Prefer:

key={user.id}

when you have a stable unique ID.

### Important interview point

Keys should be:

> **Unique among sibling elements and stable across renders.**

Also, `key` is used by React internally; it is **not automatically available as a normal prop** inside the child component.

# 18. Controlled vs Uncontrolled Components

This is especially important when dealing with **forms**.

### Interview-style introduction

> **"“The main difference is where the current value of the input/form field is stored and controlled. In a controlled component, React state is the source of truth for the input value. In an uncontrolled component, the DOM itself manages the value, and we typically access it using a ref."**

“Source of truth” simply means:
The place where the actual, current value is stored and controlled.
---

## Controlled Component

Example:

import { useState } from "react";

function Form() {

const [name, setName] = useState("");

return (
\<input
value={name}
onChange={(e) => setName(e.target.value)}
/>
  );
}

Here:

User types
↓
onChange
↓
setName()
↓
React state changes
↓
Input gets new value

So React state controls the input.

That's why it's called a **controlled component**.

### Why is this useful?

Because React always knows the current value.
Use them when React needs to know and control the input value while the user is typing.
We can easily:
Show character count
* validate input
* enable/disable buttons
* conditionally display UI
* submit state data
* manipulate the value

---

# Uncontrolled Component

Here the DOM maintains the value.

import { useRef } from "react";

function Form() {
const inputRef = useRef();

const handleSubmit = () => {
console.log(inputRef.current.value);
  };

return (
<>
\<input ref={inputRef} />
\<button onClick={handleSubmit}>
        Submit
\</button>
\</>
  );
}

Here we aren't doing:

value={name}
onChange={...}

Instead, the DOM stores the value and we access it using:

inputRef.current.value

Use them when you don't need React to track the value on every keystroke.
This can be simpler for basic forms where you only need the values at submission.
Which one is more commonly used?

In normal React applications, controlled components are generally more common, especially when the form has validation, 
dynamic behavior, or the UI needs to react to input changes.

Uncontrolled components are still useful when:

The form is simple
You don't need to track every change
You mainly need the value on submit
You want less React state management
You're working with certain DOM-oriented integrations
---

## Controlled vs Uncontrolled

| ControlledUncontrolled       |                              |
| ---------------------------- | ---------------------------- |
| React state controls value   | DOM controls value           |
| Uses `value` + `onChange`    | Often uses `ref`             |
| React is the source of truth | DOM is the source of truth   |
| Easier validation/control    | Simpler for some basic cases |
| Common in React forms        | Useful in certain situations |

### Interview answer

If asked which one you generally prefer:

> "For most React forms, I prefer controlled components because the form state stays inside React, which makes validation and conditional logic easier to manage."

# 19. What is Lifting State Up?

> **"Lifting state up means moving state from a child component to their closest common parent when multiple child components need to share or modify the same data."**

This is another very important React data-flow concept.

---

## The problem

Suppose we have:

          App
         /   \
      Input   Display

`Input` changes some data.

`Display` needs to show that data.

If the state is inside `Input`, `Display` can't directly access it.

So we move the state to their common parent:

          App
         /   \
      Input   Display

Now:

App
│
├── state
│
├── Input
│     ↑
│   callback
│
└── Display
      ↑
     data

---

## Example

Parent:

function App() {
const [name, setName] = useState("");

return (
<>
\<Input name={name} setName={setName} /> //parent passing setName as prop to input
\<Display name={name} />
\</>
  );
}

Input:

function Input({ name, setName }) {
return (
\<input
value={name}
onChange={(e) => setName(e.target.value)}
/>
  );
}

Display:

function Display({ name }) {
return \<h2>Hello {name}\</h2>;
}

Now the parent owns the state:

             App
          state: name
           /      \
          ↓        ↓
       Input     Display
          ↓
      setName()

---

# Lifting State Up vs Prop Drilling

These two can sound similar, so keep the distinction clear.

### Lifting State Up

It's about:

> **Where should the state live so multiple components can share it?**

We move state **up to a common parent**.

### Prop Drilling

It's about:

> **Passing props through multiple levels of components just to reach a deeply nested component.**

So:

Lifting State Up
→ Move state to common parent

while:

Prop Drilling
→ Passing props through unnecessary intermediate components

---

## One Important React Data Flow Rule

At this point, remember this:

        Parent
        /    \
      Child  Child

**Data normally flows down:**

Parent
↓
Props
↓
Child

But a child can communicate with the parent by receiving a **callback function as a prop**:

Parent
↓ callback
Child
↓ calls callback
Parent state changes
↓
Parent re-renders
↓
New props flow down

This pattern is extremely common in React.
