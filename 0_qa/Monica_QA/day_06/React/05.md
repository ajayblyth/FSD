# 23. What is React Router?


> **"React Router is a library which we use to handle client-side routing in React applications. We use it to display different components /pages based on the URL without doing a full browser reload."**

For example:

/              → Home
/products      → Products
/about         → About
/login         → Login
/profile       → Profile

In a traditional multi-page application, navigating to another page can involve requesting another HTML document from the server.

In a React SPA, React Router lets us change the displayed component while the application continues running in the browser.
SPA = Single Page Application.

## Basic routing

import { BrowserRouter, Routes, Route } from "react-router-dom";

function App() {
return (
\<BrowserRouter>
\<Routes>
\<Route path="/" element={\<Home />} />
\<Route path="/products" element={\<Products />} />
\<Route path="/login" element={\<Login />} />
\</Routes>
\</BrowserRouter>
  );
}

Now:

/          → Home
/products  → Products
/login     → Login

---

## Navigation

We normally use `Link` rather than a normal `<a>` for internal React routes.

import { Link } from "react-router-dom";

function Navbar() {
return (
\<nav>
\<Link to="/">Home\</Link>
\<Link to="/products">Products\</Link>
\<Link to="/login">Login\</Link>
\</nav>
  );
}
why link?:
Because a normal <a> tag usually causes a full browser reload, while React Router's <Link> changes the URL and lets React handle the navigation without reloading the whole page.

---

## Dynamic Routes

Suppose we want:

/products/101
/products/102
/products/103

We can define:

\<Route path="/products/:id" element={\<ProductDetails />} />

Then inside the component:

import { useParams } from "react-router-dom";

function ProductDetails() {
const { id } = useParams();

return \<h2>Product ID: {id}\</h2>;
}

If we visit:

/products/101

then:

id

will be:

101

# 24. How do you call an API in React?

### Interview-style introduction

> **"In React, I usually call APIs inside useEffect when the request is triggered by a component lifecycle or dependency change. I manage the RESPONSE using state and generally keep SEPARATE loading and error states so the UI can represent each STAGE."**

1. What is "component lifecycle"?

It basically means the different stages a component goes through:

Component created/mounted
        ↓
Component updates
        ↓
Component removed/unmounted

For API calls, we commonly mean:

When the component first appears on the screen.

A common pattern is:
Component
↓
useEffect
↓
API request
↓
setState
↓
Re-render
↓
Display data

---

## Example

import { useEffect, useState } from "react";

function Users() {
const [users, setUsers] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(false);

useEffect(() => {
fetch("[https://jsonplaceholder.typicode.com/users](https://jsonplaceholder.typicode.com/users)")
.then(response => {
if (!response.ok) {
throw new Error("Failed to fetch");
}

return response.json();
      })
.then(data => {
setUsers(data);
      })
.catch(() => {
setError(true);
      })
.finally(() => {
setLoading(false);
      });
  }, []);

if (loading) {
return \<p>Loading...\</p>;
  }

if (error) {
return \<p>Something went wrong\</p>;
  }

return (
\<div>
      {users.map(user => (
\<p key={user.id}>{user.name}\</p>
      ))}
\</div>
  );
}

---

## Why use `useEffect`?

We don't want to make the API call directly in the component body:

function Users() {
fetch(...); // ❌
return ...;
}

Because the component function can execute again during re-renders, which could cause repeated requests.

Instead:

useEffect(() => {
fetch(...);
}, []);

The dependency array controls when that effect runs.

---

## Typical API states

When making an API request, we commonly have:

Loading
↓
Request
↓
┌───────────────┐
↓               ↓
Success         Error
↓               ↓
Data            Error message

So React applications commonly maintain:

const [data, setData] = useState([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState(null);

---

## `async/await` version

You can also write:

useEffect(() => {
const fetchUsers = async () => {
try {
setLoading(true);

const response = await fetch(
"[https://jsonplaceholder.typicode.com/users](https://jsonplaceholder.typicode.com/users)"
);

if (!response.ok) {
throw new Error("Request failed");
}

const data = await response.json();

setUsers(data);

    } catch (error) {
setError(error.message);
    } finally {
setLoading(false);
    }
  };

fetchUsers();

}, []);

This is often easier to read in real projects.

# Authentication and Protected Routes

"In a React application, I usually handle authentication by sending the user's credentials to the backend and receiving a token or session. I store the authentication state, often using Context if multiple components need it, and use a ProtectedRoute to control access to protected pages. If the user is authenticated, I allow access; otherwise, I redirect them to the login page. The backend is responsible for validating the credentials and token and enforcing actual authorization."
---

## Basic Authentication Flow

User enters email/password
        ↓
React sends login request to backend
        ↓
Backend validates credentials
        ↓
Backend returns token/session
        ↓
React stores authentication information
        ↓
React considers user authenticated
        ↓
User can access protected routes

For JWT-based authentication:

Login → JWT token → Authentication state → Protected routes → Authenticated API requests

# Protected Routes

Suppose our application has:

/public

But:

/dashboard

should only be accessible to authenticated users.

We can create a reusable `ProtectedRoute` component.

│   └── ProtectedRoute.jsx
├── pages/
│   ├── Login.jsx

## Basic ProtectedRoute

import { Navigate } from "react-router-dom";

function ProtectedRoute({ isAuthenticated, children }) {
  if (!isAuthenticated) {
    return <Navigate to="/login" replace />;
  }

  return children;
}

export default ProtectedRoute;

### How does this work?

If the user tries to access:

/dashboard

React Router renders `ProtectedRoute`.

It checks:

Is user authenticated?

       /       \
     Yes        No
      ↓          ↓
 Dashboard     /login

If authenticated:

return children;

`children` means the component placed inside `ProtectedRoute`.

For example:

<ProtectedRoute>
  <Dashboard />
</ProtectedRoute>

Here:

children = <Dashboard />

So the dashboard is displayed.

If the user isn't authenticated:

return <Navigate to="/login" replace />;

The user is redirected to the login page.

---

# Using ProtectedRoute with React Router

<Route
  path="/dashboard"
  element={
    <ProtectedRoute isAuthenticated={isAuthenticated}>
      <Dashboard />
    </ProtectedRoute>
  }
/>

This means:

> **When the user visits `/dashboard`, first check authentication. If authenticated, show `Dashboard`; otherwise, redirect to `/login`.**

---

# Where does `isAuthenticated` come from?

In a real application, we don't want to manually pass:

isAuthenticated

through many components.

This is where **Context** becomes useful.

We can create an `AuthContext`:

const [user, setUser] = useState(null);

For example:

user = null → Not logged in

user = { id: 1, name: "Ajay" } → Logged in

Components can access this authentication state using:

const { user } = useContext(AuthContext);

So our concepts connect like this:

useState → Store authentication state
useContext → Share authentication state across components
React Router → Handle navigation and routes
ProtectedRoute → Check authentication before showing protected pages

# Important: Authentication vs Authorization

These are related but different.

### Authentication

> **"Who are you?"**

Example:

User logs in
→ Backend verifies email/password
→ User is authenticated

### Authorization

> **"What are you allowed to access?"**

For example:

Admin → /admin
User  → /profile

The frontend can hide or protect routes based on roles, but **the backend must enforce real authorization**.

A user should not be able to access protected data simply by bypassing a React route check.

# Authentication vs Authorization

This is a **very common interview question**.

### Authentication

> **"Authentication verifies who the user is."**

Example:

Email + Password
↓
Who are you?

### Authorization

> **"Authorization determines what an authenticated user is allowed to access or do."**

Example:

Admin → Can delete users
User  → Cannot delete users

So:

Authentication
→ Who are you?

Authorization
→ What are you allowed to do?

---

# One Important Security Point

Don't say in an interview:

> "The frontend protects the API."

It doesn't.

A React protected route only protects the **frontend navigation/UI experience**.

A user could still manually call your API.

The backend must independently verify authentication and authorization.

So:

React
→ controls UI/routes

Backend
→ actually protects APIs/data

That's an excellent interview point.
