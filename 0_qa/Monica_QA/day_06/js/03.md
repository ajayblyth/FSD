# 1. JSON.stringify()

JSON.stringify() converts a JavaScript value, usually an object or array, into a JSON string.

In simple words:

JavaScript Object → JSON String

Example:

const user = {
    name: "Ajay",
    age: 25
};

const jsonString = JSON.stringify(user);

console.log(jsonString);

Output:

{"name":"Ajay","age":25}

Notice that jsonString is now a string, not an object.

console.log(typeof jsonString);
// "string"


## Why do we use JSON.stringify()?

It is commonly used when we need to send JavaScript data to a server or store it as JSON.

For example, when sending data using fetch():

fetch("/users", {
    method: "POST",
    headers: {
        "Content-Type": "application/json"
    },
    body: JSON.stringify(user)
});

Here, the JavaScript object is converted into a JSON string before being sent to the backend.

JSON is a text-based data format, so objects need to be converted into JSON before sending them as request data.


## Interview answer

If the interviewer asks "What is JSON.stringify()?", you can say:

"JSON.stringify() converts a JavaScript value into a JSON string. It is commonly used when sending JavaScript objects to a backend API or when storing structured data as JSON. After stringify(), the result is a string, not a JavaScript object."


------------------------------------------------------------

# 2. JSON.parse()

JSON.parse() does the opposite of JSON.stringify().

It converts a valid JSON string into a JavaScript value.

In simple words:

JSON String → JavaScript Object


Example:

const jsonString = '{"name":"Ajay","age":25}';

const user = JSON.parse(jsonString);

console.log(user.name);

Output:

Ajay

Now user is a JavaScript object.

console.log(typeof user);
// "object"


## Why do we use JSON.parse()?

It is commonly used when we receive JSON data as a string and need to work with it as a JavaScript object.

For example:

const jsonString = '{"name":"Ajay","age":25}';

const user = JSON.parse(jsonString);

console.log(user.name);
console.log(user.age);

After parsing, we can access properties normally using JavaScript object syntax.


## Interview answer

"JSON.parse() converts a valid JSON string into a JavaScript value, usually an object or array. It is commonly used when receiving JSON data and we need to work with that data inside JavaScript."


------------------------------------------------------------

## 3. JSON.stringify() vs JSON.parse()

Remember this flow:

JavaScript Object
      ↓
JSON.stringify()
      ↓
JSON String
      ↓
JSON.parse()
      ↓
JavaScript Object


Example:

const user = {
    name: "Ajay",
    age: 25
};

const json = JSON.stringify(user);

console.log(typeof json);
// string

const result = JSON.parse(json);

console.log(typeof result);
// object


## Easy way to remember

stringify():

Object → String

parse():

String → Object


## Interview answer

"The main difference is that JSON.stringify() converts a JavaScript value into a JSON string, while JSON.parse() converts a valid JSON string back into a JavaScript value."


------------------------------------------------------------

## 4. Limitations of JSON

JSON is designed mainly for data interchange, so it supports a limited set of data types.

It does not preserve every JavaScript type.

This is important when using:

JSON.parse(JSON.stringify(object))

as a deep-copy technique.


## Functions are not preserved

Example:

const user = {
    name: "Ajay",
    greet: function () {
        console.log("Hello");
    }
};

const result = JSON.stringify(user);

console.log(result);

Output:

{"name":"Ajay"}

The function is omitted.

So JSON.stringify() cannot preserve functions.


------------------------------------------------------------

## 5. undefined and JSON

undefined behaves differently depending on whether it is inside an object or an array.


## undefined inside an object

const user = {
    name: "Ajay",
    age: undefined
};

console.log(JSON.stringify(user));

Output:

{"name":"Ajay"}

The age property is removed.

So:

undefined object property
        ↓
property is omitted


## undefined inside an array

const arr = [1, undefined, 3];

console.log(JSON.stringify(arr));

Output:

[1,null,3]

Here undefined is converted to null.

So remember:

Object:
undefined → property omitted

Array:
undefined → null


------------------------------------------------------------

## 6. Date and JSON

Date objects are not preserved as Date objects during normal JSON serialization.

Example:

const obj = {
    date: new Date()
};

const result = JSON.stringify(obj);

The Date is represented as a string in the JSON output.

When we parse it:

const parsed = JSON.parse(result);

console.log(typeof parsed.date);
// "string"

It does not automatically become a Date object again.

If we need a Date object, we have to create one again:

const date = new Date(parsed.date);


## Interview point

"JSON serialization converts Date values into strings. After JSON.parse(), the value remains a string, so if I need a Date object, I have to explicitly create a new Date from that string."


------------------------------------------------------------

# 7. Map and Set with JSON

JSON does not have native representations for JavaScript Map and Set.

For example:

const data = {
    numbers: new Set([1, 2, 3])
};

console.log(JSON.stringify(data));

The Set is not preserved as a Set.

This means:

JSON is not a general-purpose serialization or deep-cloning mechanism for every JavaScript data type.


------------------------------------------------------------

# 8. Circular References

JSON cannot directly serialize circular references.

Example:

const user = {
    name: "Ajay"
};

user.self = user;

Now:

user.self
   ↓
user

The object refers back to itself.

If we try:

JSON.stringify(user);

JavaScript throws:

TypeError

because JSON cannot represent this circular structure directly.


## Interview answer

"JSON.stringify() cannot serialize circular references because JSON doesn't have a direct representation for an object that refers back to itself."


------------------------------------------------------------

# 9. JSON.parse(JSON.stringify()) for Deep Copy

You may have seen this:

const copy = JSON.parse(JSON.stringify(user));

This is often used as a simple deep-copy technique.

Example:

const user = {
    name: "Ajay",
    address: {
        city: "Bangalore"
    }
};

const copy = JSON.parse(JSON.stringify(user));

copy.address.city = "Delhi";

console.log(user.address.city);

Output:

Bangalore

The nested object was copied, so changing the nested property in copy doesn't affect user.


## But there is an important limitation

This technique only works reliably for simple JSON-compatible data.

It can lose or change:

- Functions
- undefined
- Date objects
- Map
- Set
- Other special JavaScript types

It also fails with circular references.


## Interview answer

"JSON.parse(JSON.stringify()) can be used as a simple deep-copy technique for JSON-compatible data, but it is not suitable for arbitrary JavaScript objects because some values are lost or converted during JSON serialization."


------------------------------------------------------------

# 10. structuredClone()


structuredClone() is a modern JavaScript API used to create a deep clone of many supported JavaScript values.

Unlike a shallow copy, nested objects are also cloned.

Example:

const user = {
    name: "Ajay",
    address: {
        city: "Bangalore"
    }
};

const copy = structuredClone(user);

copy.address.city = "Delhi";

console.log(user.address.city);

Output:

Bangalore


## Why is this a deep clone?

The nested address object is also copied.

Conceptually:

Original:

user
 ↓
address object

Copy:

copy
 ↓
new address object

So user.address and copy.address are different objects.


------------------------------------------------------------

## structuredClone() vs Object.assign()

Object.assign() creates a shallow copy.

Example:

const user = {
    name: "Ajay",
    address: {
        city: "Bangalore"
    }
};

const copy = Object.assign({}, user);

copy.address.city = "Delhi";

console.log(user.address.city);

Output:

Delhi

Why?

Because the nested address object is still shared.

Both objects point to the same nested object.

With structuredClone():

const copy = structuredClone(user);

copy.address.city = "Delhi";

console.log(user.address.city);

Output:

Bangalore

Because the nested object is also cloned.


------------------------------------------------------------

## structuredClone() Supports More Types

One major advantage of structuredClone() is that it can preserve many built-in JavaScript types.

Example:

const data = {
    date: new Date(),
    numbers: new Set([1, 2, 3])
};

const copy = structuredClone(data);

console.log(copy.date instanceof Date);
// true

console.log(copy.numbers instanceof Set);
// true

The Date remains a Date.

The Set remains a Set.


------------------------------------------------------------

##. structuredClone() Supports Circular References

Unlike JSON.stringify(), structuredClone() can clone supported circular structures.

Example:

const user = {
    name: "Ajay"
};

user.self = user;

const copy = structuredClone(user);

console.log(copy.self === copy);

Output:

true

The circular relationship is preserved.


------------------------------------------------------------

## 14. Important structuredClone() Limitation

Do not say:

"structuredClone() can clone everything."

It cannot clone every JavaScript value.

For example, functions cannot be cloned.

const obj = {
    greet: () => console.log("Hello")
};

structuredClone(obj);

This throws:

DataCloneError


## Interview-safe answer

"structuredClone() provides deep cloning for many structured-clone-supported JavaScript values, but it doesn't support every JavaScript value, such as functions."


------------------------------------------------------------

## 15. JSON Copy vs structuredClone()

JSON copy:

const copy = JSON.parse(JSON.stringify(user));

structuredClone():

const copy = structuredClone(user);


Comparison:

Feature                    JSON Copy                  structuredClone()
---------------------------------------------------------------------------
Deep copy                  Yes, for JSON data         Yes, for supported values
Functions                 Not preserved              Not supported
undefined                 Not preserved in objects   Preserved
Date                      Becomes string              Preserved as Date
Map                       Not preserved               Preserved
Set                       Not preserved               Preserved
Circular references       Not supported               Supported
Special JS types          Limited                     Much broader


------------------------------------------------------------

## 16. Important Interview Question

Question:

"What is the difference between JSON.parse/stringify and structuredClone()?"


Interview answer:

"JSON.stringify() converts a JavaScript value into a JSON string, and JSON.parse() converts a valid JSON string back into a JavaScript value. JSON is mainly designed for data interchange, so it has limitations with values like functions, undefined, Date, Map, Set, and circular references.

structuredClone() is designed specifically for cloning JavaScript values. It performs a deep clone for many supported types and can preserve values such as Date, Map, and Set, and it also supports circular structures. However, it still cannot clone every JavaScript value, such as functions."


------------------------------------------------------------

## 17. Practical Use

Use JSON.stringify() when:

- Sending JSON data to a backend
- Storing JSON-compatible data
- Converting an object into a JSON string


Use JSON.parse() when:

- Receiving JSON strings
- Reading JSON-compatible data from storage
- Converting JSON text into a JavaScript value


Use structuredClone() when:

- You need a deep copy
- Your object contains nested objects
- You need to preserve supported types such as Date, Map, and Set
- Your data may contain circular references


------------------------------------------------------------

## Mental Model

JSON.stringify()
Object → JSON string

JSON.parse()
JSON string → JavaScript value

JSON.parse(JSON.stringify())
JSON-compatible data → Deep copy

structuredClone()
JavaScript value → Deep clone of supported values


## Final Interview Takeaway

The most important thing to remember is:

JSON.stringify() and JSON.parse() are mainly for JSON serialization and deserialization.

structuredClone() is mainly for deep cloning.

So if the interviewer asks:

"Would you use JSON.parse(JSON.stringify()) for every deep-copy requirement?"

Answer:

"No. It works for simple JSON-compatible data, but it can lose or transform values such as functions, undefined, Date, Map, and Set, and it cannot handle circular references. For a proper deep clone of supported JavaScript values, I would prefer structuredClone()."

# 12. Memory Management

Memory management explains how JavaScript allocates memory for data, how unused memory is reclaimed, and how memory leaks can happen.

For interviews, the three main concepts are:

1. Stack vs Heap
2. Garbage Collection
3. Memory Leaks


# 1. Stack vs Heap

JavaScript needs memory to store variables, function calls, objects, and other data.

For interview purposes, we commonly explain this using Stack and Heap.

Important:
The ECMAScript specification does not define JavaScript's exact memory layout as "stack vs heap". JavaScript engines such as V8 are free to optimize how values are stored.

So, treat Stack vs Heap as a conceptual model.


## Stack

The call stack is used to manage function execution.

When a function is called, its execution context is added to the call stack.

Example:

function add(a, b) {
    const result = a + b;
    return result;
}

add(10, 20);


Conceptually:

Call Stack

┌─────────────┐
│ add()       │
├─────────────┤
│ Global      │
└─────────────┘

When add() finishes, its execution is removed from the call stack.

Interview explanation:

"The call stack is used to manage function execution. When a function is called, its execution context is added to the stack, and when the function finishes, it is removed."


# 2. Heap

The heap is commonly used to describe dynamically allocated memory, especially for objects.

Example:

const user = {
    name: "Ajay",
    age: 25
};


Conceptually:

Stack                     Heap

user ─────────────────→  {
                            name: "Ajay",
                            age: 25
                          }


The variable user provides access to the object.

Important interview clarification:

Don't simply say:

"All primitives are stored in stack and all objects are stored in heap."

That's an oversimplification.

A better interview explanation is:

"Conceptually, the call stack manages function execution, while objects are generally allocated in dynamically managed memory commonly referred to as the heap. The actual implementation depends on the JavaScript engine."


# 3. Garbage Collection


JavaScript automatically manages memory using Garbage Collection (GC).

Unlike languages such as C or C++, we normally don't manually free memory.

The basic idea is:

"If an object is no longer reachable by the application, the JavaScript engine can eventually reclaim its memory."


Example:

let user = {
    name: "Ajay"
};

user = null;


Initially:

user ─────→ { name: "Ajay" }


After:

user = null;


Conceptually:

user → null

{ name: "Ajay" }  ← unreachable


The object is now eligible for garbage collection.

Important:

"Eligible for garbage collection" does NOT mean the object is immediately deleted.

The JavaScript engine decides when and how garbage collection runs.


## 4. Reachability

JavaScript garbage collection is generally based on reachability.

The engine starts from certain roots, such as:

- Global objects
- Currently executing function contexts
- Other engine-managed roots

It follows references from these roots.

If an object cannot be reached from those roots, it can eventually be collected.


Example:

let user = {
    name: "Ajay"
};

let another = user;

user = null;


Does the object become garbage immediately?

No.

Because:

another ─────→ { name: "Ajay" }


There is still a reachable reference.

Only after:

another = null;


and assuming there are no other references to the object, does the object become unreachable and eligible for garbage collection.


## 5. Memory Leak

A memory leak happens when an application unnecessarily keeps references to data that it no longer needs.

Because the object is still reachable, the garbage collector cannot reclaim it.

Example:

const users = [];

function addUser(user) {
    users.push(user);
}


If users keeps growing forever and old data is never removed, memory usage can continuously increase.

The important idea is:

Object is no longer needed
        ↓
Still referenced
        ↓
Still reachable
        ↓
GC cannot reclaim it
        ↓
Memory usage can increase


## 6. Common Causes of Memory Leaks


## 1. Accidental Global References

Example:

function test() {
    data = new Array(1000000);
}


In sloppy mode, accidentally creating a global variable like this can keep a large object alive.

Using strict mode helps catch this type of mistake.

"use strict";


## 2. Event Listeners

Example:

const button = document.querySelector("button");

function handleClick() {
    console.log("Clicked");
}

button.addEventListener("click", handleClick);


If listeners are repeatedly created and are no longer needed, they should be cleaned up when appropriate.

For example:

button.removeEventListener("click", handleClick);


Important:

The same function reference must be used when removing the listener.

button.addEventListener("click", handleClick);

button.removeEventListener("click", handleClick);


The exact leak behavior depends on what other references exist, but proper cleanup is important in long-lived applications.


## 3. Timers

Example:

const id = setInterval(() => {
    console.log("Running");
}, 1000);


If the interval is no longer required, clear it:

clearInterval(id);


If an interval is left running unnecessarily, it continues executing and can keep related resources or references alive.


## 4. Closures

Closures themselves are NOT memory leaks.

However, a closure can keep data reachable for as long as the closure itself remains reachable.

Example:

function createHandler() {
    const largeData = new Array(1000000);

    return function () {
        console.log(largeData.length);
    };
}

const handler = createHandler();


As long as handler is reachable, the closure may keep largeData reachable as well.

So don't say:

"Closures cause memory leaks."

A better interview answer is:

"Closures don't inherently cause memory leaks, but a long-lived closure can retain references to large objects for longer than necessary, which can contribute to memory retention."


##7. Garbage Collection vs Memory Leak

Don't confuse these two concepts.


Garbage Collection:

JavaScript automatically identifies objects that are no longer reachable and can reclaim their memory.


Memory Leak:

The application unintentionally keeps objects reachable even though they are no longer needed.


So:

Object no longer needed
        ↓
Still referenced accidentally
        ↓
Still reachable
        ↓
GC cannot reclaim it
        ↓
Memory usage increases


## Interview Answer

If the interviewer asks:

"How does memory management work in JavaScript?"

You can say:

"JavaScript automatically manages memory. Conceptually, function execution is managed through the call stack, while objects are generally allocated in dynamically managed heap memory. The JavaScript engine uses garbage collection to reclaim memory from objects that are no longer reachable. A memory leak happens when the application unintentionally keeps references to objects that are no longer needed, for example through long-lived arrays, event listeners, timers, or closures."


## Important Cross-Question

Interviewer:
"Can we manually trigger garbage collection?"


Answer:

"Normally, JavaScript applications don't control garbage collection directly. The engine decides when to perform it. Some JavaScript runtimes provide special debugging or runtime options for forcing or exposing GC, but normal application code shouldn't depend on that."


## Important Cross-Questions


Q: Does setting an object to null immediately free its memory?

Answer:

"No. Setting it to null only removes that particular reference. If other references to the object exist, it is still reachable. Even after it becomes unreachable, garbage collection may not happen immediately."


Q: Are closures memory leaks?

Answer:

"No. Closures are a normal JavaScript feature. However, a long-lived closure can keep references to large data alive for longer than necessary, which can contribute to memory retention."


Q: Who manages garbage collection?

Answer:

"The JavaScript engine manages garbage collection automatically. Developers normally don't manually allocate and free memory."


Q: What is the difference between stack and heap?

Answer:

"The call stack primarily manages function execution and execution contexts, while the heap is commonly used for dynamically allocated objects and data. The exact implementation depends on the JavaScript engine."


## Mental Model

Stack
→ function execution
→ call stack
→ execution contexts

Heap
→ dynamically allocated objects/data

Garbage Collection
→ identifies unreachable objects
→ eventually reclaims their memory

Memory Leak
→ object is no longer needed
→ but still referenced
→ remains reachable
→ GC cannot reclaim it

# 13. Event Propagation

Event propagation explains how an event travels through the DOM when we interact with an element.

For example, if a button is inside a div and we click the button, the event travels through the DOM hierarchy.

The three important phases are:

1. Capturing
2. Target
3. Bubbling


## 1. Event Propagation Phases

Suppose we have:

<div id="parent">
    <button id="child">Click Me</button>
</div>

When we click the button, the event travels roughly like this:

Window
  ↓
Document
  ↓
html
  ↓
body
  ↓
div (parent)
  ↓
button (target)
  ↑
div (parent)
  ↑
body
  ↑
html
  ↑
Document

So the overall flow is:

1. Capturing phase
       ↓
2. Target phase
       ↓
3. Bubbling phase
       ↑


# 2. Event Capturing

During capturing, the event travels from the outer ancestor elements towards the target element.

Example:

parent.addEventListener("click", () => {
    console.log("Parent");
}, true);

child.addEventListener("click", () => {
    console.log("Child");
});

The true means that the parent listener should run during the capturing phase.

When the button is clicked:

Parent
Child

The event reaches the parent during capturing before reaching the button.

### Interview answer

Event capturing is the phase where an event travels from the outer DOM elements towards the element that triggered the event. We can register a capturing listener by passing true as the third argument to addEventListener().


# 3. Event Bubbling

After reaching the target, the event normally travels back up through its ancestors.

Example:

parent.addEventListener("click", () => {
    console.log("Parent");
});

child.addEventListener("click", () => {
    console.log("Child");
});

Click the button:

Child
Parent

Why?

Because the event starts at the button and then bubbles up to the parent.

button
   ↑
parent
   ↑
body
   ↑
document

### Important

Many common DOM events, including click, bubble.

However, not every DOM event bubbles.

### Interview answer

Event bubbling is the phase where an event travels from the target element back up through its parent elements. It is the default behavior for many common DOM events and is commonly used for event delegation.


## 4. stopPropagation()

stopPropagation() prevents the event from continuing through the propagation path.

Example:

parent.addEventListener("click", () => {
    console.log("Parent");
});

child.addEventListener("click", (event) => {
    event.stopPropagation();
    console.log("Child");
});

When clicking the child:

Child

The parent does not execute because propagation was stopped.

### Important

stopPropagation() stops the event from moving to other elements in the propagation path.

However, other listeners attached to the same element may still execute.


## stopPropagation() vs stopImmediatePropagation()

This is a common interview cross-question.

### stopPropagation()

Stops the event from propagating to other elements.

But other listeners attached to the same element may still run.

### stopImmediatePropagation()

Stops propagation and also prevents other listeners on the same element from executing.

Example:

button.addEventListener("click", () => {
    console.log("First");
});

button.addEventListener("click", (event) => {
    event.stopImmediatePropagation();
    console.log("Second");
});

button.addEventListener("click", () => {
    console.log("Third");
});

Output:

First
Second

The Third listener does not execute because stopImmediatePropagation() stopped the remaining listeners on that element.

### Interview answer

stopPropagation() stops an event from propagating to other elements, while stopImmediatePropagation() also prevents other listeners on the same element from executing.


# 5. Event Delegation


Event delegation is very important in interviews and real applications.

Event delegation means:

Instead of adding event listeners to many child elements, we add one listener to a common parent and use event bubbling to determine which child triggered the event.

Example:

<ul id="users">
    <li>Ajay</li>
    <li>Rahul</li>
    <li>Vijay</li>
</ul>

Instead of adding a separate listener to every li, we can do:

const users = document.getElementById("users");

users.addEventListener("click", (event) => {
    if (event.target.tagName === "LI") {
        console.log(event.target.textContent);
    }
});

If we click:

Ajay

The output is:

Ajay

What happens internally?

The click occurs on the li:

li
 ↓
ul

The event bubbles from the li to the ul.

The ul has the event listener, so it handles the event and checks event.target to determine which li was clicked.


## Why use Event Delegation?

### 1. Fewer event listeners

Without event delegation:

1000 buttons
     ↓
1000 event listeners

With event delegation:

1000 buttons
     ↓
1 parent listener

This reduces the number of event listeners we need to manage.

### 2. Works with dynamically added elements

Suppose we add a new user:

users.innerHTML += "<li>New User</li>";

We don't necessarily need to attach another click listener to the newly added li.

Why?

Because the listener is already attached to the parent.

The new li can bubble its click event to the parent, and the parent listener can handle it.

### Interview answer

Event delegation is a technique where we attach one event listener to a parent instead of multiple child elements. Because events bubble, the parent can identify which child triggered the event using event.target. It is useful for reducing listeners and handling dynamically added elements.


## 6. event.target vs event.currentTarget

This is a very common interview question.

Consider:

parent.addEventListener("click", (event) => {
    console.log(event.target);
    console.log(event.currentTarget);
});

Suppose we click the child.

### event.target

event.target is the actual element that originally triggered the event.

event.target
     ↓
child

### event.currentTarget

event.currentTarget is the element whose event listener is currently executing.

event.currentTarget
     ↓
parent

So:

Click child

event.target
     ↓
child

event.currentTarget
     ↓
parent


### Easy way to remember

target
→ Who actually triggered the event?

currentTarget
→ Whose listener is currently running?

This distinction is especially useful in event delegation.


## 7. Capturing vs Bubbling

Capturing:
    Outer → Inner
    Happens before the target
    addEventListener(..., true)
    Less commonly used

Bubbling:
    Inner → Outer
    Happens after the target
    Default for events that support bubbling
    Very commonly used


## Interview Answer

If asked "What is event propagation?", you can say:

Event propagation is the process by which an event travels through the DOM. It has three phases: capturing, target, and bubbling. During capturing, the event travels from the outer ancestor towards the target element. At the target phase, it reaches the element that triggered the event. Then, during bubbling, it travels back up through the parent elements. We can control propagation using methods like stopPropagation(). Event delegation uses bubbling by placing a single listener on a parent and handling events from its child elements.


## Important Cross-Questions

### What is event bubbling?

Event bubbling means an event starts at the target element and then propagates upward through its parent elements.

### What is event capturing?

Event capturing means the event travels from the outer ancestor elements down toward the target element.

### How do you stop propagation?

event.stopPropagation();

### How do you stop other listeners on the same element?

event.stopImmediatePropagation();

### What is event delegation?

Event delegation means attaching one listener to a parent and using event bubbling and event.target to handle events from its children.

### Difference between target and currentTarget?

event.target is the element that originally triggered the event, while event.currentTarget is the element whose listener is currently executing.
