# 1. Execution Context

**High-priority topic** because it connects directly to **hoisting, scope, `this`, closures, and the call stack**.

## What is Execution Context?

Basically, **execution context is the environment in which JavaScript executes code**. It contains the information JavaScript needs to run that code, such as **variables/functions, scope information, the value of `this`, and references to the outer environment**.

Think of it as a **workspace created by JavaScript for executing code**.

## Types of Execution Context

There are mainly **two types we care about**:

### 1. Global Execution Context

Created when JavaScript starts executing a script.

var name = "Ajay";

function greet() {
    console.log("Hello");
}

console.log(name);

Before executing this code, JavaScript creates the **Global Execution Context**. It handles global-level variables and functions.

### 2. Function Execution Context

Every time a function is **called**, JavaScript creates a new Function Execution Context.

function add(a, b) {
    let result = a + b;
    return result;
}

add(10, 20);

When `add()` is called, JavaScript creates a separate execution context containing things like:

a = 10
b = 20
result = 30
this = ...

When the function finishes, its execution context is removed from the call stack.

## Creation Phase and Execution Phase

This is the important part for interviews.

When an execution context is created, JavaScript roughly goes through **two phases**:

### 1. Creation Phase

JavaScript prepares the environment before actually executing the code. It:

* Creates variables/functions in the environment
* Sets up scope relationships
* Determines the value of `this`
* Handles hoisting behavior

Example:

console.log(a);
var a = 10;

During the creation phase, `a` is created and initialized with:

undefined

So when execution reaches `console.log(a)`, it prints:

undefined

### 2. Execution Phase

Now JavaScript executes the code **line by line**.

var a = 10;
console.log(a);

During execution:

a = 10

Then `console.log(a)` prints:

10

## Function Example

var x = 10;

function add(a, b) {
    var result = a + b;
    return result;
}

var answer = add(5, 10);
console.log(answer);

### Step 1 — Global Execution Context

JavaScript creates the global context.

During creation:

x      → undefined
add    → function
answer → undefined

Then execution starts:

x = 10

When this line executes:

add(5, 10)

a **Function Execution Context** is created.

### Step 2 — Function Execution Context

For `add()`:

a      → 5
b      → 10
result → undefined

Then:

result = a + b;

So:

result → 15

Then:

return result;

returns `15`.

The function execution context is removed.

Finally:

answer = 15

## Execution Context and Call Stack

Execution contexts are managed using the **Call Stack**.

function one() {
    two();
}

function two() {
    console.log("Hello");
}

one();

The stack roughly becomes:

        ┌──────────────┐
        │ two()        │
        ├──────────────┤
        │ one()        │
        ├──────────────┤
        │ Global       │
        └──────────────┘

`two()` finishes → removed.
Then `one()` finishes → removed.
Finally, the global context remains until the script finishes.

## Interview Answer

If the interviewer asks **"What is Execution Context?"**, you can say:

> **Execution context is the environment in which JavaScript executes a piece of code. It contains information such as variables, functions, scope information, and the `this` value. JavaScript creates a global execution context when the script starts and creates a function execution context whenever a function is called. Each execution context goes through a creation phase, where the environment is prepared and hoisting-related setup happens, followed by an execution phase where the code actually runs. These contexts are managed using the call stack.**

### Very Important Connection

**Execution Context → Creation Phase → Hoisting → Execution Phase → Call Stack**
# 2. Lexical Environment

Closely related to **Execution Context, Scope, and Closures**, so understanding it properly is important for interviews.

## What is a Lexical Environment?

Basically, a **Lexical Environment is an internal structure that stores variables/functions and keeps a reference to its outer environment**.

In simple words:

> It tells JavaScript **what variables are available here** and **where to look if a variable is not found here**.

Example:

let name = "Ajay";

function greet() {
    let message = "Hello";
    console.log(name);
    console.log(message);
}

greet();

Inside `greet()`:

greet's Lexical Environment
    message → "Hello"
          ↓
Outer Lexical Environment
    name → "Ajay"

When JavaScript looks for `name` inside `greet()`:

1. It first checks the local environment.
2. `name` isn't there.
3. It goes to the outer environment.
4. Finds `name`.
5. Uses `"Ajay"`.

This is the basis of the **scope chain**.

## Lexical means "where the code is written"

let x = 10;

function test() {
    console.log(x);
}

test();

`test()` was **written inside the global scope**, so its outer environment is the global environment. Therefore, it can access `x`.

This is called **lexical scoping**.

It doesn't matter where the function is called from; what matters is **where the function was defined**.

## Lexical Environment and Scope

Think of them like this:

**Scope** = the rule that determines where a variable can be accessed.
**Lexical Environment** = the internal structure JavaScript uses to implement that scope.

Example:

let x = 10;

function outer() {
    let y = 20;

    function inner() {
        let z = 30;

        console.log(x);
        console.log(y);
        console.log(z);
    }

    inner();
}

outer();

For `inner()`:

inner environment
    z
     ↓
outer environment
    y
     ↓
global environment
    x

That's essentially the **scope chain**.

## Lexical Environment and Closures

This is where it becomes very important.

function outer() {
    let count = 0;

    function inner() {
        count++;
        console.log(count);
    }

    return inner;
}

const fn = outer();

fn();
fn();

Output:

1
2

Normally, you might think `count` should disappear after `outer()` finishes. But `inner()` still has access to `count`.

Why?

Because `inner()` **remembers the lexical environment in which it was created**.

That's a **closure**.

So the relationship is:

Lexical Environment
        ↓
Outer environment reference
        ↓
Scope chain
        ↓
Closures can preserve access to outer variables

We'll cover closures separately later, but this connection is important.

## Interview Answer

If the interviewer asks **"What is a Lexical Environment?"**, you can say:

> **A lexical environment is an internal JavaScript structure that stores variables and functions and maintains a reference to its outer lexical environment. JavaScript uses this relationship to implement lexical scoping and the scope chain. When a variable isn't found in the current environment, JavaScript looks in the outer environment. This mechanism is also important for understanding closures.**

## One Important Correction to Remember

Don't say:

> "Lexical environment is just scope."

That's not technically accurate.

Better:

> **Scope is the accessibility rule, while the lexical environment is the internal mechanism JavaScript uses to store bindings and connect them to their outer environment.**

## Connection So Far

Execution Context
       ↓
Lexical Environment
       ↓
Scope Chain
       ↓
Closures
# 3. Temporal Dead Zone (TDZ)

TDZ is important because it explains **why `let` and `const` behave differently from `var` before declaration**.

## What is TDZ?

Basically, the **Temporal Dead Zone is the period between entering a scope and the point where a `let` or `const` variable is declared/initialized, during which accessing that variable causes a `ReferenceError`.**

Example:

console.log(a); // ReferenceError

let a = 10;

Here, `a` already exists in the scope, but it **cannot be accessed yet**.

The time from entering the scope until:

let a = 10;

is the **Temporal Dead Zone**.

## Why does this happen?

Compare `var` and `let`:

### `var`

console.log(a);
var a = 10;

Output:

undefined

`var` is hoisted and initialized with `undefined`.

Conceptually:

var a = undefined;

console.log(a);

a = 10;

### `let`

console.log(a);
let a = 10;

Output:

ReferenceError

`let` is also **hoisted in the sense that its binding is created during scope setup**, but it is **not initialized with `undefined`**.

Until the declaration is evaluated, it remains in the **TDZ**.

## `const` behaves the same way

console.log(x);

const x = 20;

Result:

ReferenceError

And `const` must also be initialized at declaration:

const x; // SyntaxError

Because `const` requires an initial value.

## TDZ with a Block

A common interview example:

let x = 10;

{
    console.log(x);
    let x = 20;
}

What happens?

**ReferenceError.**

You might expect JavaScript to use the outer `x`, but it doesn't.

Inside the block, this declaration:

let x = 20;

creates a new block-scoped `x`.

Before that declaration is executed, the inner `x` is in its TDZ.

So JavaScript doesn't go to the outer `x`.

## Important: TDZ is about Execution, not simply "before the line"

let x = 10;

{
    let y = x;
    console.log(y);
}

This is perfectly valid because `x` is already initialized.

TDZ applies specifically to the `let`/`const` binding **before its initialization within its scope**.

## Interview Answer

If asked **"What is TDZ?"**, you can say:

> **Temporal Dead Zone is the period between entering a scope and the initialization of a `let` or `const` variable. During this period, the variable exists in the scope but cannot be accessed, and accessing it results in a ReferenceError. Unlike `var`, `let` and `const` are not initialized with `undefined` during the creation phase.**

## Common Cross-Question

**Interviewer:** Is `let` hoisted?

**Good answer:**

> **Yes, its binding is created during the creation phase, but it is not initialized. Until execution reaches its declaration, it remains in the Temporal Dead Zone. So although `let` is hoisted, we cannot access it before its declaration.**

That's the distinction interviewers usually want.

## Remember This

var
↓
Hoisted + initialized with undefined
↓
Can be accessed before declaration

let / const
↓
Binding created but not initialized
↓
TDZ
↓
Access before initialization → ReferenceError
# 4. Function Concepts

For a 3+ year interview, these four are important:

1. **First-class functions**
2. **Higher-order functions**
3. **IIFE**
4. **Function Declaration vs Function Expression**

---

## 1. First-Class Functions

In JavaScript, **functions are treated like values**.

That means you can:

* Store a function in a variable
* Pass a function as an argument
* Return a function from another function
* Store functions in objects/arrays

Example:

const greet = function () {
    console.log("Hello");
};

greet();

Here, the function is stored in the variable `greet`.

### Passing a function as an argument

function greet() {
    console.log("Hello");
}

function execute(fn) {
    fn();
}

execute(greet);

Here, `greet` is passed as a value to `execute()`.

### Returning a function

function outer() {
    return function () {
        console.log("Hello");
    };
}

const fn = outer();
fn();

So when we say **functions are first-class citizens**, we mean JavaScript allows functions to be handled like other values.

### Interview Answer

> **JavaScript treats functions as first-class citizens, which means functions can be assigned to variables, passed as arguments, returned from other functions, and stored in data structures like objects and arrays.**

---

# 2. Higher-Order Functions

A **higher-order function** is a function that **takes another function as an argument or returns a function**.

Example:

function calculate(a, b, operation) {
    return operation(a, b);
}

function add(x, y) {
    return x + y;
}

console.log(calculate(10, 20, add));

Here, `calculate()` is a **higher-order function** because it receives another function.

### Common Examples

JavaScript array methods are commonly higher-order functions:

numbers.map(...)
numbers.filter(...)
numbers.reduce(...)
numbers.forEach(...)

Example:

const numbers = [1, 2, 3, 4];

const result = numbers.map(function (num) {
    return num * 2;
});

`map()` receives a function, so `map()` is a higher-order function.

### First-Class vs Higher-Order

A common interview question.

**First-class function** = **language capability**

> JavaScript allows functions to be treated as values.

**Higher-order function** = **function that uses other functions**

> It accepts a function or returns a function.

First-class functions
        ↓
Functions can be treated as values

Higher-order functions
        ↓
A function takes/returns another function

---

# 3. IIFE

IIFE stands for:

**Immediately Invoked Function Expression**

It is a function that is **defined and executed immediately**.

Example:

(function () {
    console.log("Hello");
})();

Output:

Hello

Notice:

(function () {
    // function
})();

The final `()` immediately calls the function.

### Why was IIFE used?

Before modern JavaScript features like `let`, `const`, modules, etc., IIFEs were commonly used to create a **private scope** and avoid polluting the global scope.

Example:

(function () {
    const secret = "123";

    console.log(secret);
})();

console.log(secret); // ReferenceError

`secret` is available only inside the IIFE.

### Interview Answer

> **An IIFE is a function expression that is immediately invoked after it is created. It was commonly used to create an isolated scope and avoid global variables, especially before ES6 modules and block-scoped variables became common.**

---

## 4. Function Declaration vs Function Expression

### Function Declaration

function add(a, b) {
    return a + b;
}

The function is declared using the `function` keyword with a name.

Function declarations are **hoisted with their function definition**, so you can call them before the declaration:

add(10, 20);

function add(a, b) {
    return a + b;
}

This works.

### Function Expression

The function is assigned to a variable:

const add = function (a, b) {
    return a + b;
};

You normally cannot call it before the assignment:

add(10, 20); // ReferenceError

const add = function (a, b) {
    return a + b;
};

Why?

Because the variable `add` is created according to `const`'s rules and remains in the **TDZ** until initialization.

## Quick Comparison

| Feature    | Function Declaration             | Function Expression                       |
| ---------- | -------------------------------- | ----------------------------------------- |
| Syntax     | `function add(){}`               | `const add = function(){}`                |
| Named      | Usually yes                      | Can be named or anonymous                 |
| Hoisting   | Can be called before declaration | Cannot use before variable initialization |
| Common use | Normal reusable functions        | Callbacks, conditional assignment, etc.   |

---

## One Important Interview Point

Don't say:

> "Function expressions are not hoisted."

That's slightly misleading.

For:

const add = function () {};

the **`add` binding is created during scope setup**, but because it's `const`, it's in the **TDZ until initialization**.

So the safer interview answer is:

> **Function declarations are hoisted with their complete function definition, so they can be called before their declaration. A function expression is assigned to a variable, so its availability depends on how that variable is declared and initialized.**

---

## Remember the Whole Topic

First-class function
→ Function can be treated like a value

Higher-order function
→ Takes/returns another function

IIFE
→ Function defined and immediately executed

Function declaration
→ function add() {}
→ callable before declaration

Function expression
→ const add = function() {}
→ must be initialized before use
# 5. Objects

Objects are one of the most commonly used concepts in JavaScript, so for interviews you should understand not just the syntax, but **how properties are accessed and manipulated**.

## 1. Object Creation

An object is a collection of **key-value pairs**.

### Object Literal — Most Common

const user = {
    name: "Ajay",
    age: 25,
    city: "Bangalore"
};

Here:

name → "Ajay"
age  → 25
city → "Bangalore"

The keys are called **properties**.

### Using `new Object()`

const user = new Object();

user.name = "Ajay";
user.age = 25;

It works, but object literals are generally preferred because they're simpler.

### Using `Object.create()`

const user = Object.create(null);

user.name = "Ajay";

`Object.create()` creates an object with the prototype you specify. We'll cover this in detail in the **prototype** topic.

## 2. Property Access

There are two main ways.

### Dot Notation

const user = {
    name: "Ajay",
    age: 25
};

console.log(user.name);
console.log(user.age);

Use this when you know the property name directly.

### Bracket Notation

console.log(user["name"]);

Bracket notation becomes especially useful when the property name is stored in a variable:

const key = "name";

console.log(user[key]);

Output:

Ajay

If you write:

console.log(user.key);

JavaScript looks for a property literally called `"key"`.

That's an important difference.

## 3. Computed Properties

Computed properties allow you to **use an expression as an object property name**.

const property = "name";

const user = {
    [property]: "Ajay"
};

console.log(user.name);

Output:

Ajay

Without the brackets:

const user = {
    property: "Ajay"
};

the property would literally be called `property`.

### Practical Example

const key = "age";
const value = 25;

const user = {
    [key]: value
};

console.log(user.age); // 25

So:

[property]

means:

> Evaluate the expression and use its result as the property name.

## 4. `Object.keys()`

Returns an array containing the object's **own enumerable property names**.

const user = {
    name: "Ajay",
    age: 25,
    city: "Bangalore"
};

console.log(Object.keys(user));

Result:

["name", "age", "city"]

### Common Use

Object.keys(user).length

can be used to find the number of enumerable own properties.

## 5. `Object.values()`

Returns an array containing the object's **own enumerable property values**.

console.log(Object.values(user));

Result:

["Ajay", 25, "Bangalore"]

## 6. `Object.entries()`

Returns an array containing **key-value pairs**.

console.log(Object.entries(user));

Result:

[
    ["name", "Ajay"],
    ["age", 25],
    ["city", "Bangalore"]
]

This is useful when you want to loop over both the key and value:

for (const [key, value] of Object.entries(user)) {
    console.log(key, value);
}

Output:

name Ajay
age 25
city Bangalore

## 7. `Object.assign()`

`Object.assign()` copies properties from one or more source objects into a target object.

const user = {
    name: "Ajay"
};

const details = {
    age: 25,
    city: "Bangalore"
};

Object.assign(user, details);

console.log(user);

Result:

{
    name: "Ajay",
    age: 25,
    city: "Bangalore"
}

### Important: It Modifies the Target

In:

Object.assign(user, details);

`user` is modified.

### Creating a New Object

A common pattern is:

const result = Object.assign({}, user, details);

Now `user` itself isn't modified.

## Important: `Object.assign()` is a Shallow Copy

This is a common cross-question.

const user = {
    name: "Ajay",
    address: {
        city: "Bangalore"
    }
};

const copy = Object.assign({}, user);

The top-level properties are copied, but nested objects are still referenced.

So:

copy.address.city = "Delhi";

will also affect:

user.address.city

because both refer to the same nested object.

This is called a **shallow copy**.

We'll connect this later with `structuredClone()`.

## Quick Interview Comparison

| Method                          | Returns                                |
| ------------------------------- | -------------------------------------- |
| `Object.keys(obj)`              | Array of keys                          |
| `Object.values(obj)`            | Array of values                        |
| `Object.entries(obj)`           | Array of `[key, value]` pairs          |
| `Object.assign(target, source)` | Target object after copying properties |

## Interview Answer

If asked **"How do you work with objects in JavaScript?"**, you can say:

> **Objects store data as key-value pairs. We can create them using object literals and access properties using dot or bracket notation. Bracket notation is especially useful for dynamic property names. JavaScript also provides methods like `Object.keys()`, `Object.values()`, and `Object.entries()` to retrieve object data, while `Object.assign()` can copy properties between objects. `Object.assign()` performs a shallow copy, so nested objects are still shared by reference.**

## One Thing to Remember

Object
 ↓
keys()     → keys
values()   → values
entries()  → [key, value]
assign()   → copy/merge properties
# 6. Prototype & Inheritance — Deeper Concepts

One of the **most important JavaScript interview topics**, especially at 3+ years.

The first thing to understand is that JavaScript uses **prototype-based inheritance**.

## 1. What is a Prototype?

Basically, a **prototype is an object from which another object can inherit properties and methods**.

Every normal JavaScript object has an internal link to another object called its **prototype**.

const user = {
    name: "Ajay"
};

console.log(user.toString());

We never defined `toString()` inside `user`.

So where did it come from?

`user` ultimately inherits it through the **prototype chain** from `Object.prototype`.

## 2. Prototype Chain

When you access a property:

user.name

JavaScript first checks the `user` object. If it doesn't find the property, JavaScript looks at the object's prototype. If it isn't there either, it continues upward.

Example:

user
  ↓
Object.prototype
  ↓
null

This is the **prototype chain**.

Example:

const user = {
    name: "Ajay"
};

console.log(user.xyz);

JavaScript checks:

user → xyz?
       ↓ no

Object.prototype → xyz?
       ↓ no

null → stop

Result:

undefined

## 3. `prototype` vs `__proto__`

This is a **very common interview question**.

They are related, but they are **not the same thing**.

### `prototype`

`prototype` is primarily a property of **constructor functions/classes**.

function Person(name) {
    this.name = name;
}

Person.prototype.sayHello = function () {
    console.log("Hello");
};

When we create:

const p1 = new Person("Ajay");

`p1` can access:

p1.sayHello();

because `p1`'s prototype points to `Person.prototype`.

### `__proto__`

`__proto__` is an accessor that exposes an object's **prototype**.

console.log(p1.__proto__ === Person.prototype);

Result:

true

So remember:

Person.prototype
        ↑
        │
      p1.__proto__

A simple interview explanation:

> **`prototype` is the object used by constructor functions to provide shared properties and methods to instances, while `__proto__` refers to an object's prototype.**

### Important Modern Practice

Although you'll see `__proto__` frequently in interviews, in production code it's generally better to use:

Object.getPrototypeOf(obj)

and:

Object.setPrototypeOf(obj, prototype)

when appropriate.

## 4. Constructor Functions

Before ES6 classes, constructor functions were commonly used to create multiple similar objects.

function Person(name, age) {
    this.name = name;
    this.age = age;
}

const p1 = new Person("Ajay", 25);
const p2 = new Person("Rahul", 30);

The `new` keyword does several things internally.

Conceptually:

1. Creates a new object
2. Links that object to Person.prototype
3. Calls Person with this pointing to the new object
4. Returns the object

So:

p1.__proto__ === Person.prototype

is:

true

## 5. Why Put Methods on the Prototype?

Consider:

function Person(name) {
    this.name = name;

    this.sayHello = function () {
        console.log("Hello");
    };
}

Every instance gets its **own function object**.

If we create 1,000 persons, we potentially create 1,000 separate `sayHello` functions.

Instead:

function Person(name) {
    this.name = name;
}

Person.prototype.sayHello = function () {
    console.log("Hello");
};

Now all instances can share the same method through the prototype.

p1 ──┐
     ├──> Person.prototype.sayHello
p2 ──┤
     │
p3 ──┘

This is one reason prototypes are useful.

## 6. `Object.create()`

`Object.create()` creates a new object with a specified prototype.

const person = {
    greet() {
        console.log("Hello");
    }
};

const user = Object.create(person);

user.greet();

`user` doesn't directly contain `greet`. Its prototype is `person`.

Conceptually:

user
 ↓
person
 ↓
Object.prototype
 ↓
null

You can verify:

console.log(Object.getPrototypeOf(user) === person);

Result:

true

# 7. ES6 Classes

Modern JavaScript provides `class` syntax:

class Person {
    constructor(name) {
        this.name = name;
    }

    sayHello() {
        console.log("Hello");
    }
}

const p1 = new Person("Ajay");

p1.sayHello();

The important point is:

> **JavaScript classes are primarily syntactic sugar over JavaScript's prototype-based inheritance model.**

The method:

sayHello()

is placed on:

Person.prototype

rather than being recreated for every instance.

You can verify:

console.log(
    Person.prototype.hasOwnProperty("sayHello")
);

Result:

true

## 8. Inheritance with Classes

Example:

class Animal {
    speak() {
        console.log("Animal speaks");
    }
}

class Dog extends Animal {
    bark() {
        console.log("Dog barks");
    }
}

const dog = new Dog();

dog.speak();
dog.bark();

`Dog` inherits from `Animal`.

Conceptually:

dog
 ↓
Dog.prototype
 ↓
Animal.prototype
 ↓
Object.prototype
 ↓
null

So when:

dog.speak();

is called:

1. JavaScript checks `dog`
2. Checks `Dog.prototype`
3. Doesn't find `speak`
4. Checks `Animal.prototype`
5. Finds `speak`

That's prototype-chain lookup.

## 9. Classes vs Prototype-Based Inheritance

Don't say that classes completely replace prototypes.

A better interview answer is:

> **JavaScript is fundamentally prototype-based. ES6 classes provide a cleaner, more familiar syntax for implementing constructor and inheritance patterns, but class methods are still stored on the prototype and inheritance still works through the prototype chain.**

## Most Important Interview Question

### What is the difference between `prototype` and `__proto__`?

Say:

> **`prototype` is a property of constructor functions and classes that is used as the prototype for objects created from them. `__proto__` is an accessor that refers to the prototype of an individual object. For example, if `const p = new Person()`, then `p.__proto__ === Person.prototype`.**

## One Mental Model to Remember

             Person
          (constructor)
               │
               │ .prototype
               ↓
       Person.prototype
               ↑
               │
           p.__proto__
               │
               ↑
              p
          (instance)

When looking for a property:

p
 ↓
Person.prototype
 ↓
Object.prototype
 ↓
null

That's the **prototype chain**.

## Interview-Level Summary

* **Prototype** → object used for inheritance/shared methods.
* **`__proto__`** → accessor to an object's prototype.
* **Prototype chain** → sequence JavaScript searches when a property isn't found.
* **Constructor function** → traditional way to create objects with shared prototype methods.
* **`Object.create()`** → creates an object with a specified prototype.
* **Class** → cleaner syntax built around the same prototype mechanism.
